## Assumptions and deviations

- A1. `canSubmitBrief(..., routeChosen)` returns true for any chosen route (T2's contract), so the `not-ready` gate lives in the wizard (`copyProviderReady` is forced false), not inside `canSubmitBrief`. The spec text "true when routeChosen and the state is ready" is met by the pair.
- A2. `unset` state line says "No route chosen — captions use the server default: <effective>." When a never-chosen team has no provider at all (`effective` null, `message` set), the line is the plain default text without the message; the wizard still shows the message path only for chosen routes, as specced.
- A3. E2E isolation: each case runs on its own team (the `background-notice.test.ts` `freshTeam` pattern), so "reset the setting" is the team's lifetime and `beforeEach`/`afterAll` clear the global model-calls ring. The editor in TC-ROUTE-08 is added to the suite team and the team is soft-deleted afterwards.
- A4. TC-ROUTE-08's 401 uses a bogus session cookie, as TC-HB-06 does: the proxy redirects a cookie-less request to `/login` (200), so a cookie cannot be absent. The first run failed on exactly that; fixed in the test only.
- A5. TC-ROUTE-03/04 create the brief first (while the route is ready or the key is valid) because `POST /api/briefs` is `422` for a not-ready chosen route, then break the route and run `assemble-b`. The run fails with `failureReason` containing the route-named message and records no `copy` call.
- A6. Extra case beyond the spec list inside TC-ROUTE-09: a chosen-and-ready team's wizard POST body has no `copyProviderKey`.
- A7. `tests/e2e/a11y.test.ts` still has a CLI-mode branch ("Register image key" / "Image API key", lines ~765-774, 951, 1214). It runs in API mode, so it passes unchanged; the CLI branch is now stale wording but harmless and untouched (out of T3's files).

- Caller grep (`copyProviderKey|resolveCopyProvider|copyProviderIsClaude|canSubmitBrief|resolveBriefCopyKey` in `src`): no caller needed a change beyond the files above.
