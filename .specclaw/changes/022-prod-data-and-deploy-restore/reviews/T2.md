## Boot safety

- `docker-entrypoint.sh` runs `node dist/scripts/env-preflight.js` after `set -e` and before the `SKIP_MIGRATIONS` branch, so it covers both paths. A non-zero exit stops the boot.
- The preflight imports `@/lib/env`, the same module the app uses. It is not stricter than the app. The scheduler chain is `worker.ts` -> `agent/config.ts`, which imports `@/lib/env`, and `crypto.ts` does too. So the scheduler already validates this same schema at boot, and a scheduler env that fails the preflight would already fail at its worker start. Nothing new is blocked by the preflight itself. The one new effect is that a bad env now fails before the migration rather than after it, which is the intent.
- It is not looser either. The production checks (TOKEN_ENCRYPTION_KEY, BETTER_AUTH_SECRET, minioadmin, the MOCK_AI vs cli check, CLAUDE_CLI_MODEL) all live in env.ts. `auth.ts`'s own placeholder check is mirrored by env.ts's BETTER_AUTH_SECRET check.
- `NEXT_PHASE` is not set at container boot, so the build-phase skip is inert. `ENV NODE_ENV=production` is set in the image.
- The esbuild step uses the same flags as the worker. The `@/` alias resolves, since worker.ts's chain already depends on it, and the image build passed.
