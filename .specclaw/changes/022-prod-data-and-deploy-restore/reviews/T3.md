## Findings

### [WARN] docs/handoff.md:78 — Recovery step is incomplete for a failed carry-over

**Problem:** The text says that if the carry-over fails, "the previous container keeps serving", and that `migrate resolve --rolled-back` is needed "before any retry". A failed migration leaves a failed row in `_prisma_migrations`. Prisma's `migrate deploy` then refuses (P3009) until that row is resolved. That applies to any container whose entrypoint runs `migrate deploy`, including a restart of the previous container or of the scheduler resource. Also, earlier migrations in the same run (for example `20260927120000` through `20261012120000`) have already committed, and the text does not say so. So "wrote nothing" holds only for the carry-over itself.
**Fix:** Say that the resolve step is needed before any restart or redeploy of either resource, not only before a retry. Add that earlier migrations in the run stay applied, so the backup remains the only full recovery. The same applies to the restore bullet.

### [WARN] docs/handoff.md:85 — "3 × legacy" post-check rests on an unverified assumption

**Problem:** The check assumes prod has zero `DraftCaption` rows before the deploy ("Prod has no `DraftCaption` rows before the deploy"). The checklist never makes the operator confirm it. If the assumption is wrong, the check gives a false alarm or a false pass. Nothing in the pre-deploy step 2 records the baseline.
**Fix:** Add `SELECT count(*) FROM "DraftCaption";` to the step 2 query and require 0. Or state the expected post-count as `before + 3 × (drafts converted)`.

### [NOTE] docs/handoff.md:97 — Migration list command uses the local `v2`

**Problem:** The spec writes `origin/main origin/v2`, and this uses `origin/main v2`. After the `git fetch origin` on the previous line, a stale or unpushed local `v2` could produce a wrong list.
**Suggestion:** `git diff --name-only origin/main origin/v2 -- prisma/migrations`. The same applies to the checklist claim at `:100`.
