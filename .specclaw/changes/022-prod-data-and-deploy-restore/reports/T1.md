## Decisions made where the spec left room

1. **The whole migration, including `CREATE TABLE`, is one `DO` block.** That makes it atomic whether or not Prisma wraps the file in a transaction. Scenario 3 shows a failed guard leaves no table at all, so a retry after `migrate resolve --rolled-back` re-creates it cleanly.
2. **The expected text in the guard is derived from `a."copyText"` (the archive), not from the insert's `l."copyText"`.** The two expressions are distinct strings, which is why scenario 3's patch hits exactly once and a wrong write cannot also fool the check.
3. **Two guard checks beyond the spec's three:** the archive row count equals the non-null source count, and no unconverted legacy draft is left (016's predicate). Both are cheap and fail closed.
4. **Channels are an explicit `VALUES` list** (`INSTAGRAM`, `LINKEDIN`, `WHATSAPP`), not `enum_range`. A later enum value cannot change what this historical migration writes.
5. **The test runs Prisma through `node node_modules/prisma/build/index.js`, not `npx`.** It is the same CLI with no shell, so it behaves the same on Windows and in CI. `DATABASE_URL` is always passed explicitly as the scratch URL. Prisma's `.env` loading never overrides an existing env var.
6. **Server source precedence:** `process.env.DATABASE_URL`, then the `.env.test` line, then `setup-test-db.mjs`'s fallback. The database name is always replaced by the hard-coded `bistec_studio_upgrade`. Before any client is created, the script asserts that the derived names are exactly `bistec_studio_upgrade` and `postgres`, and otherwise exits 2. `dropScratch()` re-checks the constant before every `DROP`.
7. **Scenario 1 also covers the schema diff,** which reports in its PASS line, so the output stays one line per scenario.
8. **"migrate deploy on the dev and test databases":**
   - **Test DB:** dropped, recreated and migrated by `npm run test:e2e:db`. All 35 migrations applied in order, `20261012130000_legacy_caption_carryover` included.
   - **Dev DB:** deliberately skipped, by the orchestrator's decision, because it belongs to another checkout. **The stray command in the incident above then migrated it anyway, against that decision.**
   - **The no-op apply on an already-dropped database** is proven by scenario 2 rather than on a live database.
