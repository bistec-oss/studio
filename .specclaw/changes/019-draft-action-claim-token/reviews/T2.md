## Findings

### [NOTE] src/lib/drafts/claim.ts:22-29 — YAGNI / one-liner

`claimWhere` and `claimData` have identical bodies (`{ pendingAction: claim.action, pendingActionClaimId: claim.claimId }`). They name two roles (guard vs write), which reads well at call sites, but it is two functions to keep in sync. Recommend one helper, e.g. `claimFields(claim)`, with `claimWhere`/`claimData` removed, or keep `claimWhere` and have `claimData` documented as an alias (`export const claimData = claimWhere`). Merging is safe: FR-02 only mandates `claimWhere`. Low value either way; do not block.

### [NOTE] src/lib/captions/store.ts:288-291 — Design

The settle's leading guard is a real write (`updatedAt: new Date()`) on a live claim. Harmless (the run is about to complete), and it is what takes the draft lock first per NFR-04. Mentioned only so T3/T4 do not "optimise" it into a read.

### [NOTE] tests/unit/draftActions.test.ts:60-67 — Test quality

`statefulRow` only checks a key when it is present in the WHERE (`k in where`). If a future edit dropped the token from a guard, the late-settle cases would still catch it (the row would change), so this is fine; no action.
