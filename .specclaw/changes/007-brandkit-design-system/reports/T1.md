## Assumptions and deviations

1. **`detectVagueDesign` returns an object, not an array:** `{ candidates, truncated, more }`, because FR-03 needs `truncated` and `more` beside the list.
2. **Overlap rule.** The spec says "earlier start wins, then the longer"; design.md says a later longer match replaces an earlier one. I followed the spec: different starts, the earlier wins; same start, the longer wins. Test: "breathing room around the layout" (`whitespace-share`) beats "breathing room" (`logo-clear-space`).
3. **`nouns` field omitted.** Design.md lists `nouns?` on the entry. The design-noun-within-3-words rule is built into the trigger regex for the ambiguous words (a `near(words, nouns)` helper in `entries.ts`: the word, up to two words, then a noun). `triggers` is `readonly string[]` of regex sources compiled with `giu` by the detector, which is the serialisable form design.md describes.
4. **Form per entry** (the spec left it open): `replace` for `logo-clear-space`, `margin-even`, `edge-blend`; `insert` for `mark-size-match`, `element-scale`, `canvas-share`, `whitespace-share`. `breathing room` is a `logo-clear-space` trigger (the spec lists it under two entries); the layout sense is a longer `whitespace-share` trigger.
5. **Provenance matching is by unit, not by template slot.** Every measurable span in the replacement must have a unit that some range of the entry uses (`%`, `px`, `letters`), and every number in it must lie inside one of those ranges. A different unit, an out-of-range number or no span is `unverified`. A slot-by-slot check would need the model's wording to follow the template order.
6. **`validateProposals` check order:** unknown-candidate, duplicate, too-long / too-short, multi-sentence, forbidden-content, not-measurable, stale-quote. A candidate's first proposal is the only one considered, even if it is rejected (a later one for the same id is `duplicate`). A quote over 160 characters is not separately checked: the detector's patterns cannot produce one.
7. **`containsForbidden`** also rejects any literal kit colour string (case-insensitive), besides the generic hex shape, a URL (`http(s)://` or `www.`), an HTML tag, a code fence, and a kit font name matched as a whole word (so "Poppinsish" is allowed, "pOPPins" is not).
8. **Review reducer.** `accept` and `reject` change a status only on a `pending` edit; `accept` does not touch the text. The host-facing helper is `acceptEdit(state, id, text) => { state, text }` (apply, then `textChanged`), which is a no-op for a non-pending edit. `textChanged` re-checks `pending` and `stale` edits, so a stale edit comes back to `pending` if its quote reappears exactly once (the spec only requires the pending-to-stale direction). `review.ts` imports only the `Edit` type from `authoring/validate`; it does not import the detector (the hook can).
9. **`applyEdit` insert:** after the first `.`/`!`/`?` (followed by whitespace or the end) after the quote, one space, then the sentence. With no terminator it adds `. ` first (the sentence had none); at a newline it inserts before the newline.
10. **Golden string** for `buildBrandKitSystemContext` was captured by running the unchanged function on a fixed kit before any change; the test builds it with `.join('\n')`. `PROMPT_VERSION` in the code is the literal `'2026-10-21.1'`, as the task said.
11. **Static "no sampler" check.** The upgrade and authoring files must not contain the string `sampleImageColors` at all, so none of my comments name it ("the colour sampler" instead). The mocked sampler is also asserted at zero calls after a full detect and validate run.
12. `tsc` initially failed on `extractBrandKitBlock` because `z.ZodType<T>` infers the schema's input type (defaults make fields optional); the helper is generic over `S extends z.ZodTypeAny` and returns `z.output<S>`.
13. New files were formatted with prettier (`--write`), as lint-staged would. `assistant.ts` and other existing files were not reformatted.
