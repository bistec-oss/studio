## Things to check (found while writing the runbook)

1. **🟠 The roll-forward has a gap that the spec doesn't mention.** down.sql restores `copyText` NOT NULL. But `20261011140000_legacy_caption_text` stays recorded as applied in `_prisma_migrations`, so redeploying 012 will **not** re-run `DROP NOT NULL`. Since T9, no 012 code writes `copyText`, so after a roll-forward every new draft insert would fail on NOT NULL.
   - **What the runbook now says:** run `ALTER TABLE "Draft" ALTER COLUMN "copyText" DROP NOT NULL;` before redeploying 012. It flags this step as not in FR-06, to be confirmed in a scratch DB at verify.
   - **Why I'm confident:** it follows from the down.sql text, the T9 note ("a draft create against a DB without migration 3 fails on NOT NULL") and how Prisma records applied migrations. **I couldn't test it**, since this is a docs-only task and no DB may be touched.
   - **Suggested next step:** the verify could add this to TC-CAP-13's scratch-DB check, or the spec/down.sql could gain a matching `prisma/rollback/012-…roll-forward.sql`.
2. **Rollback step 1 (stop both 012 containers before down.sql) is mine.** It is not in FR-06. It follows from the same fact: once NOT NULL is restored, a still-running 012 container can't create drafts.
3. **"The old container can't read a 012-created draft during the cutover"** is stated as the one exception to "the old container keeps working". The reason is the same as the T9 review's: the old client treats the column as non-null. The spec's Edge Cases mention only the reverse direction (old-container drafts).
4. **Whether the old image's `migrate deploy` refuses the three newer migrations** is left as "if it refuses, use `SKIP_MIGRATIONS=1`", as FR-06 words it. I did not establish which way Prisma 5 goes.

## Resolution of item 1 (orchestrator, user decision 2026-10-11)

The user chose to make down.sql self-healing instead of adding a manual step. The change has five parts:

- **`prisma/rollback/012-per-channel-captions.down.sql`:** after restoring NOT NULL, it now runs `DELETE FROM "_prisma_migrations" WHERE "migration_name" = '20261011140000_legacy_caption_text';`. A 012 redeploy's boot `migrate deploy` then re-applies migration 3 by itself.
- **TC-CAP-13** (`tests/e2e/captions.test.ts`) now also proves the roll-forward on the scratch DB:
  - migration 3 is un-recorded;
  - a second `migrate deploy` re-applies it;
  - `copyText` is nullable again;
  - a new draft with no `copyText` saves.
- **Spec FR-06 and the design "Data Model Changes" block** are amended to match.
- **Runbook:** the handoff's manual `ALTER` step is replaced by "Redeploy 012, no manual step". `e2e-test-plan.md` TC-CAP-13 is updated.
- **Checks:**
  - tsc is clean;
  - `npm run test:e2e:mock -- tests/e2e/captions.test.ts -g "down.sql" --retries=0` passed 1/1;
  - **mutation:** with the `DELETE` removed, the case fails with "Expected: 0, Received: 1". The file was then restored, and the scratch DB is dropped.
