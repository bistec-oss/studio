**Status:** built. tsc is clean, lint has 0 errors (the 7 pre-existing warnings), and unit is 73 files / 2022 tests. A targeted E2E run passed 107/0, and a throwaway smoke spec of the new controls passed 1/1; that spec has since been deleted. Nothing is committed.

## What changed

### `CaptionPanels.tsx`

- **The one regenerate POST** lives in `regenerate(body, failure)`. Its body is `{}`, `{channel}` or `{headline:true}` (FR-11).
  - It shares one `firing` flag, so every panel locks while any POST is in flight.
  - It returns `false` when the request is refused, and toasts the server message. The fallbacks are "Failed to regenerate the captions", "… the caption" and "… the headline" (FR-20 table).
- **`locked` = `firing || pendingAction !== null`** (A2). It disables every Regenerate and Undo, and "Regenerate all".
- **"Regenerate all"** first waits for any caption panel's save on blur to land (`flush()`). It then calls `capture()` on each panel's undo handle **before** firing. If the request is refused, it runs the revert each `capture()` returned (see Review fixes).
  - The handles are a stable `Map<Channel, RefObject<CaptionUndoHandle>>` built once from `CAPTION_CHANNELS`.
  - The headline has no handle, so "Regenerate all" never touches it (A9).
- **`HeadlinePanel`** is the first sub-panel. Its skeleton is `captionActionTargets(draft).includes('HEADLINE')`, as FR-19 requires.
- **The headline field is disabled while `pendingAction === 'REGENERATE_COPY'`,** because the PATCH would 409 then (FR-12).
- **Unchanged:** the h2 "Captions", "Regenerating…", "Writing the captions…" and "Regenerate all".

### `CaptionPanel.tsx`

- **One `useUndoableAction<string>` per panel.** Its restore PATCHes `{channel, text}` for this channel only, then sets the field and calls `onSaved()`.
- **The undo snapshot is what the field shows,** so text typed but not yet saved can come back too.
  - An empty field takes no snapshot; Undo would restore nothing.
  - `useImperativeHandle(undoRef, …)` exposes `capture` (it returns a revert) and `flush` for "Regenerate all".
- **When a regenerate settles,** a PENDING → not-PENDING change, the snapshot is dropped if the text is unchanged. A failed regenerate keeps its text (A7), so it leaves nothing to undo.
- **The tail order is:** save state · Undo (only with a snapshot) · Copy · Generate/Regenerate.
  - The verb is "Generate" when the field is empty.
  - The button shows a spinner while its own row is PENDING.
- **Copy** calls `navigator.clipboard.writeText(value)`.
  - On success it toasts "Caption copied". On any failure, including no clipboard API, it toasts "Couldn't copy. Select the text and copy it manually."
  - It is disabled while the row is PENDING, or while the field is empty.
- **The FAILED notice wording** now points at the panel's own button: "… Write it below, or use Generate." It used to point at "Regenerate all". T12 owns the other notices.
- **Exported for `HeadlinePanel`:** `SaveState` (Saving… / Saved / Unsaved changes, the same markup as before) and `count`, so the two panels can't drift apart.

### `HeadlinePanel.tsx` (new)

- **The h3 "Headline".** The tail holds the save state, Undo, and "Generate headline" or "Regenerate headline" (Generate when there is no stored headline).
- **The field** is an `Input`, not ruled (§8.3).
  - It has `aria-labelledby` pointing at the h3 and `aria-describedby` pointing at the helper text, plus the error once there is one.
  - Its placeholder is "Write the headline…".
- **The helper text** reads "The text on the image. Regenerate the design to use a changed headline." The `n / 100` counter (`HEADLINE_MAX`) sits beside it and turns `--status-failed` past 100.
- **Saved on blur** with `PATCH {headline}`.
  - On failure the typed value stays and the state shows "Unsaved changes".
  - The server's message, e.g. "The headline was not saved (…)" on a 400, shows inline as `<p role="alert">`.
  - The field gets `aria-invalid` and a red edge through `aria-[invalid=true]:border-status-failed`. That class wins by specificity, so it doesn't depend on CSS source order (`cn` is a plain join).
- **The snapshot is the field's value when it validates** (`validateHeadline`), and otherwise the stored headline. When neither is non-empty, no snapshot is taken. It is captured before a headline regenerate, and dropped if the regenerate settles with the headline unchanged. This was changed by review F2.
- **The field follows a new server headline** by adjusting state during render rather than in an effect. That keeps lint at the 7-warning baseline. An effect version would have added an 8th `set-state-in-effect` warning.
- **Skeleton:** one line at control height, `role="status"`, named "Generating the headline".

## Notes and choices

1. **Undo after a "Generate" from empty:** the spec says each panel "captures that panel's undo snapshot before firing." When the field is empty, that snapshot would be `''`, and undoing to it would turn a FAILED row into READY with empty text. That isn't useful, so an empty field takes no snapshot. This mirrors the design Undo, which clears when there is nothing to go back to. The spec's AC-24 case (Regenerate WhatsApp, then Undo) is unaffected.
2. **The caption snapshot is the field's value,** not the stored text. A user with an unsaved edit gets that edit back on Undo. The headline snapshot was the stored value at first. Since review F2 it is also the field's value, but only when that value validates (see Review fixes).
3. **Headline save errors are all shown inline,** 409 included, not only 400. The spec names the 400. Showing every PATCH failure beside the field is consistent and loses nothing.
4. **The FAILED notice's last sentence** changed from "use Regenerate all" to "use Generate". The panel now has its own Generate button, as FR-19 describes for a FAILED row. T12 still owns the review, last-regenerate-failed and WhatsApp-guide notices, and the caption counter wording.

## Review fixes (review WARN, `reviews/T11.md`)

### F1: a refused regenerate wiped a live Undo

**Two fixes went in.** The primary fix is the first one: it is correct whatever the timing.

1. **A refusal puts back only what its own call captured.**
   - `CaptionUndoHandle.capture()` now returns a revert, which restores the snapshot that capture replaced (or clears it, if there was none).
   - A panel's `regenerate()` and `regenerateAll()` run those reverts when the request is refused.
   - `HeadlinePanel` does the same inline.
   - **Result:** a refused click never drops an Undo taken by an earlier, successful call.
2. **`firing` stays true until the refetch after the 202 has resolved.**
   - `onActionStarted` is now typed `() => void | Promise<unknown>` and is awaited. The page passes `fetchDraft`, which returns its promise.
   - This closes the A2 window in the UI: there is no enabled button between the 202 and `pendingAction` being seen.
   - The refetch runs outside the POST's error path, so a refetch failure can never count as a refusal and trigger the revert.

### F2: the headline snapshot was the stored prop, not what the user saw

- **The snapshot is now the field's value when `validateHeadline(value).ok`.** Otherwise it falls back to the stored headline. When neither is non-empty, there is nothing to undo.
- **Why the validation check:** an unsaved headline can be invalid (empty, over 100, a fence). The Undo PATCH would 400 on it, so that undo could never succeed.

### A related race the smoke check found

- **What happened:** typing a headline and clicking "Regenerate headline" straight away. The blur-save's PATCH and the regenerate POST were in flight together.
- **Why it broke:** when the claim won, the PATCH got a 409. The regenerated headline was the same as the old stored one, so the field never re-synced. It was left showing the typed text, unsaved.
- **The fix:** each panel keeps its in-flight blur-save promise.
  - A panel's Regenerate awaits it before it captures and fires.
  - "Regenerate all" awaits every panel's `flush()`.
  - The same race existed for captions (a 409 "This caption is being generated" toast), so it is fixed there too.

### Optional NOTE N2: the stale inline 409

**Done.** When `editLocked` goes from true to false, `HeadlinePanel` clears the inline error. This uses the same adjust-during-render pattern as the server-value sync.

- The field stays "Unsaved changes", so the next blur retries the save and shows any real 400 again.
- A 400 shown before a lock is cleared too. That is harmless, because the same retry brings it back.
