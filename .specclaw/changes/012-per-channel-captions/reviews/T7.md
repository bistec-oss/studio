# Review: 012 T7 (publishing through the one resolver)

**Mode:** full. **tsc:** clean. **Unit (jobRunner, channels, captionResolve):** 56/56.

## Spec compliance

Built what T7 said: every publish path now ends in `publishToChannel(channel, exportKey, draftId, teamId)`, which resolves the channel's caption through `loadCaptionForPublish` before signing the export. Immediate POST, job runner, retry route, MCP `publish_post` and ACP `publish_post` (ACP delegates to the MCP tool) all go through `createAndPublishPost` or `publishToChannel`. Scheduler post-actions (`executePostAction`) only create SCHEDULED rows, so they reach the job runner and the resolver at publish time (FR-16). No scope creep.

Grep of `copyText` in `src` outside components: no read on any publish path. Remaining reads are the backfill/store (legacy migration source), `generateDraft` placeholders, social publisher parameter names, and MCP `getDraft` (see NOTE 1).

## Key checks

- Fail closed: the publisher-map miss (WhatsApp) throws a terminal error with the shared `unavailableReason`. A non-ok resolution throws a terminal `PublishError` before `resolveExportUrl`. The publisher receives only `caption.text`.
- Job runner: a terminal error sets FAILED with `nextRetryAt: null` (which also clears the claim lease) and leaves `retryCount` alone. A non-terminal error keeps the existing backoff, and `draft export missing` stays retryable. Every branch of the catch updates the row, so nothing stays in PUBLISHING.
- POST 422 `CAPTION_UNPUBLISHABLE` happens before any `post.create`, on both the scheduled and immediate paths, so it leaves no row.
- Tenancy: the posts routes' team and visibility checks are untouched. `draft.caption` is the post's own channel only (`loadCaptionText(draft.id, post.channel)`), so no other channel's text leaks.
- `mockPlatformId` is only called inside the `MOCK_SOCIAL` branches. The helper is exported but harmless.

## Findings

### [NOTE] src/mcp/tools/generate.ts:103 - stale legacy `copyText`

**Problem:** `getDraft` still selects and returns `copyText: true`. After T8/T9 this is the legacy column, not a channel caption. It is not a publish path, so it is outside T7.
**Fix:** confirm T8 (or the MCP task) replaces it with per-channel captions; otherwise it will serve stale or empty text.

### [NOTE] src/app/api/posts/route.ts:41-47 - check order

**Problem:** the caption check runs before the `scheduledAt` validation (400) and before the `findLivePost` 409. A duplicate request on a draft whose caption has since failed returns 422 rather than 409, and a bad `scheduledAt` costs a DB read plus a possible legacy materialization write first.
**Fix:** move the caption block to just after the duplicate guard if the 409 or 400 precedence matters. No change needed otherwise.

### [NOTE] src/app/api/posts/route.ts:119-129 - per-post caption load on the list GET

**Problem:** `loadCaptionText` calls `loadDraftCaptions` per post, up to 50 per page. That is up to 50 extra queries, and a legacy draft can trigger a materialization write inside a GET.
**Fix:** acceptable at this size; batch by draft id if the library list gets slow.

### [NOTE] src/mcp/tools/publish.ts:41 - refusal records a FAILED row

**Problem:** MCP and ACP `publish_post` have no up-front caption check, so a refused caption creates a PENDING then FAILED Post row and throws. The POST route returns 422 with no row. The result is safe and fail-closed, just inconsistent. It matches the report's note that the 201-on-FAILED behaviour is pre-existing.
**Fix:** optional. Call `loadCaptionForPublish` before `createAndPublishPost` to mirror the route.

## Verdict

No correctness, security or tenancy defects. The fail-closed boundary holds on every path, terminal errors never retry, and the tests are falsifiable per the report's three mutations. Only minor consistency notes remain.
