## Findings

### [NOTE] src/lib/captions/backfill.ts:12-13 - env coupling

`import { prisma } from '@/lib/prisma'` pulls in `@/lib/env`, whose production assertions throw on any missing or invalid variable (env.ts:104). The backfill's default client is unused because the CLI passes `db`, but the module-level `new PrismaClient()` still runs. A bad env fails the boot at the backfill instead of at `server.js`. That is harmless, since the app would refuse to start anyway, and it matches the scheduler bundle. No change is needed. Make the `prisma` default lazy only if the scheduler resource's env ever differs from the app's.

### [NOTE] src/lib/captions/backfill.ts:89 - unbounded lock wait

`pg_advisory_lock` blocks with no timeout. A stuck holder, such as a crashed session that is still open server-side, hangs boot silently. This is the same trade-off `migrate deploy` makes, and it fits the design (serialize, then find nothing left). Optionally log "waiting for caption backfill lock" before the lock call.

### [NOTE] src/lib/captions/store.ts:285-296 - claimCaptionAction marks rows only if they exist

`tx.draftCaption.updateMany({ where: { draftId, channel: { in: channels } } ... })` is a silent no-op for a not-yet-materialized legacy draft. It still returns true and sets `pendingAction`. T6's route must call `loadDraftCaptions` before claiming; otherwise the later per-row settle finds nothing. Add a comment or an explicit assertion in T6. It uses the global `prisma` and ignores the `db` injection that the other functions accept.

### [NOTE] src/lib/captions/store.ts:215-217 - log line carries unsanitised topic

`topic "${d.brief.topic}"` is user text embedded in a log line. A newline in it can forge a `[captions] REVIEW` line. Low impact. Optionally use `JSON.stringify(d.brief.topic)`.

### [NOTE] Rolling cutover

An old container that edits `copyText` after the draft has been migrated loses that edit, because the new code reads rows only. The spec covers the in-flight regenerate case (defer, then materialize the newest text). It does not cover a post-migration edit during the cutover window, which is brief. This is recorded here and needs no change in T4.

## Key checks (no defect found)

- **Migration SQL:** it matches the schema (enums, `TEXT` default `''`, `PENDING` default, `needsReview` default false, `TIMESTAMP(3)` defaults). It has the named CHECK `status <> 'FAILED' OR text = ''`, an FK with `ON DELETE CASCADE`, and a unique `(draftId, channel)` index. It is additive only (two nullable `Draft` columns, no DROP or RENAME), so AC-27 holds.
- **Entrypoint:**
  - It sits inside the `SKIP_MIGRATIONS` else-branch under `set -e`, after `migrate deploy`.
  - It fails the boot only on a top-level error. Per-draft errors are caught and counted at backfill.ts:116, which matches FR-04's failure handling and A8, so a bad draft cannot crash-loop prod.
  - Both resources boot through it, and the advisory lock serializes them. The loser finds `captions: none` empty and writes 0.
- **Advisory lock:** the CLI forces `connection_limit=1`, so lock, work and unlock share one session. Unlock is in `finally`. `$transaction` on the single connection runs sequentially, so it cannot deadlock.
- **Lazy path:** no lock is needed. `createMany skipDuplicates` plus `updateMany where captionMigration: null` make it race-safe, and `written` is true for exactly one caller.
- **Keyset paging:** the cursor advances on `(createdAt, id)` regardless of outcome, so deferred drafts cannot loop forever. The `page.length < pageSize` break is correct.
- **Materializer:** `materializeStep` returns null when rows exist, the outcome is recorded or the text is null, so it never writes in those cases. Both defer conditions are covered.
- **REVIEW lines:** the statuses SCHEDULED, PENDING and PUBLISHING exist in `PostStatus` and match the spec. Both the draft filter and the posts select use them.
- **`saveGenerationCaptions`:** the row guard is `status: 'PENDING'`, FAILED rows carry `text: ''` (CHECK-safe), and the headline is written only when valid.
- **Wiring:** the Dockerfile bundle uses the same flags as the worker. `COPY dist` carries it into the runner, and the report says this was checked on the image.
- **npm scripts:** `--env-file=.env` is the existing convention. The report notes the T10 CI caveat.
- **Tests:** the Prisma-mocked tests are falsifiable. The report lists 8 mutations that each turned a test red, and I have no contrary evidence.

PASS-grade code with only optional notes.
