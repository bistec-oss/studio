# Review: 012 T11 (per-channel regenerate, headline panel, per-panel undo, copy)

**Mode:** full. Reviewed from `git diff -- src/components/drafts` plus the new `HeadlinePanel.tsx`, against spec FR-18, FR-19, A2, A7, A9 and AC-24. Not run: tsc, lint, unit or E2E (wave-2 E2E is T13).

## Spec compliance

Present and matching the spec:

- **FR-18:** the Headline panel has an `Input` named by `aria-labelledby` its h3, is not ruled, and shows the exact helper text and an `n / 100` counter.
- **FR-19:** Generate/Regenerate (and "... headline") flips on empty text. Buttons are disabled while any action is pending (`locked`). Undo is per panel and PATCHes only its own channel or the headline. Copy uses `navigator.clipboard.writeText` and the exact toasts. The headline skeleton is driven by `captionActionTargets`.
- **A2, A9:** single-flight is draft-level. "Regenerate all" posts `{}`, so it never touches the headline.
- **A7:** a failed regenerate that leaves READY text is handled by the settle effect, which drops the Undo.

Not in this task, correctly: the notices, the WhatsApp guide and the caption counters (T12).

## Self-declared departures

1. **No snapshot of an empty field: ACCEPTABLE.** FR-19 says "captures that panel's undo snapshot", and AC-24 only requires Regenerate then Undo to restore the previous text. Undoing a Generate back to `''` would PATCH an empty text onto a row that was FAILED, and A7's `FAILED => text=''` constraint means the resulting empty READY row is a worse state than the one it replaces. Nothing to go back to is a fair reading.
2. **Caption snapshot = field text; headline snapshot = stored headline: ACCEPTABLE for captions, see F2 for the headline.**
3. **Every headline save failure shown inline, a 409 included: ACCEPTABLE.** Dropping the typed value would be worse. See N2 on staleness.
4. **FAILED notice wording "... or use Generate.": ACCEPTABLE.** FR-19 names "Generate" as the FAILED row's recovery, and the old text pointed at a button that no longer matches. It is a necessary consequence, not T12 creep. Risk: a T10 or other E2E assertion on the old "Regenerate all" wording (named risk, not checked per the no-crawl rule).
5. **`useImperativeHandle` undoRef: ACCEPTABLE.** "Regenerate all" must capture three snapshots held in three hooks, so this is the smallest way. The un-memoised handle is harmless.
6. **State adjusted during render: ACCEPTABLE.** This is React's documented pattern, guarded by `stored !== shown`, so it does not loop.
7. **`SaveState` and `count` exported: ACCEPTABLE**, with a coupling note in N1.

## Findings

### [WARN] CaptionPanel.tsx `regenerate()` and CaptionPanels.tsx `regenerateAll()` — single-flight race clears a live Undo

**Problem:** `captureUndo()` runs before firing, and `if (!(await onRegenerate())) undo.clear()` runs when the request is refused. `locked` only turns on from `firing` or the polled `pendingAction`. `onActionStarted()` is not awaited, so between the 202 and the refetch the buttons are enabled again. A second click in that window (another panel, or the same one) is refused with 409. Its `undo.clear()` then wipes the snapshot the first, successful call just took. `regenerateAll` does the same to all three handles. The result is a missing Undo after a successful regenerate.
**Fix:** only clear what this call captured. Have `capture` return whether it replaced a snapshot and restore the prior one on refusal. Alternatively, keep `firing` true until `onActionStarted` has settled (await the refetch), which closes the window for every panel.

### [WARN] HeadlinePanel.tsx `regenerate()` — headline snapshot is the prop, so a just-typed headline is lost from Undo

**Problem:** `if (headline) undo.capture(headline)` captures the stored prop. Typing, then clicking Regenerate, blurs the field first, so the save PATCH runs and the typed text becomes the stored value. The prop only updates after the `onSaved` refetch, which may not have landed by the click. Undo then restores the older headline, not the one the user just saw. Captions capture the field text, so the two panels disagree. Departure 2's rationale (stored, so Undo equals "what the design used") is not what the spec asks for: FR-19 says "that panel's undo snapshot", with no stored/unsaved distinction.
**Fix:** capture `value` (non-empty) as the caption panel does, or document in the report why stored is intended and test it in T13.

### [NOTE] N1 — HeadlinePanel imports `SaveState` and `count` from `CaptionPanel.tsx`

**Problem:** a sibling-to-sibling import. It works, but `CaptionPanel` now carries the shared pieces.
**Suggestion:** leave it (YAGNI); move both to a small shared file only if T12 adds a third consumer.

### [NOTE] N2 — HeadlinePanel.tsx: an inline 409 stays after the lock lifts

**Problem:** `error` clears only on the next save or a changed server value. A 409 shown during an action lingers after the draft unlocks, with `role="alert"` still on the page.
**Suggestion:** also `setError(null)` when `editLocked` goes false, or on the next `onChange`.

### [NOTE] N3 — settle effects depend on observing the busy/PENDING phase

**Problem:** the `wasPending`/`wasBusy` effects clear a stale Undo only if a poll saw the busy state. A fast regenerate that fails between polls is never observed, so Undo stays and restores the identical text. It is harmless and self-correcting.
**Suggestion:** none needed.

### [NOTE] N4 — HeadlinePanel.tsx `h-control-md`, `aria-[invalid=true]:border-status-failed`

**Problem:** these are Folio tokens as far as the diff shows, and the diff alone cannot confirm that `h-control-md` and the border-status token exist. `uiTokenGuard` will catch a bad palette class, but a missing token class would silently render unstyled.
**Suggestion:** confirm in the T13 visual or render pass.

## A11y check

- **Names:** the three-caption Regenerate buttons are "Regenerate <Label> caption", Undo is "Undo <Label> caption", Copy is "Copy <Label> caption", and the headline buttons carry distinct visible text. Each aria-label contains its visible text, so label-in-name holds.
- **Wiring:** the headline `Input` uses `aria-labelledby`, with `aria-describedby` switching on the error and `aria-invalid` set.
- **Alert and status:** the error is `role="alert"` and the skeleton is `role="status"`.
- **Blur:** no double PATCH on blur, because `save()` is guarded by `saved` and `value === stored`.

## Verdict

Spec is met and all seven departures are acceptable, with F2 narrowing departure 2. One real race (F1) and one inconsistency (F2) should be fixed before wave-2 E2E, but neither blocks the build.

## Re-review of fixes

Reviewed from `git diff -- src/components/drafts` (full T11 diff) plus the three components as they now stand and `useUndoableAction`. Not run.

**1. Are F1 and F2 resolved? Yes.**

- **F1:** `captureUndo()` returns a revert closing over the `previous` snapshot it replaced, so a refusal restores only its own capture. `regenerate()` keeps `firing` true until the awaited post-202 refetch, which closes the window in which a second click could get a 409. The `useUndoableAction` `capture` and `clear` are stable `useCallback`s, so the revert has no stale-closure problem. The handle is rebuilt every render (no deps), so `regenerateAll` reads the latest `value` after its `await flush()`.
- **F2:** the headline snapshot is now the field value when `validateHeadline(value).ok`, else the stored headline, else nothing. It matches the caption panels. The server re-normalises the value on the Undo PATCH, so passing the raw value is safe.
- **Third race (blur-save vs claim):** the fix is sound. Each panel keeps the blur-save promise in a ref, and Regenerate awaits it. `save()` catches every error (toast or inline), so the stored promise never rejects and `flush()` cannot reject. It could hang only if `apiFetch` itself never settles, in which case the existing save would hang the same way. That is accepted.
- **N2:** done, via render-time adjustment on the `editLocked` true-to-false edge.

**2. New bugs? None blocking.**

- **Stuck `firing`:** no. A failed POST sets `false` and returns false. A rejected refetch is swallowed and the `finally` sets `false`. A refetch that resolves slowly keeps the buttons disabled, which is the intent.
- **Unhandled rejections:** none. `onBlur` stores a promise that cannot reject, and `onActionStarted` is wrapped in try/catch. The `onActionStarted` type was widened to `void | Promise<unknown>` and the page passes `fetchDraft`, which is compatible.
- **Revert correctness:** a refused regenerate-all calls three reverts, and each restores its own previous snapshot or clears, as intended. Caveat: a revert is a plain `capture(previous)`, so if something else changed the snapshot in between (nothing can while `firing` holds the lock), it would overwrite it. Acceptable.

**3. Simplicity.** It is about as small as it can be. The flush is one ref plus one handle member per panel. The revert closure is shorter than a stack or token scheme would be. The duplicated "inFlightSave ref + onBlur assignment" in two panels is small enough not to extract.

### [NOTE] N5 — "Regenerate all" does not flush the headline's blur-save

A headline blur-save is not awaited by `regenerateAll`, because only caption panels expose a handle. The PATCH is dispatched on blur before the click handler runs, so it normally reaches the server first. If it loses the race it 409s, shows an inline error, and the field is left unsaved until the next blur. Low probability, and recoverable (N2 clears the stale error). Optional fix: add `flush` to the headline too. Not needed for this task.

### [NOTE] N6 — a snapshot can be a value whose save failed

If the blur-save fails (for example a 409) and the user then regenerates, the snapshot is the typed, unsaved text, and Undo would write it. It matches the "what the field shows" rule the spec implies, so no change is requested.

No remaining WARN or BLOCK.
