# T15 review: export-posts / import-posts carry captions and the headline (full mode)

Diff: `scripts/export-posts.mjs`, `scripts/import-posts.mjs`. Judged against FR-22 (scripts) and the four declared items.

## Spec compliance

- **FR-22:** met. Export adds `captions: true`, a top-level `captions` array and `counts.captions`; `headline`, `captionMigration` and `legacyCaptionText` ride in the scalar draft rows. Import restores them, and a v1 bundle's `copyText` goes to `legacyCaptionText` with no rows, which the loader materializes on first read.
- **Declared 1 (version 1 to 2):** correct. An old importer rejects a v2 bundle rather than creating drafts with no caption. The new importer accepts 1 and 2. Good.
- **Declared 2 (createMany skipDuplicates):** correct in intent; see the first WARN for one gap.
- **Declared 3 (PENDING rows imported as-is):** acceptable. Caption rows are not publish-scheduler work (unlike PENDING Posts, which are deliberately skipped), so nothing acts on them. A PENDING row whose generation never completes would show as pending until the stale sweep or a regenerate; same as at the source. NOTE-level only.
- **Declared 4 (teamId):** T15 did not make it worse. The new code adds no tenancy-bearing model: `DraftCaption` has no `teamId` in the written fields. It only adds a `draftCaption` write that follows the same draft creation that already fails.
- **Scope:** nothing extra. The dry-run per-draft log lines are small and serve the "dry-run is truthful" verification.

## Findings

### [WARN] `scripts/import-posts.mjs` caption import touches drafts that already existed

**Problem:** The caption filter runs over all bundle captions, not only those of drafts created in this run. `haveDrafts` drafts are skipped in the draft loop (`if (haveDrafts.has(d.id)) continue`), but their bundle captions are still inserted whenever the local draft lacks that `(draftId, channel)` row. Example: a draft already imported from a v1 bundle (legacy text, no rows, not yet read) is later re-imported from a v2 bundle; it now gets rows from the bundle while its own `legacyCaptionText` and `captionMigration` are untouched. The header promises "nothing on the target is overwritten", and the comment says "a re-run never changes an existing caption"; this adds captions to an existing draft, so the draft can end up with rows and an un-migrated legacy column. The materializer treating rows as authoritative probably makes this harmless, but it is an unreviewed state.
**Fix:** restrict to new drafts: `const newDraftIds = new Set(drafts.filter(d => !haveDrafts.has(d.id)).map(d => d.id))` and filter `captions` by `newDraftIds.has(c.draftId)`. Then the composite-unique slot check is only a guard against the loader having materialized rows in the gap, and the "skipped" count reflects it.

### [NOTE] Composite-unique skip and ids

**Problem:** Ids are not remapped (draft and caption ids are the bundle's), so the skip-by-id and skip-by-slot checks are consistent. Drafts are created with their original id, so a caption's `draftId` always resolves. No defect; noted because the question was raised. With the WARN fix above, the slot check would rarely fire.

### [NOTE] Dry-run truthfulness

**Problem:** The dry run counts `newCaptions` against the real DB (existing ids and slots), so the counts match a real run, and per-draft lines print the same `data` object the real path writes. One caveat: in a dry run a caption for a draft that is "created" is counted even though the draft isn't written, which is correct. The `captions:` summary line prints `created` from the pre-write count; in a real run it is replaced by the `createMany` count, which is accurate.
**Fix:** none.

### [NOTE] Both keys present

**Problem:** `"legacyCaptionText" in d ? d.legacyCaptionText : (d.copyText ?? null)` prefers the new key when both exist, including a null `legacyCaptionText` over a non-null `copyText`. That is right for a v2 bundle (null means post-012 draft) and cannot occur from this exporter (it never emits `copyText`). A hand-merged bundle with both would silently drop `copyText`.
**Fix:** none needed.

### [NOTE] Dead code

**Problem:** None found. `_captions` is destructured out deliberately; `draftCaptionFields` is used once but names the v1/v2 mapping, which is worth the helper.

## Risk named (outside the diff)

`headline` is "required, fenced" in 012 for new drafts. A v1 import writes `headline: null`; that relies on the schema column staying nullable with the Topic fallback (FR-03). The dry runs in the report show it works against the current schema.

## Verdict

One WARN (caption rows added to already-present drafts), no BLOCK. Everything declared holds.
