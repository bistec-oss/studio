## Spec compliance

- Review notice: `Notice tone="warning" role="status"`, text is verbatim FR-19. PASS.
- Last-regenerate-failed notice: `tone="warning"`, text "The last regenerate failed: <reason>. The caption below is unchanged." is verbatim. Shown only for READY + failureReason. PASS.
- FAILED notice: `tone="error"` with the reason, as FR-19 says ("shows Notice tone=error with its failureReason and the Generate button"). FR-19 gives no exact sentence, so T11's wording "... Write it below, or use Generate." is allowed.
- Counters: `1,234 / 2,200 (Instagram)` and `412 / 1,000 guide` match. `toLocaleString('en-US')` is pinned, so the separators are exact in any browser locale. Headline `n / 100` is unchanged.
- "Over the <Label> limit" is shown with `text-status-failed`. The guide warning "Longer than the 1,000-character guide" uses `text-status-scheduled`. Both match FR-19 and neither blocks saving.
- WhatsApp helper text is verbatim (spec line 417), and it is shown only for non-publishable channels.

## The three choices

1. No `role` on the FAILED and last-failed notices: **confirmed.** FR-19 gives `role="status"` to the review notice only, and the notice primitive adds no role of its own. Adding `role="alert"` to notices that arrive by polling would be a spec addition.
2. WhatsApp counter stays grey past 1,000: **confirmed.** FR-19 turns the counter red for a hard limit only. For the soft guide it adds a separate amber warning, which is what the code does.
3. Review notice follows the server's `needsReview`: **confirmed.** FR-19 says it goes "when the row is edited or regenerated", and the server clears the flag on a save. See risk R1.

## Quality

- `aria-describedby`: every id is rendered whenever it is listed. `reviewId`, `failureId`, `helpId` and `warningId` are tied to the same conditions as their elements. `failureId` is on two notices, but they are mutually exclusive (`FAILED` vs `READY`). `counterId` is always listed and always rendered in the non-pending branch. No dangling ids. The headline's `counterId` is rendered in the same branch as the input.
- Tokens: only `status-failed`, `status-scheduled` and `fg-muted` are used. There are no raw colours.
- Simplicity: this is one derived block with no new state. Fine.
