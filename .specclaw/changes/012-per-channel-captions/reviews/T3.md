# T3 review: migration planner and publish resolver (full mode)

Verified: `npx tsc --noEmit -p .` clean; `vitest run` on both test files 57/57.

**Spec compliance:** FR-05 and FR-14 are built as written. The six rule strings match the spec exactly, the order is right, and the stored text is returned unchanged. No scope creep. Both modules import only `@/lib/channels` and `type Channel`, so they are client-safe.

## Key checks

- **Text loss: impossible by construction.**
  - The SPLIT conditions require `lines.slice(0, headers[0].line)` to be blank, so there is no prose before the first header.
  - Every later line belongs to some section, and `rest` is kept.
  - Any extra or duplicate header falls back to the full legacy text.
  - The empty-after-normalise check runs before storing, so IG and LI are never blank for non-blank input.
- **Header grammar.**
  - Handled: `**LinkedIn:**`, `Instagram caption:`, `## WhatsApp`, `LinkedIn Post`, lowercase, trailing spaces. The `\1` backreference to a non-participating group matches empty in JS, so unwrapped headers work. `#instagram` and `IGLOO` are correctly not headers.
  - Not handled (false negatives): an emoji before the header ("📸 Instagram:"), and "Instagram (caption):". Both fall back flagged `needsReview`, which is the safe direction and matches the spec grammar, so this is not a defect.
- **Normalisation** goes through `captionSpec(channel).normalise`, the same registry function T2 uses. It is consistent.
- **Resolver:** rule 1 uses `isPublishableChannel` (exact uppercase). Counts and the limit use the shared `captionLength` on the untrimmed stored text, which is what would be sent. Whitespace-only text is rule 5. A null `failureReason` or an empty string gives no parenthesis.
- **Tests:** deterministic (mulberry32 seeded, with an explicit determinism test). The report records six mutations that each turned a test red. The AC-02 (a)–(i) and AC-05 cases are present.

## Decisions judged

1. Same-line text needs a colon: agreed. This is a legitimate reading of the spec's "text after the header on the same line", and it prevents "Instagram is where…" from being a header.
2. `#instagram` is not a header: agreed (requires whitespace after `#`).
3. Emptiness is checked after normalise: agreed. It is strictly safer.
4. CRLF is normalised only when splitting: agreed. The fallback stays verbatim, as the spec says.
5. The resolver cannot see the publishers map: accepted, with a condition. T7 must treat a missing publisher as rule 1 with the identical string. tasks.md:58 says T7 "replaces" the current stub with the resolver, but it does not name this requirement. See NOTE 1.
6. A null `failureReason` omits the parenthesis: agreed. The spec string is silent on this case.

## Findings

### [NOTE] src/lib/captions/resolve.ts:30, tasks.md T7 — Design adherence

**Problem:** Rule 1 here covers only "not publishable in the registry". The spec's "or has no publisher" half lives in T7's `publishToChannel`. Nothing in tasks.md T7 states that the publishers-map miss must reuse the exact rule-1 string, and a divergent wording would break AC-17.
**Suggestion:** Add a T7 acceptance line: on a publishers-map miss, throw terminal `PublishError` with `resolveCaptionForPublish(channel, null)`-independent text equal to the rule-1 string. Better: export one `unavailableReason(channel)` from resolve.ts and use it in both places.

### [NOTE] src/lib/captions/migrationPlan.ts:111-112 — Correctness (real-world output)

**Problem:** Models often put a `---` or `***` separator between sections. The grammar has no concept of it, so the separator stays at the end of the preceding section (for example the Instagram caption ends in `---`). Nothing is lost, but the migrated Instagram text has a stray rule and `needsReview` is false. The fallback never has this issue.
**Suggestion:** Optional. Strip a trailing line of only `-`, `*` or `_` (3 or more) from each section body before the trim. Skip if you want to stay strictly on the spec grammar.

### [NOTE] src/lib/captions/migrationPlan.ts:70-77 — Naming

**Problem:** `parseHeader` destructures `[, , name, innerColon, outerColon, rest]`. The two leading slots are the whole match and the wrapper, and positional destructuring hides this.
**Suggestion:** None required. A one-line comment naming the groups would help.

## Verdict rationale

No correctness, security or scope problems. The planner can't lose text, the grammar errs toward the fallback, and the resolver is a faithful single gate. Only minor notes remain: one cross-task obligation for T7 and one cosmetic edge.
