# Proposal: Provider flexibility and onboarding

**Created:** 2026-09-15
**Status:** 🟡 Draft

## Problem

bistec-studio is used by marketing staff, not engineers, but getting a team running still requires engineering-shaped steps — and two of the provider paths are either missing or quietly broken.

**1. Connecting a Claude account requires installing a CLI by hand.** In CLI mode a user's generations bill their own subscription via a personal token pasted at `/settings`. That token comes from `claude setup-token`, which means a non-technical marketer must first install Claude Code locally with no guidance from the product. There is no in-app path and no documented install route.

**2. There is no way to choose a copy model.** The COPY provider slot was deliberately **hidden** in CLI mode on 2026-07-28, on the reasoning that _"Offering it invited admins to register a key that would never be used."_ That removed a misleading control but also removed the choice: a team that wants copy generated by a specific API model instead of the OAuth chain has no way to say so. IMAGE has a provider slot; COPY effectively does not.

**3. The IMAGE slot resolves to nothing for most users, silently.** Both production IMAGE providers are `isEnabled: true` but `isDefault: false`, and `resolveImageProvider` tier 3 requires `isDefault`. A teammate without a personal OpenAI key therefore gets **no AI background at all** — and generation does not fail, it falls back to CSS/SVG. The user sees a worse post and is never told why. Adding more image providers on top of this resolution path would ship a picker over a broken resolver.

**4. There is only one image provider.** Teams cannot use Gemini or any alternative image model.

**5. The CLI `Read` tool is unsandboxed on production.** The prompt-injection review identified CLI-mode vision's `--allowedTools Read` as the sharpest vector — server file disclosure — and it has been live since the CLI switch. Prompt-level hardening landed in PR #30; the OS-level sandbox was left as the residual follow-up and is still open.

## Proposed Solution

Make provider choice explicit and correct, and make first-time setup something a marketer can complete unaided.

1. **Guided Claude account connection.** Document and surface `winget install Anthropic.ClaudeCode` as the supported Windows install route, with an in-app walkthrough from install → `claude setup-token` → paste. Note that the package is a portable install with a known winget tracking defect ([winget-cli#6200](https://github.com/microsoft/winget-cli/issues/6200)) — it does not appear in `winget list` and does not upgrade or uninstall cleanly, so the guide must cover that rather than pretend it is a clean package.
2. **A real COPY provider choice.** Reinstate the COPY slot as a genuine selector: **OAuth CLI (default)** or a registered API model. This revisits the 2026-07-28 decision rather than layering UI on top of it — the slot was hidden because it was cosmetic, and the fix is to make it functional. The existing carve-outs stay: a team that already has a legacy COPY row keeps seeing it, and API mode is unchanged.
3. **Fix `isDefault` resolution.** Repair the live production bug so a team-level image key actually serves teammates without a personal key, and make the silent CSS/SVG fallback visible rather than mute.
4. **Add Gemini (and a pluggable second image provider) to the IMAGE slot**, selectable per team with a default.
5. **Sandbox the CLI `Read` tool** at the OS level, closing the residual item from the security review.

## Scope

### In Scope

- Windows install guidance for the Claude CLI (`winget install Anthropic.ClaudeCode`) plus in-app onboarding for the token flow
- `/settings` and `/team` credential UX for non-technical users
- COPY provider slot: OAuth CLI vs registered API model, reversing the CLI-mode hide
- `resolveImageProvider` — `isDefault` fix, plus surfacing when the AI background was skipped
- Gemini / additional IMAGE provider support and per-team default
- OS-level sandbox for the CLI `Read` tool used by vision

### Out of Scope

- Claude-authored SVG/CSS background art as an image source (considered and not selected)
- A full in-app OAuth flow that removes the CLI requirement entirely — larger, and dependent on capabilities outside this codebase
- macOS/Linux install routes beyond documentation parity
- Refine and design quality — proposals **004** and **007**
- Analytics — proposal **006**

## Impact

- **Files affected:** ~15–25 (estimated) — provider resolution, `/team` and `/settings` UI, provider registration, CLI spawn/sandbox, docs
- **Complexity:** medium
- **Risk:** medium — provider resolution is on the critical path for every generation, and the `isDefault` change alters behaviour for teams that are currently (silently) getting no background. The sandbox work touches the CLI spawn shared by every model call, so it needs care: a too-tight sandbox breaks generation outright.

## Open Questions

- Should the AI-background skip become a **visible warning** on the draft, or a hard failure? It has been silent by design (generation "never throws"); making it loud is a behaviour change users will notice.
- Does reinstating the COPY slot risk re-creating exactly the confusion the 2026-07-28 change removed? Proposed mitigation is that the slot shows OAuth CLI as an explicit selected default rather than an empty slot inviting a key — needs confirming.
- What sandbox mechanism fits the Alpine container — seccomp, a bind-mounted read-only subtree, a dedicated unprivileged user, or running vision in a separate short-lived container? This materially changes the size of the work.
- Gemini image generation has different size/aspect-ratio support than gpt-image. Does `imageSizeFor` need a per-provider capability map, or do we constrain to the intersection?
- Is Windows the only platform that matters for the install guide, or do any users run macOS?

## Decisions (user, 2026-09-30)

- **Item 2 (COPY route) is deferred to 008.** It sits on 008's model resolver, per the ROADMAP soft dependency. 005 builds items 1, 3, 4 and 5.
- **A skipped AI background is a visible warning, not a hard failure.** Generation still completes with CSS/SVG, and the draft says why no AI image was used and how to fix it.
- **The install guide covers Windows and macOS**, each with a full walkthrough. Linux gets a pointer to Anthropic's docs.
- **Image sizing uses a per-provider capability map.** Each provider declares the sizes it supports, and `imageSizeFor` picks the best fit per provider.
- **Item 5, the sandbox mechanism:** researched on 2026-09-30, with the recommendation below. It still needs confirming at plan time.

## Decisions (user, 2026-10-01, at plan start)

- **Item 5, the sandbox: remove the tool.** This confirms the 2026-09-30 research recommendation.
  - Vision sends its images over stdin (stream-json) with `--tools ""`.
  - Every CLI child gets an env allowlist.
  - Non-vision calls also get `--tools ""`.
  - The CLI version is pinned in the Dockerfile.
  - Fallback, if stream-json images fail on the container CLI: `--restricted` plus deny rules. These are defence in depth only.
- **Item 3, the `isDefault` fix: fall back, and make the default explicit.**
  - When a team has no default IMAGE row, the resolver uses its enabled one, the oldest first if there are several.
  - /team makes the default explicit.
  - The draft warns when the AI background was skipped.
- **Item 4, Gemini: mock-verify only.** No Gemini key is available for a live test, so verify-report records Gemini as not live-verified.

## Research: CLI `Read` sandbox (2026-09-30, pre-plan)

**Recommendation: remove the tool instead of confining it.** CLI-mode vision (`vision.ts:114-134`) should send the reference images as base64 image blocks over stdin. The invocation is `claude -p --input-format stream-json --output-format stream-json --verbose --strict-mcp-config --tools ""`, and it creates no temp files and passes no `--allowedTools Read`.

- This was **verified live** on CLI 2.1.285 on Windows. The `system/init` tools list was `[]`, and a test PNG was described correctly.
- It matches the documented streaming-input image support.
- With no tools, an injected "read /proc/self/environ" has nothing to call.

**Why the alternatives lose:**

- **Claude Code's built-in `sandbox` setting** only covers Bash. Read/Edit/Write use the permission system and bypass it.
- **bubblewrap/firejail** need unprivileged user namespaces, which Docker's default seccomp/AppArmor blocks. The CLI docs say nested-container mode "considerably weakens security".
- **A dedicated uid** needs a setuid helper in a non-root container, and gains nothing when the secrets are env vars, not files.
- **A per-call container** needs the Docker socket.

**Fallback, if stream-json images fail on the container's pinned CLI:** use `--restricted` with the cwd set to the temp dir, or a scoped `Read(//tmp/bistec-vision-*/**)` allow plus `Read(//proc/**)` / `Read(//app/**)` deny rules. These are defence in depth only, since pattern rules are not an OS boundary.

**A second finding, in the same scope:**

- `claudeCli.ts:199-211` gives **every** CLI child the whole `process.env` (minus the two Anthropic keys). That includes `DATABASE_URL`, `TOKEN_ENCRYPTION_KEY` and the MinIO credentials.
- The fix is to replace it with an env allowlist (PATH, HOME and the OAuth token), and to add `--tools ""` to every non-vision call as cheap hardening.
- Also pin the CLI version in the Dockerfile (currently an unpinned `npm install -g`), because the stream-json schema can drift.

**Unverified:**

- stream-json images on the container's CLI version;
- Coolify's seccomp profile;
- the bypass forms of `--restricted` and the deny rules.

**Acceptance evidence to plan for:**

- a unit test that the vision args contain `--tools ""` and never `--allowedTools`;
- a unit test that the child env has no secrets;
- a real-CLI injection test, kept out of CI, in which an injected instruction to print `/proc/self/environ` yields nothing;
- a smoke test from the built image.
