## Local stream-json evidence

The local CLI is **`2.1.287 (Claude Code)`**, on win32 with `shell:true`.

**The credential.** The success run used the developer's logged-in CLI session. The child env had `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_*` stripped. No token was read or printed. The dev DB has no stored token, so a success run through `runClaudeCliStreamJson` itself was not possible: `spawnClaude` always injects a token.

**The command:**

    claude -p --input-format stream-json --output-format stream-json --verbose --strict-mcp-config --tools "" --model haiku

**The input line.** It was one line on stdin, then EOF. The data is elided here; the image was a generated 16×16 solid-red PNG.

    {"type":"user","message":{"role":"user","content":[{"type":"image","source":{"type":"base64","media_type":"image/png","data":"<base64 108 chars>"}},{"type":"text","text":"What single colour fills this image? Answer with one word."}]}}

**Success: exit 0.** The events were:

- `system/hook_started` ×2 and `system/hook_response` ×2, from the dev's own user hooks;
- `system/init` with **`tools: []`**;
- `assistant` (a thinking block), then `assistant` (text `"Red"`);
- `rate_limit_event`;
- the result: `{"type":"result","subtype":"success","is_error":false,"result":"Red","api_error_status":null, …}`.

The result event's other keys: `duration_api_ms, stop_reason, session_id, total_cost_usd, usage, modelUsage, permission_denials, terminal_reason, …, num_turns, ttft_ms, duration_ms, uuid, result_index`.

This shows two things:

- the model saw the pixels with no tool;
- several assistant messages come before the result.

**Auth failure: exit 1, stderr empty.** The run used a deliberately FAKE token. The events were:

- `system/init` (`tools: []`);
- `system/api_retry` ×2;
- `assistant` with text `"Failed to authenticate. API Error: 401 OAuth access token is invalid."`;
- the result: `{"type":"result","subtype":"success","is_error":true,"result":"Failed to authenticate. API Error: 401 OAuth access token is invalid.","api_error_status":401, …}`.

Note that a failure can carry `subtype:"success"`. That is why `is_error` is checked independently of the subtype.

**A real-code smoke test.** `runClaudeCliStreamJson` was run inside `runWithClaudeAuth` with a FAKE token through `tsx`, against the real CLI:

- the spawn line was `claude -p --strict-mcp-config --tools "" --input-format stream-json --output-format stream-json --verbose --model haiku`, with `stdin=287 chars`;
- it exited 1 at 5.7s;

## Concerns

1. **The 600k guard now counts image bytes, so CLI vision rejects reference images over about 450 KB raw.** That is roughly 600k base64 characters, summed across all the images in one call. This is a regression in practice.
   - The spec's edge case asked for it, and I implemented it as written.
   - Before T5 the images were files, the Read tool auto-resized them, and they never counted.
   - **Who hits it:** an uploaded 1080×1080 PNG post is commonly 1–2 MB, so F6 image→template and F5 brand-kit assistant calls with real references will now fail in CLI mode. They fail with a clear "reference images are too big — use smaller images" error, not silently.
   - Image tokens are priced by pixel size, not by base64 length, so a text-character guard is the wrong measure for images.
   - **Options** (a decision for the lead or user):
     - (a) measure only the text blocks against 600k, with a separate byte cap below the CLI's 10 MB stdin limit;
     - (b) downscale the images before encoding (e.g. ≤1568px long edge, as the API recommends);
     - (c) keep it as is.
   - **AC-16 in T6 should use a realistic image size,** not just a tiny PNG.
2. **`tests/unit/claudeCliArgs.test.ts`** still lists a `vision` row in its text-mode option table, with the comment "interim T4 options". That row now just exercises `runClaudeCli`, not the vision site. The real vision-site AC-13 coverage is in `visionCli.test.ts`. The file was outside T5's declared list, so I left it; a one-line comment or row removal would tidy it.
3. **The dev's user-level hooks run in every headless spawn.** `SessionStart` `hook_started` / `hook_response` events showed up. Nothing T5 changed causes this: `--strict-mcp-config` doesn't cover hooks, and `--bare` would, but it needs `ANTHROPIC_API_KEY`. It is noted for T6: the container has no user hooks.
4. **`DEP0190`** still prints on every win32 `shell:true` spawn, as T4 noted.
5. **No success run through `runClaudeCliStreamJson` with a stored token.** None exists in the dev DB. The success shape was proven with identical args and the identical line via the logged-in session.
