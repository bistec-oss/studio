## Findings

### [WARN] src/lib/analytics/track.ts:139-153 — Correctness (bound vs AC-02)

AC-02 says an insert that hangs past 2 s returns within 2.1 s. When the insert times out, `count()` then awaits up to a further 500 ms (`COUNTER_TIMEOUT_MS`, line 18), so the worst case is about 2.5 s (the report admits it). The unit test (analyticsTrack.test.ts:108-122) only passes because the counter mock resolves instantly. Either do not await the counter on the timeout path (fire and forget, `void count(...)` already carries its own catch), or state 2.5 s in the spec and add a test with a hanging counter that asserts the total. Not a BLOCK: the caller is still bounded and nothing throws.

### [NOTE-1] src/lib/analytics/catalogue.ts:67 — Design adherence

`verdict: z.string().max(20)` accepts any string, so the insights page cannot trust it. Acceptable given the import-purity constraint; revisit in T2 by extracting the verdict constant into a pure module and importing it.

### [NOTE-2] src/lib/analytics/track.ts:140-150 — Correctness

A timed-out insert is not cancelled. If the database recovers, the row is stored AND the event is counted `dropped`, so "events lost" can slightly overcount. Harmless for an operations signal; worth a line in the docs task.

### [NOTE-3] src/lib/analytics/track.ts:120 — Simplicity

`if (problem !== null || !entry)`: the `!entry` half is only there for the type narrowing (an unknown name already sets `problem`). `const issues = problem ?? 'invalid'` is likewise redundant. Cosmetic.

### [NOTE-4] src/lib/analytics/catalogue.ts:117 — Privacy

`instruction` is capped but not passed through `redactText`. FR-03 and NFR-04 only require the cap, and the user text is the point of the event, so this is compliant. Be aware a user could paste a credential into a refine instruction.

### [NOTE-5] src/lib/analytics/trace.ts — Dead code

`ActionTrace`/`newActionTrace` have no importer yet. This is planned (T2 consumes them), so no action.
