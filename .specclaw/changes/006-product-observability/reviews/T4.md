## Findings

### [WARN] src/app/api/events/route.ts:19 - Security (size cap)

`const text = await req.text()` buffers the entire body before `Buffer.byteLength(text) > MAX_BODY_BYTES`. The cap is not bypassable by a lying/missing Content-Length (good), but the 2 KB limit only bounds what is parsed, not what is read; memory use is bounded only by the framework proxy cap (16 MB, next.config proxyClientMaxBodySize). Authenticated users only, so low severity.
**Fix:** reject early on a Content-Length above the cap, and read `req.body` with a running byte count that cancels past 2048.

### [WARN] src/lib/analytics/queries.ts:136 / sections.tsx:169 - Funnel honesty

`submitted.ofStart = ratio(submitted, start)` where start is step-0 events. A resumed wizard sends no step 0 (useBriefWizard.ts, resume branch sets the mark to the restored step), yet its submit counts in `brief.submitted`. Resumed submissions therefore inflate the numerator against a denominator that excludes them, and the rate can exceed 100%. The column header says "Briefs" while the caption says steps are counted per visit.
**Fix:** exclude `resumed: true` from the submitted rate (or show resumed separately), and head the column "Visits".

### [NOTE] src/app/api/events/route.ts:36 - Rate limit placement

Invalid-name/invalid-payload requests (400) are not rate-limited. They are cheap (no DB), so acceptable; just record it.

### [NOTE] src/lib/brief/briefDrafts.ts:183 - Abandoned on Discard

`deleteRowWithImages` then `trackAbandoned`: two concurrent Discards of one row could both pass the find and emit twice. Rare; counts only.

### [NOTE] src/lib/analytics/rateLimit.ts:17 - Memory

Per-user arrays are capped at 60; the map is swept only above 1000 users (O(n) per call while above that). Bounded by active users in the window; fine. Excess is counted in AnalyticsDrop by the route, not stored.
