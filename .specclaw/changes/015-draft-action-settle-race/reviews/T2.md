## Findings

### [NOTE] page.tsx:128-135 — requested-number guard never retries

**Problem:** `requestedRevisionRef` is set before the fetch. `fetchRevisions` swallows errors, so a transient failure leaves the number permanently "requested" and the list stale until a manual refresh or `refreshAfterChange`.
**Fix:** Optional. Clear the ref in `fetchRevisions`' catch, or accept it, since the list is supplementary.

### [NOTE] RefinementPanel.tsx:170-176 — out-of-order poll response (named risk)

**Problem:** A poll GET sent before the POST and answered after the awaited refetch would overwrite the state with pre-202 data while `settleArmed` is true. It would need a poll in flight at send time, and polling only runs while `pendingAction` is non-null, which is rare given the input is disabled. The consequence would be a false "finished without producing a new revision".
**Fix:** None needed now. If it is ever seen, ignore draft responses older than the latest request.

### [NOTE] tests/e2e/settle-race.test.ts — race coverage is the applied path only

**Problem:** The forced race is covered for the applied outcome (refine) and the list (regenerate). Conflict, error and not-applied under the race rely on the unchanged logic plus the non-raced AC-04 suites.
**Fix:** Optional. Add one raced not-applied or error case.

## Test quality

The race is forced genuinely. The hold applies only to the first exact-path GET after the action POST, and `held()` is asserted. The mock finishes in-process well inside the 3 s hold, and the 15 s timeouts leave margin over it. The mutation runs show each case failing for its own cause when only its fix is reverted, so neither passes for the wrong reason. The flake risk is low.
