# T2 — Settle on state: RefinementPanel and the revision list

**Implemented by the orchestrator directly** (small, and the root cause and repro were already in hand).

## What was built

- **`src/components/drafts/RefinementPanel.tsx`:**
  - `onActionStarted` is typed `() => void | Promise<unknown>` and is now **awaited** after the 202.
  - A new `settleArmed` state is set once that refetch has landed.
  - The resolution effect now runs when a resolution is pending, `settleArmed` is true and `pendingAction === null`. The `prev === 'REFINE'` observed-edge requirement and `prevActionRef` are removed.
  - Resolving clears both the ref and `settleArmed`.
  - The outcome branches are untouched, in the same order: conflict → not-applied → error → applied (with `onRefined()`) → "finished without producing a new revision".
- **`src/app/(app)/drafts/[id]/page.tsx`:**
  - The edge-only "pendingAction non-null → null ⇒ refetch revisions" effect is replaced. The page now refetches the revision list whenever `draft.currentRevisionNumber` is non-null and missing from the loaded list.
  - **No-loop guard (FR-02):** `requestedRevisionRef` allows one request per missing number.
  - The now-unused `DraftAction` import is removed.
  - `fetchDraft`, which is async, was already passed as `onActionStarted`, so it is awaitable as it stands.
- **Why arming right after the await is safe:** `fetchDraft` never rejects. On a failed request it sets `error`, and the page swaps to its error view (`page.tsx:218`), which unmounts the panel. The spec's edge-case text is corrected to say this; the planned wording had assumed the next poll would resolve the row.
