## Spec compliance

## Focus 1: can anything still call `captionSpec('WHATSAPP')`?

I checked every caller of `captionSpec(` and every reader of caption rows.

- `extract.ts:107` and `:135`: the targets come from the request or from `GENERATION_TARGETS`, which are registry channels.
- `resolve.ts:58`: it runs after `isPublishableChannel`, and that set is now the registry set.
- `CaptionPanel.tsx:96`: the rows come from `loadDraftCaptions` (`store.ts:48`). That function orders through `CAPTION_CHANNELS.flatMap`, so a legacy row drops out. `GET /api/drafts/[id]`, regenerate-copy, MCP `captionList` and `CaptionPanels` all read the loader output.
- `regenerateStampTier` only looks up rows for the requested targets. A legacy row is never reached.
- `saveGenerationCaptions` and `captionRowsFromFields` iterate the registry.
- `claimCaptionAction` takes parsed targets, and the parser rejects WHATSAPP.
- The stale sweep, `settlePendingCaptions` (`store.ts:261-273`), selects every PENDING row, including a legacy one. It never calls `captionSpec`. `fieldFor` is `() => ({ok:false, reason})`. A legacy PENDING row therefore settles to FAILED and keeps its text. The spec accepts this (Edge Cases).

I found no path that throws.

## Focus 2: retry route and the generation catch path

The `updateMany` is scoped with `channel: { in: [INSTAGRAM, LINKEDIN] }`. A WhatsApp row is not matched, so it is untouched. `createMany` with `skipDuplicates` only adds registry rows.

**WARN-grade edge (not blocking).** The catch path in `src/lib/agent/generateDraft.ts:353-358` uses `updateMany where: { status: 'PENDING' }` with `data: { status: 'FAILED', text: '', failureReason: 'generation failed' }`. This path is untouched by T1.

- Take a legacy WHATSAPP row that is still PENDING (a generation interrupted before the deploy). Retry now leaves it PENDING. If that retry then fails, the catch path flips the hidden row to FAILED and blanks its text.
- That breaks FR-05 and AC-06 ("status, text and failure reason kept whether the retry succeeds or fails") and "not deleted or changed" in FR-04.
- The corner case is rare. A draft that was only swept or failed has no PENDING WhatsApp row, and the sweep would settle such a row first while keeping its text.
- A one-line scope fixes it: add `channel: { in: registry }` to that `where`. Alternatively, record it as a known limit in the T1 report.
- No test covers it.
