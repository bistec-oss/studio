The body `{ key, size }` is strict zod through `parseBody`. `planComposition({ imageStyle: key, aspectRatio: size, hasCompositeSource: true })`; a non-hero plan is 400. ## Judgement calls

1. **`planNext` is not reused for the probe; `planNextProbe` is new.** `planNext` hard-codes 2 attempts per slot and refuses a slot as `already-passed` after one accepted attempt, so a pass rule of "2 accepted of at most 3 attempts" cannot run through it. `planNextProbe` keeps the same reasons (`cap`, `max-attempts`, `already-passed`, `awaiting-verdict`) and adds `cannot-pass` (not enough attempts left to reach two accepts). It reuses `parseLedger`, `attemptsFor` and `checkBase`. `planNext` itself is unchanged.
2. **Ledger line `threshold` and `promptHash` are null when written.** They are known only from the response, and the line must be written before the request. The real values are recorded in `results.json` (`threshold`, `promptHash`) per attempt. The ledger line shape still carries both keys.
3. **The image is read back by fetching its public IMAGES URL** (the background step persists it and returns only that URL; the brief allows only an `onPrompt` change in `background.ts`). The object key is taken from the URL under the IMAGES bucket and deleted afterwards; a provider URL outside the bucket is not deleted.
4. **The route unit test fakes `generateBackgroundForBrief`** (and the kit, storage and prisma), so the mock seam inside the background step is not exercised by this test; it is the existing 009 seam.
5. The brand kit is the team default (`resolveBrandKit(teamId)`), since the probe takes no kit id.

## Follow-up fix before OP-025 (2026-10-25, orchestrator)

The probe route called `generateBackgroundForBrief` outside `withClaudeAuth`. In CLI mode (`DESIGN_PROVIDER=cli`, the OP-025 server) the Haiku decision call spawns `claude -p`, which hard-fails with no credential context; the unit test faked the step and the mock seam never spawns, so neither caught it. The route now wraps the step in `withClaudeAuth(user.userId, user.teamId, …)`, as every other model route does, and `lookProbe.test.ts` gains a case asserting the step runs inside that context for the acting user and team.
