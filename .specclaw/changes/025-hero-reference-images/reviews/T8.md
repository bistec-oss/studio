## Spec compliance

- Insertion and the render check use the detected or stamped rect. The prompt swaps the contract region for the detected rect (`withDetectedScreen`).
- `composites` is written only after a render that passed, and a fallback stamp has none.

- The in-page check uses `getBoundingClientRect` against the stamped rect plus `elementFromPoint` at the centre and four 10% inset points. The verdict comes from the existing `evaluateCompositeFacts`.

- `__MOCK_COMPOSITE_FAIL__` is gated on `MOCK_AI` in `shouldMockCompositeFail`, and `MOCK_PUPPETEER` alone does not enable it.
- Tenancy is enforced: `isTeamScreenshotKey` refuses a foreign team key and any `..`, `\` or `%`, and `compositeRenderForSource` checks it before reading.
- Every `renderHtmlToPng` and `evaluateInRenderedPage` caller passes the argument. Non-composite callers pass `null`, and the diff shows no behaviour change for them.
- No scheduler, MCP, ACP or `prisma/` files are touched, the four released looks are unaffected, and no test was deleted.
- The `compositeRenderFor(stamp, teamId, size)` signature change is reasonable and reported.

## Findings

### [WARN] src/lib/agent/designAgent.ts:~193-196 (final-text fallback) — Correctness / NFR-08

```
if (text && lastHtml === "") {
  lastHtml = restoreInlineAssets(text, inlineAssets)
  if (postProcess) lastHtml = postProcess(lastHtml)
}
```

**Problem:** when the API loop ends with prose and never calls `renderHtml`, the HTML is inserted but no render and no composite check ran. The result is `exportUrl: ""` (`lastExportUrl` was never set). `pathB` then stamps the provisional `composites[...]` for that draft. That is a stamp for a composite that was not checked in a render, which breaks the "no stamp lists an unchecked composite" rule. The path already existed for classic, but T8 is what makes it unsafe.
**Fix:** when `composites` is set and no render passed (`lastExportUrl === ""`), throw `new CompositeRenderError('composite-not-rendered', 'the design was never rendered')` at loop end, so the classic fallback runs. Add a unit test for it.

### [NOTE] src/lib/agent/designAgent.ts:~271-275 — orphaned exports

Only `lastExportUrl` is attached as `uploadedKey`. If the API loop rendered more than once before the failing render, the earlier passing exports are never deleted. This is the same leak as before, but the new fallback makes it reachable. Delete every key this run uploaded, or accept the leak and record it as a known limit.

### [NOTE] src/lib/composite/insert.ts `compositeHtmlProblems`

It counts `data-composite` anywhere in the text, including comments or CSS the model wrote. That fails closed and is acknowledged in the report, so it is fine. Be aware it can cause a spurious classic fallback if a model mentions the attribute in a comment.

### [NOTE] src/lib/agent/pathB.ts `observeKeptLayout`

The layout observation now renders with the composite element present, and T9 is meant to exclude `[data-composite]` from the measured boxes. Until then a spurious `layout-violation` observation is possible. It is observation-only, so it has no behavioural effect.

### [NOTE] tests/e2e/product-screenshots.test.ts

TC-SHOT-07 to 09 drive the API through `request`, not a page, so the `waitForResponse` ordering rule does not apply. They are written and not run, so the orchestrator must run them.
