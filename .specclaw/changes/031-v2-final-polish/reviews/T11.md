## Findings

- [NOTE] src/lib/campaign/briefingAssistant.ts:175 — Correctness. `postStyle: z.string().trim().max(40).optional()` is checked in the plan schema, so a proposed key longer than 40 chars (or a non-string) fails the whole `posts` array and the plan is dropped. The comment above it says "a bad key must be replaced, not drop the plan". Fix: drop `.max(40)` and use `z.unknown()` (or `z.coerce`/`catch`), then cap the length in `normalisePlan`.
- [NOTE] src/lib/campaign/briefingAssistant.ts:262 — Tenancy. `loadDefaultStyle` does `findUnique({ where: { id: campaignId } })` with no teamId. It is safe today: the chat route (`briefing/chat/route.ts`) loads the campaign and rejects `campaign.teamId !== user.teamId` with a 404 before calling `runBriefingChat`. It is only caller-trusting. Consider `findFirst({ where: { id, teamId } })`, since `runBriefingChat` already receives teamId.
- [NOTE] src/lib/testHooks.ts:205 — Declared deviation, accepted. The mock reply has 2 rows (`launch` and the bad `flash-sale`), not the 3 of design §7.1. It still covers an active key, a replaced key and the replaced line. The AC-29 matrix is covered by the unit tests, and the existing E2E row counts are preserved.
- [NOTE] tests/unit/schedulePlan.test.ts:24 — Test quality. `retired` is built and only `retired.status` is asserted, a tautology. The retired case really runs on `withoutTip` (an inactive key absent from the list). Fine for the behaviour, but a real retired entry passed through `activeStyles({...})` would be stronger.
- [NOTE] src/lib/campaign/briefingAssistant.ts:236 — A legacy goal that maps to nothing (e.g. "awareness") falls silently to the fallback with no `styleReplaced`. This matches the comment and FR-30, since only a proposed key is reported.
