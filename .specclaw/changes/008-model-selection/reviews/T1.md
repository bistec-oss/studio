## Findings

### [WARN] src/lib/models/resolve.ts:153-227 - Correctness / orchestrator ruling (focus 2)

**Problem:** `systemDefaultFor` returns a single value: `envDefault` when eligible, else the table default (`return env` at :164). If the env model is eligible but refused by the team's effective set, tier 4 refuses it and goes straight to the fallback (:227-230). So `envDefault: 'OPUS'` on a team without Opus gives Haiku (`set[0]`) on DESIGN_FREEFORM, not the table's Sonnet. The ruling is: record the substitution, then try `tableDefault(surface, designPath)`, and only then the fallback.
**Fix:** in tier 4, if the env model is applicable and not in `set`, call `refuse(env)`, then try `tableDefault(...)`; if that is in `set`, return it with `source: 'system'`; if not, `refuse(table)` and go to tier 5. `systemDefaultFor` can return `{ env, table }`, or the env branch can be inlined in `decideModel`. Any wave-2 picker that pre-selects through `systemDefaultFor` must use the same two-step logic.
**Tests do not cover it.** The `envDefault` cases (modelResolve.test.ts:181-197) never use an env model the team refuses. The AC-03 oracle (:344-349) encodes the current behaviour: `system = env ?? TABLE[...]`, then `skip(system)` and the fallback. It has to change with the fix, and the exhaustive test will go red until it does. Add an explicit case: `envDefault: 'OPUS'`, `allowed: ['HAIKU','SONNET']`, DESIGN_FREEFORM, expecting `SONNET`, source `system`, `substitutedFrom` `'OPUS'`. Add the gated variant too (`gateOn`, team credential, CLI).

### [NOTE] tests/unit/modelResolve.test.ts:307-350 - Test quality (focus 3)

**Problem:** AC-03 is exhaustive over its stated product (169,344 combinations plus a separate tier-1 loop). The oracle is built from hand-written tables for eligibility, defaults, stamp families and gating, not from catalogue helpers, so it is independent in its data. The tier sequence (stamp, team, system, fallback) does mirror the implementation's structure step for step. That is acceptable for a tier-order spec, and the falsifiability mutation in the report shows it bites. Its one blind spot is the env-refused case above, which it encodes as the current behaviour. The fix to the oracle belongs with the WARN.

### [NOTE] src/lib/models/resolve.ts, catalogue.ts - YAGNI (focus 5)

**Problem:** The trailing `catalogue` parameters (`decideModel`, `effectiveSet`, `internalModel`, `modelTier`, `entryForStamp`, `entryFor`, `defaultPolicy`, `validatePolicy`) are justified by the planted-catalogue tests (invariants, the $8/$40 tier case). Keep them. `modelTier` and `systemDefaultFor` have no non-test consumer in T1; both are spec'd for wave-2 pickers and the picker pre-selection. `DEFAULT_POLICY` and `defaultPolicy()` are two exports for one thing, and `DEFAULT_POLICY` is the likely T4 consumer. All of these are tolerable; confirm in T4 and T13 that each is consumed, or drop it.

### [NOTE] src/lib/models/resolve.ts:116 - Correctness (minor)

**Problem:** `entry.surfaces[surface]!.timeoutMs` relies on the callers' eligibility filtering. This holds today (`effectiveSet` and `internalModel` filter on `isEligible`) and `internalModel` throws first if nothing matches. No change needed; named only so a later edit to `effectiveSet` keeps it true.
