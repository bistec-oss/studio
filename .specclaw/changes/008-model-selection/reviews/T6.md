## Findings

### NOTE - `storedRequest` tier is sound; AC-03 extension checks "ok", not membership

`src/lib/models/resolve.ts` tier 1b: `const hit = inSet(input.storedRequest)` uses the same `effectiveSet` as the stamp and team tiers, so allow-list, gate, eligibility and credential are all enforced. A miss calls `refuse(...)` and falls through, and it only returns `ok:false` via the `NO_ALLOWED_MODEL` check that precedes it. A stored value cannot cause a 400/throw or bypass the allow-list. Precedence (after tier 1, before stamp) matches FR-10 ("as tier 1", but stored so it falls through). The values are Prisma enum columns, so no free string reaches argv.
The exhaustive test (`modelResolve.test.ts`: "every stored key ... never a refusal") asserts only `expect(r.ok).toBe(true)`. It does not assert the resolved key is in `effectiveSet`, which is the actual AC-03 guarantee. By construction it holds; suggestion: add `expect(allowed).toContain(r.resolved.key)` (one line). Behavioural cases elsewhere (disallowed OPUS falls to Sonnet with `substitutedFrom: 'OPUS'`, gated, template-ineligible) do cover it.

### NOTE - interim stale stamps until T7 (not a T6 defect, a wave-ordering risk)

`regenerate-copy/route.ts` destructures `{ fields }` and drops the stamp, so a regenerate that rewrites caption text leaves the row's old `model` in place; `commitDraftRevision`/`recordRejectedRender` write `designModel: null`; regenerate-design ignores the draft's stamp (team default instead of like-for-like). All are declared and T7-owned. Do not commit/ship T6 alone beyond the wave: T7 must land before any deploy or E2E on stamp accuracy.

### NOTE - failed-row stamp nulling is correct for generation/retry only

T7 must not reuse `captionRowsFromFields` for settle. Confirmed no conflict today.

### NOTE - API tool tail unbounded by `deadlineAt`, as design §5 assumes

`designAgent.ts`: `createMessage(..., { deadlineAt, label: "design" })` runs on every turn, and the loop-top check `Date.now() - startedAt > deadlineMs` remains. Tool execution after the last turn is not aborted; this is exactly the 210 s "API tool tail" in design §5, so consistent. `AgentTruncatedError(effectiveMaxTokens)` is correct.
