## Findings

### NOTE 1 - `src/lib/brief/modelPicks.ts:105-121` (`refusedModelField` is inferred, not carried)

Placement rests on route check order plus `message.includes(displayName)`. It works for the cases tested, but it is coupled to message wording and to the order in `src/app/api/briefs/route.ts` (lines 96-98 parse, 207 resolve). One misattribution is reachable: caption OPUS (allowed) plus design OPUS refused for template fill gives the same model name in "Opus 5.5 isn't available for template fill", and the function picks `captionModel`. The wizard's resets make this rare, but it needs no luck to fix.
**Suggestion:** have `modelError` (`src/lib/models/requests.ts:46`) take an optional field, return `{ error, code, field?: 'captionModel' | 'designModel' }` (extend `ModelErrorBody`), and pass the field at the briefs route's three refusal sites (`parseModelField` failures, `captionProviderNotClaudeError`, and the resolve failure at line 207; resolve failures know which surface they ran). `apiFetch` would carry `field` on `ApiError`, and `refusedModelField` would shrink to reading it. This is small, additive, and removes the string matching. Other routes can ignore it. Non-blocking; the current code falls back safely to the step error.
