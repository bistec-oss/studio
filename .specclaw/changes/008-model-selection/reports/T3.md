## How the hand-written SQL was checked against Prisma's

1. **`npx prisma migrate diff --from-empty --to-schema-datamodel prisma/schema.prisma --script`.** I compared its statements for the new objects one by one with the migration. The migration uses Prisma's exact forms: `CONSTRAINT "TeamModelPolicy_pkey" PRIMARY KEY ("teamId")`, `"TeamModelDefault_pkey" PRIMARY KEY ("teamId","surface")`, FKs `"TeamModelPolicy_teamId_fkey"` and `"TeamModelDefault_teamId_fkey"` with `ON DELETE CASCADE ON UPDATE CASCADE`, `"allowedModels" "ModelKey"[]`, and `"updatedAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP`.
2. **Authoritative check on a throwaway shadow DB** (this is neither the dev DB nor the test DB):
   1. `CREATE DATABASE bistec_studio_008shadow` in `designer-postgres-1`;
   2. `npx prisma migrate diff --from-migrations prisma/migrations --to-schema-datamodel prisma/schema.prisma --shadow-database-url <that DB> --script` → **`-- This is an empty migration.`**;
   3. `DROP DATABASE … WITH (FORCE)`.

   So every migration, including this one, produces exactly the schema.

3. **AC-23 dry run, on a throwaway scratch DB** (`bistec_studio_008scratch`, created empty and dropped afterwards). The check query counts the 10 added columns, the 2 tables, the 2 types and the migration row:
   1. `prisma migrate deploy` → `10|2|2|1`;
   2. the down script with `psql -v ON_ERROR_STOP=1` → `0|0|0|0`;
   3. `prisma migrate deploy` again → it re-applied `20261012120000_model_selection` by itself → `10|2|2|1`.

   T12 still runs the real AC-23 on a copy of the test DB.

## Departures

1. **`src/lib/agent/claudeCli.ts` (outside the file list, as allowed): a one-line interim edit at the only reader.** `env.CLAUDE_CLI_MODEL` is now a `ModelKey`, so `claudeModelArgs` reads `env.CLAUDE_CLI_MODEL?.toLowerCase() ?? ""`, which is the CLI family alias (`opus`), with a comment that T5/T10 delete the read.
   - **Why the alias and not `entryFor(key).cliArg`:** the alias keeps today's override exactly for alias values. `tests/unit/refineVerify.test.ts:289` ("the override IS live…") asserts `--model opus` and is outside T3's list; `cliArg` would make it `claude-opus-5-5` and fail that test.
   - **The one behaviour change, interim only:** a full-ID value (`claude-sonnet-5-5`) is now passed as its alias (`sonnet`) instead of verbatim. That is the same family. T10 replaces all of this with `--model <resolved.arg>`.
   - **Why not a separate raw string:** it would keep a second, unvalidated copy of the variable alive, which FR-04 removes.
2. **Two places where the SQL differs from design §4's text, so that it matches Prisma.** Both were proven by the empty shadow diff.
   - **`allowedModels` is `"ModelKey"[]` with no `NOT NULL`.** Prisma generates list columns as nullable (see `Brief.channels` / `ScheduledGeneration.channels`), and design §4's `NOT NULL` would leave a non-empty `migrate diff`. Prisma never writes NULL for a list field, and FR-05's validation rejects an empty list at save.
   - **PKs and FKs are named `CONSTRAINT`s, and the FKs are separate `ALTER TABLE … ADD CONSTRAINT` statements with `ON UPDATE CASCADE`.** Design §4 declared them inline. The names Postgres would have defaulted to are the same, but `ON UPDATE` would have differed.

   Every column, type and table is otherwise exactly design §4's list. The down script is design §4's statements, plus header and ordering comments.

3. **The schema comments are `//`, not `///`** (tasks.md says `///`). The orchestrator's brief asked for the file's existing style, and the file uses `//` throughout.
4. **`IS_BUILD_PHASE` moved** to the top of `env.ts`, unchanged (see above).
