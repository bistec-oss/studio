## Summary

- **`runBriefingModel(system | undefined, messages, teamId, model, opts?)`** (`campaign/briefingAssistant.ts`):
  - It takes a required `ResolvedModel`, plus `opts.maxTokens` (API only) and `opts.label` (default `'briefing'`).
  - **CLI:** `runClaudeCli(prompt, { label, model })`. The 120 s `CLI_TIMEOUT_MS` literal is deleted, so the bound is the entry's surface timeout (design §5: one value per assistant surface, 180/180/300 s). An undefined `system` is left out of the prompt instead of becoming a blank line.
  - **API:** `createMessage(client, { max_tokens, system?, messages }, model, { label })` + `textOf`. There is no `system` key when none is given. `modelFor` is no longer imported.
- **`resolveAssistantModel(surface, teamId, userId)` + `AssistantModelError`** are new, in the same module:
  - it calls `resolveModel(surface, { userId, teamId })` and returns the `ResolvedModel`;
  - an `ok: false` result throws `AssistantModelError(code, message)` before any call is made.
  - All six entry points use it.
- **The entry points resolve at their start and pass the model by value:**
  - `runBriefingChat`, `enhanceBriefing` and `enhancePostBrief` → `ASSISTANT_BRIEFING`;
  - `runBrandKitChat`, `generateTemplateFromImage` and `draftBrandVoice` → `ASSISTANT_BRANDKIT`.
  - Each gains `userId: string | null`. The chat passes the same model to whichever call it makes, vision or text.
- **`runVisionModel({ …, model })`** (`agent/vision.ts`):
  - `model` is required on `VisionRequest`.
  - **API:** `createMessage` + `textOf`.
  - **CLI:** `runClaudeCliStreamJson(content, { label, model })`; the 180 s literal is deleted.
- **`draftBrandVoice(teamId, userId, promptText, options)`** (D8, spec open question 2):
  - It goes through `runBriefingModel(undefined, [{ role: 'user', content: promptText }], teamId, model, { maxTokens: 1024, label: 'brand-voice' })`, so it gains a CLI path.
  - The `BRAND_VOICE_MODEL` literal and its direct SDK call are deleted.
- **The token ping** (`agent/userToken.ts`):
  - `validateClaudeToken` runs `internalModel('INTERNAL_TOKEN_PING', 'cli')` with its explicit `authToken`.
  - The `'haiku'` literal and the `60_000` timeout are deleted; the entry's own timeout is 60 s.
- **Every assistant MOCK_AI branch records** (FR-16, design §7) the model it resolved, before returning its mock:
  - chat, both Enhances, the brand-kit chat, image → template and the voice draft: `recordModelCall(modelCallFor(model, pipelineMode(), label))`;
  - the token-ping mock: mode `'cli'` (see Decisions).
- **Labels:** `briefing` (chat and both Enhances), `brandkit` (the brand-kit chat, including its text-only path, which was `briefing` before), `image-template` and `brand-voice`.

## Departures (edits outside T8's file list)

1. **Seven routes**, forced by the new required `userId` parameters (the brief: "with userId passed where the route has one"):
   - `campaigns/[id]/briefing/chat`, `campaigns/[id]/briefing/enhance`, `briefs/enhance`, `admin/brandkits/[id]/assistant/chat`: pass `user.userId`. **They also catch `AssistantModelError` and return 422 `{ code, message }`**, the shape refine and regenerate-design use. Before this, a resolution failure would have been the handler's generic 500 "Internal server error", and the reason would never have reached the user. Every other error is re-thrown unchanged, and the success shapes are unchanged.
   - `admin/brandkits/[id]/prompts/generate` and `…/improve`: pass `user.userId`, use the same 422 catch, and **now wrap the call in `withClaudeAuth(user.userId, user.teamId, …)`**. Without that, the voice draft's new CLI path would have no credential and would hard-fail, so it is required for D8 to work in CLI mode. In API mode it is a no-op. The prompt text and the mock drafts were moved into consts unchanged, so the routes' MOCK_AI responses are byte-identical.
   - `admin/brandkits/[id]/templates/from-image`: passes `userId: user.userId`. Its existing catch-all already returns 422 `{ code: 'AGENT_ERROR', message }`, so a resolution failure surfaces there with its message and needed no new handling.
2. **`tests/unit/claudeCliArgs.test.ts`** (forced: `runBriefingModel`'s signature):
   - the wrapper case passes `siteModel('ASSISTANT_BRIEFING')`, and `siteModel` widens to accept it;
   - the AC-13 option table's `briefing` and `token-validate` rows now copy the source: a `ResolvedModel` and no timeout literal.
   - The `VISION_MODEL` drift test (`modelFor('B', 'cli')`) is untouched; T10 re-pins it.

## Decisions

- **Resolution happens in the lib functions, before the MOCK branch** (design §3 table). For the brand-kit chat, that is after the grounding queries, so a team with no runnable model and no references gets the model error rather than the "add a reference" reply. That is acceptable, because no next step could run either.
- **422 `{ code, message }`, not 400, for a resolution failure.** Wave 1 has no explicit request, so the only reachable failure is `NO_ALLOWED_MODEL`, for example Opus-only plus the personal-token switch on a team-credential CLI run. T13's `modelError(result)` → 400 `MODEL_NOT_ALLOWED` is for explicit-request misses. It can branch on `AssistantModelError.code` when it adds `requested` to the two chats.
- **The token-ping mock records mode `'cli'`.** The ping is a CLI call by nature (API mode stores the token unvalidated and makes no call), and the model is resolved for `'cli'`, so the record names the call the seam stands in for. Under MOCK_AI the E2E runs API mode, so T12 should expect `mode: 'cli'` for this one surface.
- **`AssistantModelError` and `resolveAssistantModel` live in `briefingAssistant.ts`,** beside `runBriefingModel`, which the brand-kit modules already import. A new module would have been a file outside the list. `policy.ts` is T4's file.
- **`runBriefingModel` keeps `isCliMode()` for its branch** (the `ResolvedModel` has no mode). Both it and `resolveModel` read the same config, so the arg and the branch agree.
