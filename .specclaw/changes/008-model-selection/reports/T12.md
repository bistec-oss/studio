## AC-23: the TEMPLATE round trip (scripted step, server stopped)

Scripted in the session scratchpad (`ac23-roundtrip.sh`), run with the `:3001` server stopped. That is the only way `CREATE DATABASE … TEMPLATE` is accepted, because the source must have no other sessions. The script touches only two databases, `bistec_studio_test` (the template, read only) and `bistec_studio_008rt` (the scratch DB). It never touches the dev DB.

1. `CREATE DATABASE bistec_studio_008rt TEMPLATE bistec_studio_test`. The copy carries the real data the suites had written: 203 drafts, 197 with a design stamp, 396 stamped revisions and 576 stamped captions.
2. `psql -v ON_ERROR_STOP=1 -d bistec_studio_008rt < prisma/rollback/008-model-selection.down.sql` runs 4 × `ALTER TABLE`, 2 × `DROP TABLE`, 2 × `DROP TYPE` and `DELETE 1` (the migration row, L24). Every 008 object is gone, and all 203 drafts are kept.
3. `DATABASE_URL=…/bistec_studio_008rt npx prisma migrate deploy` reports "Applying migration `20261012120000_model_selection`", so it re-applied the migration by itself.
4. **The `information_schema` check.** The 10 added columns and both tables' columns, each with `data_type` / `udt_name` / `is_nullable`, plus the tables, the types and the migration row, are `diff`ed from the forward state against the state after the redeploy. The result is **IDENTICAL**.
5. `DROP DATABASE bistec_studio_008rt WITH (FORCE)`, then `0 databases named bistec_studio_008rt`.

## Departures

- **AC-23 is in the suite (TC-MODEL-12) on a migrate-built scratch DB, not a TEMPLATE copy.** `CREATE DATABASE … TEMPLATE` is refused while any session is connected to the source. The running test server always holds connections to `bistec_studio_test`, so a TEMPLATE inside the suite is impossible. The fix is §W's TC-CAP-13 precedent: build from empty with the same `prisma migrate deploy`, and assert that its shape equals the test DB's (`expect(forward).toEqual(await shapeOf(prisma))`). The spec's literal TEMPLATE copy was run as well, with the server stopped (above). Both ran on throwaway databases whose names end in `_008_rollback` / `_008rt`, and `testDbUrl()` refuses any URL whose DB name doesn't end in `_test`.
- **`MANIFEST_VERSION` stays 2.** 012 bumped it because a pre-012 importer would have dropped every caption. A pre-008 importer would drop only the stamps: they would read as null ("unknown", the 004 rule), and no content is lost. Bumping would make every new bundle unreadable on a machine that hasn't pulled 008, for provenance alone. The new importer reads a missing stamp key as null, which was proven with a stripped bundle.
- **No unit test for the scripts.** They have none (012 T15 made the same call). The `--dry-run` prints the same `data` objects the real path writes, and it was run on three bundles (see Verification).
- **`a11y.test.ts`'s axe rule list is copied into §Y, not imported** (§W's precedent: importing a spec file registers its tests twice). The shared-helper follow-up from 012 now covers three copies.

## Decisions

- **The stamps are asserted as literal apiIds** (`claude-haiku-4-5`, etc.) in the test. The mock E2E is API mode, where the stamp is the `apiId` (FR-08), and the AC text states them literally. The literal guard (FR-15) scans `src/` only. If T2 moves a `cliArg` to an alias, that changes only CLI-mode stamps, which this suite never sees.
- **The AC-20 scheduler case runs in API mode,** so `credential` is `'n/a'` and Opus is not gated. The gated branch (a CLI team default of Opus substituted for `userId: null`) is unit-tested in `modelPolicy.test.ts` (T4) and can't run under `MOCK_AI`.
- **AC-21 asserts exactly one record per entry point,** not "at least one". A second record would mean a hidden extra model call (for example, a vision call plus a text call), and AC-21's cost reasoning depends on that not happening.
- **The token ping (`INTERNAL_TOKEN_PING`, mode `cli` per T8) is not in §Y.** AC-21 lists seven entry points and the ping is not one of them. Its record is unit-tested in `userToken.test.ts` (T8).
- **The suite's policy reset is a DB delete, not a PUT.** It needs `dbAvailable`, so every §Y case skips without the test DB. That is the same condition as §W's DB-seeded cases.
- **Test-DB data touched by the script verification:** one brief's `captionModel` / `designModel` was set to `SONNET` / `HAIKU` to show the brief keys travel, and then set back to NULL. Nothing was imported for real. The import dry runs write nothing, and a real import is blocked anyway by the known L22 `teamId` gap, which was not fixed here and not made worse.
