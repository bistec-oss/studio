## Overview

Nothing stops a post from inventing a fact unless someone wrote a rule for it by hand. The IRP campaign needed a hand-written "FACTS — DO NOT INVENT" block in its briefing (2026-07-28) before its posts stopped making up intake dates and deadlines. Every other campaign and every ad-hoc brief has no such rule. On a scheduled entry set to auto-publish, an invented price or salary reaches LinkedIn or Instagram with nobody looking, and the only fix is deleting it by hand on each platform.

Goal and Tone are also two loose words. The wizard offers Goal and Tone on its Content step (`src/components/brief/constants.ts:24-37`), and each reaches the caption, Path B design and background prompts as one line (`Goal: ${goal}`, `Tone: ${tone}`: `src/lib/agent/prompts/caption.ts:68-69`, `pathB.ts:123-124`, `background.ts:103-104`). Path A's two prompt builders take neither (`PathAPromptOptions` and `PathAUserMessageOptions`, `src/lib/agent/prompts/pathA.ts:11-22` and `:40-51`, have no goal or tone field).

This change (phase a of two; phase b is a separate proposal) makes two things:

1. **A post style**: a code-owned purpose preset (eight to start). Each carries its goal, a default tone, a default image style (only looks that exist today) and a **checklist** of measurable content rules. One pure resolver is the only place the mapping lives. The wizard, the briefs route, the queue runner, MCP and ACP all call it.
2. **A facts check**: after the captions are written, code (no model) pulls currency amounts, percentages, dates, times, phone numbers and bare numbers from the captions and the on-image headline, and compares them with the brief, the campaign briefing, the brand-kit voice text and the campaign documents. A value found in none of them is flagged. An interactive draft shows a notice. A scheduled entry set to auto-publish is **held** instead of published, with a named reason.

The prompt checklist asks the model to behave. The facts check proves it did. The second is the safety net; the first is the cheap part that makes the net rarely needed.

**What this does not need to prove.** The panel (party-ba) said the "Goal and Tone mean almost nothing" claim has no observed failure behind it. This spec does not rest on it. The problem it fixes is the missing default facts guard. Goal replacement is the vehicle for the checklist, and the checklist and facts check stand on their own. The acceptance bar below is therefore about the facts check (a seeded, mock-only set) and about whether the styles get chosen (the insights page). Whether the checklist lowers real-model invention is an optional operator step (OP-1), the user's call.

**The cost of doing nothing** (party-po): one invented value on one auto-published post is public and cannot be undone from this app. Interactive drafts already get human review, so their cost is lower, and the notice is cheap. The auto-publish path is where the value is, and it is the reason the facts check and the HOLD downgrade are in this phase and not later.

## Approach

**One dataset, one resolver, one check.**

- `src/lib/postStyles/` is a new pure, client-safe module (no `@prisma/client` value import, no prisma, no env, no fs). It holds the dataset, the resolver, the stamp schema and the prompt text. It imports `src/lib/designData` for image-style keys (one direction only; `designData` never imports it).
- `src/lib/factsCheck/` is a second pure module: the extractor, the normaliser, the comparison and the result type. A thin loader (`sources.ts`) and a writer (`refresh.ts`) are the only files in it that touch prisma.
- Every reader calls the resolver. A guard test fails if any file outside `src/lib/postStyles/` maps a style key to a tone, a goal, an image style or a rule (NFR-02).

**Why a new module and not `src/lib/designData/`.** `designData` is the layout contract (pixels, regions, archetype versions); 007 extends it with a separate authoring part, and `designDataBoundary.test.ts` keeps generation-side files from importing that part. Post styles are not layout: the caption prompt, the queue runner and MCP read them, and none should import a layout module for a checklist. A sibling module keeps both boundaries clean. It mirrors the 009 dataset pattern (deep-frozen data, immutable versions, a content-hash guard test, a stamp validated in code) and adds one dependency edge, `postStyles → designData`, tested in one direction.

**Facts are code-checked, not model-checked.** The checker is regular expressions and a number normaliser over text already in hand. It adds no model call, no image call and no second pass. A false positive costs a notice (interactive) or a HOLD (scheduled): the safe direction.

**The key is a long-lived contract** (party-visionary BLOCK). Keys such as `hiring` are written into five places (three columns, the MCP/ACP input, the 006 event history). They are permanent and never reused or renamed. A retired style stays resolvable. A future team-owned style gets its own id column, never a bare string in these columns. The dataset's header says so, and a unit test enforces the parts a test can (FR-02).

File map. Details are in [design.md](design.md).

## Requirements

### Functional Requirements

- **FR-01 — The columns, the migration and the down script.**
  - **Schema.** `prisma/schema.prisma` gets seven nullable columns, no defaults:

    ```
    model Brief               { … postStyle        String?  }   // 027: the style key; null = before 027 (the user's own goal and tone stand)
    model ScheduledGeneration { … postStyle        String?
                                  heldReason       String?  }   // 027: why a post action was not run (the facts check), null otherwise
    model Campaign            { … defaultPostStyle String?  }   // 027: pre-fills the wizard, the queue and (as the default) MCP/ACP
    model Draft               { … postStyle        Json?    // 027: the stamp { key, version, revision } of the last generation or regeneration; null = before 027
                                  factsCheck       Json?  }  // 027: the facts-check result (FR-10, FR-11); null = never checked
    model DraftRevision       { … postStyle        Json?  }  // 027: the stamp at that revision's render
    ```

    The key columns are `TEXT`, validated in code, so a retired key needs no migration (the 009 `Brief.imageStyle` precedent). Comments say so.

  - **Migration** `20261025120000_post_styles`. It sorts after the current head `20261024120000_analytics_events`. It is `ALTER TABLE … ADD COLUMN …` seven times (`TEXT` or `JSONB`), nothing else, so Postgres rewrites no table. Its header says, as 019, 023, 009 and 024 did, that it is additive only: the previous image keeps working against the migrated schema (it never reads or writes the columns, and its `brief.create` and `scheduledGeneration.create` omit them), and it names the down script. No backfill: every existing row stays null.
  - **Down script** `prisma/rollback/027-post-styles.down.sql`, in the 019/023/024 shape: a manual header (outside `prisma/migrations/` on purpose), `ALTER TABLE … DROP COLUMN IF EXISTS` for the seven columns, and the `DELETE FROM "_prisma_migrations"` for `20261025120000_post_styles`, so a later redeploy re-applies it. The header says it discards every stored style key, stamp and facts-check result.
  - **Rollback statement** (party-security NOTE): reverting the deploy restores the old prompts and the old Goal picker; rows already written with a style are ignored by the old code, not broken by it; the down script is needed only to remove the columns.

- **FR-02 — The post-style dataset** (`src/lib/postStyles/types.ts`, `styles.ts`).
  - **Types.**

    ```
    type PostStyleKey = 'general' | 'launch' | 'promotion' | 'event' | 'hiring' | 'announcement' | 'tip' | 'milestone'
    type RuleScope    = 'caption' | 'image'
    interface Rule    { id: string; scope: RuleScope; text: string; check?: 'facts-check' }
    interface StyleVersion { goal: string; defaultTone: ToneKey; defaultImageStyle: 'classic' | ArchetypeKey; checklist: readonly Rule[] }
    interface PostStyle    { key: PostStyleKey; label: string; summary: string; status: 'active' | 'retired'; current: number; versions: Readonly<Record<number, StyleVersion>> }
    ```

    `ToneKey` is the wizard's tone values (`professional`, `casual`, `bold`, `empathetic`); the tone list moves from `components/brief/constants.ts` into `postStyles/types.ts` and the wizard re-exports it. `check: 'facts-check'` marks a rule the facts check enforces in code (party-visionary NOTE). Nothing else reads `check` in this phase; the stored shape is what the panel asked for.

  - **Immutable and guarded.** The dataset is deep-frozen at module load, like `archetypes`. A version, once released, is never edited: a change adds `versions[n+1]` and moves `current`. A unit test pins a SHA-256 of each `(key, version)` content in a table committed in the test file, so editing a released version in place fails it, and a new version needs its hash added in the same commit (the `designData.test.ts` pattern).
  - **The key rule, written in the file header and enforced where a test can:** keys are permanent; a key is never reused for a different meaning and never renamed; a retired style (`status: 'retired'`) stays resolvable and is hidden from pickers; a future team-owned style gets its own id column and never a bare string in `Brief.postStyle`, `ScheduledGeneration.postStyle` or `Campaign.defaultPostStyle`. The test asserts: every key matches `^[a-z]+(-[a-z]+)*$`; the committed list of keys is a subset of the dataset's keys (so a deletion fails); no key repeats.
  - **Every default image style names a real key** (party-architect NOTE): a unit test asserts `defaultImageStyle` is `classic` or an `active` key in `designData` `archetypes`. Where the dataset checks this is that test, plus a module-load assertion in `styles.ts` that throws in non-production if it fails.
  - **`POST_STYLES_REVISION`** = the sum of `current` over all styles, exported. It strictly increases whenever any version or any style is added, so it cannot stay the same across a checklist edit (FR-05).
  - **Pickers.** `activeStyles()` returns the `active` styles in table order (the wizard, the queue modal, the campaign form). `getStyle(key)` returns an `active` or `retired` style, else `undefined`. `isStyleKey(raw)` is true for any key in the dataset, retired included.

- **FR-04 — The resolver** (`src/lib/postStyles/resolve.ts`; pure). The only place the style → goal, tone, image style and checklist mapping lives.

  ```
  type Surface = 'wizard' | 'briefs-api' | 'queue' | 'mcp' | 'acp' | 'regenerate'
  interface ResolveInput {
    style: string | null | undefined                          // an explicit key, or absent
    legacyGoal?: string | null                                // a pre-027 client's goal; picks a style only when `style` is absent
    campaign?: { defaultPostStyle?: string | null; defaultTone?: string | null } | null
    explicit?: { tone?: string | null; imageStyle?: string | null }
    path: 'A' | 'B'                                           // 'A' for designMode TEMPLATE
    aspectRatio: AspectRatio
    surface: Surface
    version?: number                                          // a pinned version; default = current
  }
  type ResolveResult =
    | { ok: true; key: PostStyleKey; goal: string; tone: string; imageStyle: string;
        checklist: readonly Rule[]; stamp: PostStyleStamp; notes: readonly ResolveNote[] }
    | { ok: false; code: 'UNKNOWN_POST_STYLE'; message: string }
  ```

  - **Style key.** `style` (when given) → the `legacyGoal` mapping (`hiring` → `hiring`, `announcement` → `announcement`; any other goal maps to nothing) → `campaign.defaultPostStyle` → `general`. A given key that is not in the dataset (`isStyleKey` false) is `{ ok: false, code: 'UNKNOWN_POST_STYLE' }`. A stored `campaign.defaultPostStyle` that does not resolve is also `UNKNOWN_POST_STYLE`; it is never replaced by `general`. A retired key resolves.
  - **Goal.** Always the resolved version's goal. `ResolveInput` has an optional `legacyGoal` (a string from a pre-027 client: briefs API, queue, MCP, ACP). It is read **only** to choose the style key when no explicit style is given, in this order: explicit `style` -> `legacyGoal` mapping -> `campaign.defaultPostStyle` -> `general`. The mapping is one table in the resolver: `hiring` -> `hiring`, `announcement` -> `announcement`; any other value (awareness, engagement, conversion, free text) maps to nothing, so resolution continues to the campaign default, then `general`. The mapping is case-insensitive and trims whitespace. An explicit style makes the goal input ignored (decided 2026-10-24, A7).
  - **Tone.** `explicit.tone` (trimmed, non-empty) → the campaign's tone → the style's `defaultTone`. The campaign's tone is `Campaign.defaultTone`, free text; it applies only if it matches a tone option by the wizard's current rule (the first option whose value is a substring of the lowercased text, `useBriefWizard.ts:446-449`, moved here as `matchToneOption`). Free text with no match is ignored. An explicit tone is any string up to 100 characters (MCP and ACP callers send free words today).
  - **Image style.** `explicit.imageStyle` → the style's `defaultImageStyle` → `classic`. The result is `classic` (and a note says why) when: the path is `A`; the aspect ratio is `STORY` (no current look supports it; the check is `imageStyleOptions(aspectRatio)` from `designData`); the surface is unattended (`queue`, `mcp`, `acp`: classic in this phase, as 009 set it); or the key is not an active look. An explicit `imageStyle` on an unattended surface is ignored with the note `unattended-classic`. An explicit key the API validator refuses stays a 400 at the route (`validateImageStyle`, `src/lib/brief/imageStyle.ts:19`); the resolver itself never throws.
  - **Notes** (`ResolveNote`: `'default-unavailable' | 'unattended-classic' | 'path-a-classic' | 'size-classic' | 'campaign-tone-ignored'`) are for the wizard's Review line and tests. They are not stored.
  - **Checklist.** The resolved version's rules, in dataset order, both scopes. Callers filter by scope.
  - **Per-surface rules, in one place.** `wizard` and `briefs-api` allow image styles on Path B at supported sizes. `queue`, `mcp` and `acp` are classic. `regenerate` reads the brief's stored key and uses the current version (FR-09).
  - **Stamp.** `{ key, version, revision }` (FR-05).

- **FR-05 — The stamp and the derived prompt versions** (`src/lib/postStyles/stamp.ts`).
  - **Shape.** `postStyleStampSchema = z.object({ key: string, version: int > 0, revision: int > 0 })`, validated in code at every write and tolerant at read (`parsePostStyleStamp` returns null on anything unreadable, like `parseCompositionStamp`, `src/lib/designData/stamp.ts:56`). `revision` is `POST_STYLES_REVISION` at the time of the run. A queue entry takes the latest version at run time (assumption A5), and the stamp records which version ran.
  - **Where it is written.** `RenderStamp` (`src/lib/drafts/revisions.ts:51`) gains `postStyle: PostStyleStamp | null`, with no default, so a writer that forgets it is a type error (the 009 composition precedent). `revisionStampFields` and `draftStampFields` write it to `DraftRevision.postStyle` and `Draft.postStyle`. The writers: first generation (both lifecycles), regenerate design, and every writer that carries a render forward (refine, inline edit, override, adopt, restore) carries the draft's current stamp. Regenerate copy writes `Draft.postStyle` in its settle (the copy ran under the current version). So `Draft.postStyle` is the stamp of the last generation or regeneration that applied the rules; a draft whose copy and design ran under different versions shows the later one (a stated limit, L3).
  - **Prompt versions derive from the dataset.** `PROMPT_VERSION` (`src/lib/agent/prompts/shared.ts:20`) and `CAPTION_PROMPT_VERSION` (`caption.ts:18`) become `` `<date>.<n>+ps${POST_STYLES_REVISION}` ``, so a checklist edit (which adds a version and raises the revision) changes both strings with no manual bump (party-visionary WARN). A unit test fails if either string lacks the suffix.

- **FR-06 — Inputs on every surface.** One rule on all of them: the server is the only writer of `goal`, and an unknown key is never degraded.
  - **`POST /api/briefs`** (`src/app/api/briefs/route.ts:34-48`). New optional `postStyle`. `goal` and `tone` are no longer required. A body `goal` is passed to the resolver as `legacyGoal` (it picks a style only when no `postStyle` is sent, FR-04) and is otherwise ignored. `tone` is optional (explicit). The route calls `resolvePostStyle` with surface `briefs-api` and the campaign's `defaultPostStyle` and `defaultTone` (read from the `campaign` row it already loads), and writes `Brief.postStyle`, `Brief.goal` (the style's goal), `Brief.tone` (the resolved tone), `Brief.imageStyle`. An unknown `postStyle` is `400 { error, code: 'UNKNOWN_POST_STYLE' }`. A request with no `postStyle` resolves through the legacy-goal mapping, then the campaign default, then `general` (decision 3: every new brief has a style).
  - **Queue entries** (`queueEntrySchema`, `src/lib/campaign/queue.ts:15-55`, used by `POST/PATCH /api/campaigns/[id]/queue` and `…/queue/batch`). New optional `postStyle`; `goal` becomes optional and is passed as `legacyGoal` (FR-04); `tone` becomes optional. `toEntryCreateData` writes `ScheduledGeneration.postStyle`, `goal` (the resolved snapshot, for display) and `tone` (the resolved snapshot). Unknown key: 400, with the batch route naming the entry index. Existing entries are untouched.
  - **MCP `generate_post`** (`src/mcp/server.ts:78-94`, `src/mcp/tools/generate.ts:11-20`) and **ACP `generate_post`** (`src/acp/agent.ts:19-35`, `src/app/api/acp/run/route.ts:65`). New optional `postStyle`. `goal` and `tone` are no longer in `required`; `goal` is accepted and passed as `legacyGoal`: it picks a style only when no `postStyle` is given (`hiring` and `announcement` map to their styles, anything else to `general`) and is ignored when one is (existing clients keep working; the manifest and the tool descriptions say exactly this); `tone` is accepted as an explicit tone. `generatePost` resolves with surface `mcp` or `acp` and the campaign defaults, writes the `Brief` row's `postStyle`, `goal`, `tone`, and returns the resolved `postStyle` key in its result. An unknown key throws a named error ("Unknown post style 'x'"), which the MCP and ACP layers already map to an error reply. The ACP manifest version goes `1.1.0` → `1.2.0` (additive: `postStyle` in, `postStyle` and `factsCheck` out, FR-13).

- **FR-10 — The facts check** (`src/lib/factsCheck/{extract,normalize,compare,types}.ts`; pure; never throws).
  - **Input.** `{ texts: Array<{ where: 'headline' | CaptionChannel; text: string }>, sources: string[] }`. `texts` are the headline and the registry captions (`CAPTION_CHANNELS`, `src/lib/channels.ts`; hidden legacy WhatsApp rows are not read). `sources` are the strings of FR-11.
  - **Pre-processing of a checked text** (sources are not stripped): remove URLs, email addresses, `@handles` and `#hashtags` (a number inside a hashtag or a word such as `Q3` is not extracted, limit L1); remove the exempt tokens below; normalise digits (below).
  - **Digit normalisation.** ASCII digits, Arabic-Indic (U+0660–0669, U+06F0–06F9), Devanagari (U+0966–096F), Sinhala Lith (U+0DE6–0DEF), Tamil (U+0BE6–0BEF) and fullwidth (U+FF10–FF19) map to ASCII. Other digit sets are left as they are (limit L2). Thousands commas are removed; `.` is the decimal point; `k`, `m`, `bn`, `thousand`, `million`, `billion` after a number multiply it.
  - **What is extracted** (in this order, each match consumed so a later pattern cannot re-match it). Every value has a `kind` and a normalised `key`:
    1. `tel` — a run of 7 or more digits with optional `+`, spaces, `-`, `.`, `(`, `)`. Key `tel:<digits only>`.
    2. `date` — day and month name (`15 March`, `15th of March 2027`, `March 15`, `Mar 15, 2027`), or a numeric date (`15/03/2027`, `15.3.27`, `2027-03-15`). Month names are English, full or three-letter, plus `Sept`. Key `date:<month>-<day>[-<year>]`. A numeric date is not reinterpreted between day-first and month-first: it keys on its digits as written, so a source written the other way flags (a safe false positive).
    3. `time` — `10:30`, `10:30am`, `5 pm`, `17:00`. Key `time:<minutes since midnight>`.
    4. `currency` — a symbol or code before or after a number (`$50`, `Rs. 5,000`, `LKR 2,500`, `50 USD`, `50 dollars`; symbols `$ € £ ¥ ₹`; codes `USD EUR GBP LKR INR AUD CAD SGD Rs`; words `dollar euro pound rupee`, singular or plural). Key `cur:<value>` (the currency symbol is not part of the key: `$50` and `USD 50` are the same value).
    5. `pct` — a number followed by `%`, `percent` or `per cent`. Key `pct:<value>`.
    6. `num` — any other number. Key `num:<value>`.
  - **Exemptions** (not extracted from a checked text):
    - integers 0 to 10 as bare numbers (`3 tips`, `2 minutes`). A currency, percent, date or time of any size is never exempt (limit L4: `9 years of experience` is not caught);
    - `24/7`, `24x7`, `24/365`;
    - the aspect-ratio tokens `1:1`, `4:5`, `3:4`, `9:16`, `16:9` and size tokens `<n>x<n>` and `<n>×<n>`;
    - a list marker at the start of a line (`1.`, `2)`, `(3)`) and the number in `Step <n>`, `Tip <n>` and `Part <n>`;
    - a year in a copyright line (`©`, `(c)` or `copyright`, then a four-digit year);
    - a number attached to letters (`Q3`, `COVID19`), because the boundary requires a non-letter, non-digit on both sides.
  - **Support rule.** The extractor also runs over every source string (no stripping, no exemptions) to build the source set of keys. A checked value is **supported** when its key is in the source set, with one widening: a `num:` value is also supported by a `cur:`, `pct:` or `num:` source key of the same numeric value. `tel`, `date`, `time`, `cur` and `pct` are kind-strict. A `date` with a year also needs the source's year to match when the source carries one.
  - **Result** (`FactsCheck`, schema-validated):

    ```
    { v: 1, status: 'clear' | 'flagged' | 'error', checkedAt: ISO string,
      flagged: Array<{ kind: 'tel'|'date'|'time'|'cur'|'pct'|'num', value: string /* as written, ≤ 40 chars */, where: 'headline' | 'INSTAGRAM' | 'LINKEDIN' }>,
      reason?: string /* ≤ 120 chars, only when status is 'error' */ }
    ```

    At most 20 flags (the first by `where` then position), de-duplicated on `(where, key)`. `status` is `flagged` when `flagged` is non-empty, `clear` when it is empty, `error` when the check could not run (sources could not load, or the extractor threw). The result holds no caption text and no brief text: only the matched numbers, dates and times and where they were found (NFR-05).

  - **Size.** Sources are cut at 200 000 characters in total; a text at 20 000. The check on a worst-case input finishes inside 50 ms in the unit test (NFR-06).

- **FR-11 — Sources, write points and storage.**
  - **Sources** (`src/lib/factsCheck/sources.ts`, the only prisma-touching part of the loader): the brief's `topic` and `description`; the campaign's active briefing (`getActiveCampaignBriefing`, `src/lib/campaign/briefing.ts:11`); the resolved brand kit's voice prompt (`resolveBrandKit(...).voicePrompt`, as `buildBriefInput` reads it); and the parsed text of the brief's campaign documents (`CampaignDocument.parsedText`, `prisma/schema.prisma:390`, read as `src/lib/campaign/documents.ts:112` does). Campaign documents never enter generation prompts (a standing rule) but they are the user's own words, and the IRP contact details came from a reference document; including them as sources is assumption A3. Brand-kit documents and artifacts are not sources.
  - **Where the result is written.**
    - A **synchronous** generation (scheduler, MCP, ACP: `generateDraftForBriefInner`, `generateDraft.ts:306`): computed from the `fields` and the headline in hand and written in the same `tx.draft.create` as the draft (`generateDraft.ts:332-348`).     - An **interactive** generation (`saveGenerationCaptions`, `src/lib/captions/store.ts:195-216`), a **regenerate copy** settle (`settleCaptionAction`, `store.ts:289-323`), and a manual **caption or headline edit** (`saveCaptionEdit`, `saveHeadlineEdit`, `store.ts:337-370`): after the write, `refreshFactsCheck(draftId)` re-reads the draft's READY captions and headline and the sources, computes, and writes `Draft.factsCheck` with a guarded `updateMany`. ## Edge Cases

- **A caption that quotes a stated value in different words** (the brief says "fifty percent"): spelled-out numbers are not extracted from the output or the sources (limit L6), so the written form `50%` in the caption is flagged when the brief only says "fifty percent". A safe false positive.
- **A numeric date written the other way round** in the brief and the caption is flagged (FR-10).
- **A stated value reformatted** (`5,000` and `5000`, `$50` and `USD 50`): the same key, supported.
- **A caption with no numbers**: `clear`; `flagged` is empty.
- **A headline only** (the caption call failed): checked alone. A `FAILED` caption row is skipped.
- **A draft with no READY captions**: `clear`, with an empty list (nothing to check).
- **A campaign document that is large**: its parsed text is already capped at upload; the 200 000 total cap cuts the tail.
- **A team with no brand kit** (Path A with a template and no kit): kit voice text is absent, the other sources still apply.
- **A retired style on a stored brief or entry**: resolves; its checklist applies; a picker no longer offers it.
- **Two queue entries from the same batch**: each resolves on its own at run time; there is no shared state.
- **The retention loop and the heartbeat** are untouched.
- **A flagged draft later edited by hand** so the value is stated or removed: the edit recomputes and the notice clears.
- **A held entry's draft is published by hand** from the library: allowed; the notice was the warning.

The user can change any of these at approval. The first group answers the proposal's open questions.

- **A1 (open question 1, the style table):** the eight styles, their goals, default tones and the rule text of FR-03 are the user's table of 2026-10-24 made concrete. They are a hypothesis: the 006 page shows which styles are chosen, and a style nobody chooses is retired, never deleted. The user approved the rule text and defaults on 2026-10-24.
- **A2 (open question 1, rule wording) - approved by the user, 2026-10-24 (the FR-03 rule text and defaults stand as written):** every value rule is "only if the brief states it"; no rule uses an adjective. "The brief" means topic, description, campaign briefing and brand voice text.
- **A3 (open question 2, sources; approved by the user, 2026-10-24):** the sources are the brief topic and description, the active campaign briefing, the brand-kit voice prompt, and the **parsed text of the campaign's documents**. Campaign documents are included because a stated fact can live only there (the IRP contact details). Brand-kit documents and artifacts are excluded.
- **A4 (open question 3, number noise; approved by the user, 2026-10-24):** the exemptions are the list in FR-10. Integers 0 to 10 are exempt as bare numbers; a year is **not** exempt (except in a copyright line), so "Join us in 2027" with no 2027 in the sources is flagged; phone numbers are checked and supported when present in a source.
- **A5 (versions):** a queue entry, a regenerate copy and a regenerate design use the current dataset version at run time; the stamp records which ran. Refine uses the stamped version. No entry pins a version.
- **A6 (wizard order) - decided by the user, 2026-10-24:** the Post style picker sits on step 1 (Size & Design), before the size and design choices, so the image-style picker on that step is pre-filled from the style. The Goal picker is removed from the Content step. The step order is unchanged.

When no style is given on briefs-api, the queue, MCP or ACP, a recognised legacy `goal` maps to a style in the resolver (`hiring` -> `hiring`, `announcement` -> `announcement`; anything else, including awareness, engagement, conversion and free text, -> `general`). - **A8 (the assistant):** the briefing assistant's `schedule` block is not changed to emit a style.
- **A9 (labels):** the `product-showcase` relabel to "Showcase" is a phase b change.

- **A11 (what is held):** only an unattended post action (`SCHEDULE_PUBLISH`, `PUBLISH_NOW`) is held. MCP/ACP `publish_post` and the web Publish are not blocked.

## Known limits

- **L1:** a number inside a hashtag or attached to letters (`#Top10`, `Q3`) is not checked.
- **L2:** digit sets other than the six listed are not normalised.
- **L3:** `Draft.postStyle` is the stamp of the last generation or regeneration; a draft whose copy and design ran under different versions shows the later.
- **L4:** small integers (0 to 10) and spelled-out numbers are not checked, so `9 years of experience` and `nine out of ten` pass.
- **L5:** the check reads the captions and the stored headline, not the HTML; a refine that prints a new number on the image is not checked.
- **L6:** the comparison is textual. A caption that invents a claim without a number ("the best in the country") is not caught. The prompt rules address it; the check does not.
- **L7:** a held entry's draft is a normal draft. Nothing stops a person publishing it by hand.
