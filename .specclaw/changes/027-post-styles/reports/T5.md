## Ambiguities and choices

- **Stored explicit image style on the briefs route.** The design says the create data takes the resolver's values. The 009 suite (TC-HERO-12) requires that an explicitly sent style on 9:16 is stored as given, so an explicit `imageStyle` is stored as sent and the resolver's value is used only when none was sent. `hero-image` (16) passes.
- **What a queue entry stores.** The resolved key (never null for a new or edited entry, so the campaign default is a snapshot at create time) and the resolved goal and tone. Only a pre-027 entry has a null key. The run-time resolve uses the stored key, so a later change to the campaign default does not move an existing entry.
- **`ensureBrief` and the campaign.** A stored key needs no campaign; the campaign's tone default is read (one query) only when the entry stored no tone. The design text said the campaign is read "only when `entry.postStyle` is null", which contradicts FR-16 and AC-12 (a null key gets no style), so I followed the spec.
- **A re-run cannot clear a COMPLETED held entry**, because the route accepts only FAILED or CANCELLED (unchanged; a COMPLETED re-run would make a second draft). TC-PS-21 ages an entry to FAILED with a stale `heldReason` through the database and checks that the re-run clears it.
- **Unknown stored key:** the entry takes the existing retry path (`PENDING`, `retryCount` 1, `errorReason` `Post style "ghost" is not available`, no brief, no draft, no Post, `heldReason` null) and fails after the last retry (unit). T4 review NOTE 3 / AC-22 is asserted in TC-PS-22 and in the unit test.
- **The batch index is 1-based** (`Entry 2: ...`).
- **`brief.submitted` and `scheduled_generation.settled` were not given `postStyle` or `held`:** that is T7 (the analytics catalogue).
- **MCP has no E2E.** The MCP server is stdio. Its `generatePost` is the function the ACP route calls, so the unit tests cover the MCP-only layer and the ACP E2E covers the shared function.
- **E2E exemptions:** the mock caption embeds the topic, so a value in the topic is always a stated value; the exemptions (24/7, list markers) cannot be made to differ from "no value" through the mock, and TC-PS-13 asserts a clear check for such a brief. The exemption logic itself is covered by the T3 unit corpus.
- **Campaigns in E2E:** two for the suite (A with no sources, B with a briefing and a document that state values) and one more inside TC-PS-06 (deleted at the end of that case, which needs a fresh campaign to test create and clear).
- **A shell slip:** one command of mine ran `taskkill /F /IM node.exe`, which stopped my own :3001 server early (no other server was running, per the task). Nothing else was affected.

## Orchestrator-requested fixes

1. **PATCH keeps the stored style** (`queue/[gid]/route.ts`). When the body sends neither `postStyle` nor a legacy `goal`, the update omits `postStyle` and `goal` (a legacy null stays null) and writes `tone` only if one was sent. A sent style or goal re-resolves as before (an unknown key is still 400 and writes nothing); a null or blank style counts as not sent. Unit: `tests/unit/postStylesQueueRoutes.test.ts` (styled and legacy entries, tone only, sent style, sent legacy goal, unknown key). E2E: new TC-PS-08b.
2. **A held entry can be re-run** (`queue/[gid]/rerun/route.ts`). A COMPLETED entry with a non-null `heldReason` is accepted, and only that (a normal COMPLETED, PENDING or RUNNING entry is still 409). The re-run clears `heldReason` and the existing brief is reused, so a new draft is generated. Unit cases are in the same new file. TC-PS-21 is rewritten: it holds a PUBLISH_NOW entry with the price sentinel through the real tick, re-runs it through the route, checks `heldReason` is null, ticks again, and checks a different draft and a fresh hold; it also checks that a normal COMPLETED entry is 409. No Prisma status poke.
3. **Order dependence made explicit.** The campaign-default describe now has an `afterEach` that clears campaign A's default, so TC-PS-17 no longer depends on where TC-PS-05 happens to leave it.
