## Ambiguities and choices

- `getStyle` uses `Object.hasOwn`, so `constructor`, `__proto__` and `toString` never resolve (the design only said "returns a style or undefined").
- `revisionOf(dataset)` is exported from `styles.ts` (not the index) so the "adding a version raises it" test runs on a fixture; `POST_STYLES_REVISION = revisionOf(styles)`.
- The hash is SHA-256 over `JSON.stringify(versionContent)` (the `StyleVersion` object, key order as written). The hash guard is a pure function inside the test over any dataset plus a table; it also reports "committed but missing" and "no committed hash".
- Type-only `@prisma/client` imports are allowed by the new purity checks (the existing authoring purity helper bans any `@prisma/client`; I did not change it, I added a type-only-aware filter in the new describe). No `@prisma/client` import is used by `postStyles` at all in T1.
- `ArchetypeKey` is a type-only import from `@/lib/designData`; `styles.ts` imports the `archetypes` value from `@/lib/designData` (read-only, the one allowed edge). `src/lib/designData` is untouched.
- AC-01's last sentence is checked two ways: runtime via `Prisma.dmmf` (nullable, no default, right type) and compile-time via `satisfies` on `Omit<...UncheckedCreateInput, newColumns>`. The dmmf check does not open a DB connection.
- A retired-style case runs on a fixture shaped like the dataset, because the real dataset has none; the real `activeStyles` filter is covered by its own case. T2 adds the retired-key resolver case.
- `TONE_KEYS` lives in `types.ts`; the wizard's `constants.ts` is left to T2.
