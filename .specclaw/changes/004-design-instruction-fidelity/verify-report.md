## What is proven vs what is not

**Proven by execution:** the type system, the linter, 592 unit tests, a production build, and the rasterizing harness against real Chromium. The pure modules — `htmlDocument`, `inlineAssets`, `fontSet`, `instructionClasses`, `refineEnvelope`, `refineVerify`, `inlineEdit`/`elementEdit`, `revisionChain`, `testHooks` — are genuinely exercised, including the fail-closed branches and both prototype-pollution classes found during the build.

**Read but never executed:** every database write (no Postgres), every HTTP route response (no server), every rendered pixel of the new UI (no browser), and **the entire classification pipeline end to end**.

### The API-mode blind spot — the most important finding in this report

`.env.test:27` and `.github/workflows/e2e.yml:55` both set `DESIGN_PROVIDER=claude-html`. `isCliMode()` is therefore false, and the refine route takes its **API branch**, which hardcodes `classes=['add']`, `supersedes=[]` on every refine regardless of wording. The envelope parser, `resolveEffectiveClasses`, and the `remove`/`replace`/`constrain` post-conditions are **CLI-mode-only code, unreachable from the E2E suite — locally and in CI.**

**Production runs CLI mode.** So even a fully green E2E run would be green against a code path production never takes. This is the same masking pattern CLAUDE.md already records for PR #40 ("a green E2E suite missed it" because a seeded row made the gate pass), and it is why AC-08 through AC-13 are unverified rather than met. Logged as `learnings.md` L13.

The E2E cases were written to say so on their face: the §E2 catalog preamble states which ACs cannot be proven there and instructs future authors **"do not label a case here with one of those AC numbers."**
