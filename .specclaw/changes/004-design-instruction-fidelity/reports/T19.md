## What was implemented

### New route: `POST /api/drafts/[id]/rejected/[revisionId]/adopt`

`src/app/api/drafts/[id]/rejected/[revisionId]/adopt/route.ts` (new file). Team-scoped exactly like refine (`withTeamAuth` + `canAccessContent`; unknown/invisible draft → 404). Flow:

1. Load the draft; 404 if not found/inaccessible.
2. If `draft.pendingAction !== null` → 409 "Another action is already running on this draft" (mirrors `inlineEditBlockReason`'s message, matching refine/regenerate's own 409 text for the same condition).
3. Load the `DraftRevision` row by `params.revisionId`.
   - Row doesn't exist at all → **404** ("Rejected render not found") — parallels the draft-not-found 404; a resource that genuinely doesn't exist.
   - Row exists but any precondition fails (`row.draftId !== draft.id`, `row.id !== draft.notAppliedRevisionId`, `rejectedAt` null, `adoptedAt`/`discardedAt` set, `exportUrl` null) → **409**, matching the task's own enumerated "otherwise 409" list verbatim. Documented in the route why a mismatched-draft row also gets 409 not 404: the id is only ever handed to a client via _its own_ draft's poll response, so there's no separate cross-tenant secret a 404 would additionally protect beyond what the draft-visibility check already does.
4. Calls `commitDraftRevision` with `instruction: "Use anyway: <original instruction>"`, `html: row.htmlSnapshot`, `exportKey: row.exportUrl` (reused as-is — nothing re-renders), `adoptRejectedRevisionId: row.id`.
5. Maps `AdoptConflictError` → 409 (the authoritative race-safe outcome; see below). Response: `{ reply, revisionId, exportUrl }` — same shape as inline-edit/Override.

### `commitDraftRevision` extended (`src/lib/drafts/revisions.ts:129-220`)

New optional `CommitRevisionArgs.adoptRejectedRevisionId`. When set, **inside the same transaction**, before creating the new chain row:

1. Re-reads `Draft.notAppliedRevisionId` fresh via `tx.draft.findUnique` — never trusts a value the route read earlier (same "never trust the FK alone" principle as T18's `resolveNotAppliedOutcome`). Mismatch → `AdoptConflictError`.
2. Guarded `tx.draftRevision.updateMany` stamping `adoptedAt` + `adoptedRevisionNumber` (`= revisionNumber`, computed earlier in this same `withNextRevisionNumber` body), scoped on `{ id, draftId, rejectedAt: {not:null}, adoptedAt: null, discardedAt: null, exportUrl: {not:null} }`. `count !== 1` → `AdoptConflictError`.
3. Only then does the existing `tx.draftRevision.create` + `discardNotAppliedRender(tx, draftId)` + `tx.draft.update(...)` run unchanged — the newly-adopted row is excluded from that discard because its `adoptedAt` is already non-null (the ordering hazard T17's report flagged).

New exported `AdoptConflictError` class. `withNextRevisionNumber`'s catch only retries `PrismaClientKnownRequestError` P2002, so this error propagates immediately (no wasted retry loop) and aborts the whole transaction — no partial write.

### Single-flight choice — no new DraftAction value, no new migration

Checked `prisma/schema.prisma`'s `DraftAction` enum: `REGENERATE_COPY | REGENERATE_DESIGN | REFINE`. None describes "adopt a stored render" honestly — adopt makes no model call and does no render, so labelling it `REGENERATE_DESIGN`/`REFINE` would be actively misleading to anyone reading `Draft.pendingAction` later (e.g. the UI's `designActionPending` overlay text branches on exactly those two values). Per the task's ruling ("prefer no new migration... claim with an existing action value only if its meaning fits honestly. Otherwise use the conditional-update pattern that inline-edit relies on"), I used the **conditional-update pattern**: `inline-edit` already established the precedent of skipping `Draft.pendingAction` entirely for a synchronous, no-model action and instead relying on a guarded write. For adopt, the guard is the atomic `updateMany` above — the only way `AC-20a` ("a second adopt of the same render returns 409 and creates nothing") can be violated is if two adopts both flip the same row from `adoptedAt: null` to non-null, and Postgres's row-level locking under `UPDATE ... WHERE adoptedAt IS NULL` makes that structurally impossible (the loser's `WHERE` simply matches 0 rows once the winner commits).

The route-level `pendingAction !== null → 409` check additionally blocks adopt while a genuinely different action (refine/regenerate) is running, matching FR-14a's "single-flight like every other draft action" for that case too — this is best-effort (a TOCTOU window exists between this check and the transaction, same as inline-edit's own accepted precedent), but the _authoritative_ correctness guarantee for the specific AC-20a scenario (double-adopt) is the guarded UPDATE, not this check.

### Why the transactional guard needs no extra care for the "stale/superseded" case

`recordRejectedRender` already runs `discardNotAppliedRender(tx, draftId)` **inside the same transaction** as creating a _new_ rejected row and repointing `Draft.notAppliedRevisionId` at it. So by construction, the instant `notAppliedRevisionId` stops pointing at a given row, that row's `discardedAt` is _already_ set, atomically, in the same commit. This means checking `discardedAt: null` in the guard is equivalent to "is still the live outcome" — I don't need to separately re-verify `notAppliedRevisionId` match inside the guarded UPDATE's WHERE (I do it anyway, as an explicit fresh read, for defense-in-depth and because it's what makes "a mismatched notAppliedRevisionId is refused" independently testable without relying on that equivalence argument).

## Self-review findings

- **Concurrency of two adopts**: verified via unit test #3 (same-row double adopt) and reasoned through the Postgres UPDATE-under-WHERE semantics above — the guard is the sole correctness mechanism and needs no application-level lock.
- **Ordering hazard**: verified via unit test #1's explicit assertion that the adopted row's `discardedAt` stays null (proving the stamp-before-discard order holds) and test #2 (a _different_, still-live row is untouched when the requested row has already been discarded).
- **No leak across drafts/teams**: the route's `canAccessContent` check is unchanged from refine's own pattern; the row-eligibility check requires `row.draftId === draft.id`; the guarded UPDATE additionally scopes on `draftId`. Covered by the E2E cross-team-404 case.
- **Single writer of `Draft.htmlContent`**: adopt only ever writes it through the existing `commitDraftRevision` write path (the same one every other commit uses) — no new write site was added.
- I did **not** touch `.specclaw/changes/004-design-instruction-fidelity/{state.json,status.md,tasks.md}` or the untracked `.lock/`/`reports/`/`timeline.jsonl` — these were already modified/present in the working tree before I started (per the pre-task git status) and are SDD-tooling bookkeeping, not part of this implementation; left uncommitted and untouched, matching T18's precedent.

## Concerns

- **Judgment call, not blocking**: `commitDraftRevision`'s existing `promptVersion`/`fontSet` stamping runs unconditionally, including on adopt — so an adopted render gets stamped with the _current_ `PROMPT_VERSION`/font-set digest even though it wasn't re-rendered under them (it's a reused export from whenever the original refine ran). This is a pre-existing property of a precomputed-`exportKey` commit (the Override path has the same property when it _does_ re-render, where it's accurate; here it's a minor provenance imprecision). Not specified by the brief either way; I left `commitDraftRevision`'s behavior uniform rather than special-casing adopt, to avoid scope creep.
- **Judgment call, not blocking**: the "Use anyway" button's `disabled` state is driven only by its own `adopting` boolean, not by the panel's broader `busy` (which includes `pendingAction !== null`). Clicking it while a _different_ action happens to be in flight will hit the server's 409 and surface a toast — graceful, but not pre-emptively disabled in that specific window. The route-level `pendingAction` check exists for exactly this case; I chose not to thread an extra prop through for a rare edge case rather than grow `RefinementPanel`'s prop surface further.
- **backgroundImageUrl** is intentionally omitted from the adopt call to `commitDraftRevision` — the rejected row carries no record of what background (if any) its own refine attempt used, so `Draft.imageUrl` is left as whatever it already was rather than guessing. This means the adopted render's own background image (if the model added one) may not match `Draft.imageUrl`'s tracked value going forward. Not covered by the brief; flagging for awareness, not blocking.

### Important 1 — existence probe (fixed)

`src/app/api/drafts/[id]/rejected/[revisionId]/adopt/route.ts:61-77`. The row lookup changed from `prisma.draftRevision.findUnique({ where: { id: params.revisionId } })` to `prisma.draftRevision.findFirst({ where: { id: params.revisionId, draftId: draft.id } })`. A row belonging to a different draft (same team or a different one) now simply doesn't match the query and comes back `null`, taking the same 404 branch as a genuinely unknown id — the 409 "can no longer be adopted" branch is only reachable once the row is already confirmed to belong to THIS draft. Dropped the now-redundant `row.draftId === draft.id` from the `eligible` check (the query guarantees it) and rewrote the surrounding comments. New E2E case: `a real rejected-row id belonging to a DIFFERENT team's draft is 404, exactly like an unknown id` — creates a live, adoptable rejected row on a ClientX draft, then asks the admin's own (Bistec) draft to adopt that revisionId, asserts 404; then asks the same admin draft to adopt a string that was never a real id at all, asserts the identical 404.

### Important 2 — flaky presigned-URL comparison (fixed)

`tests/e2e/refine-not-applied.test.ts`. Added a `urlPath(u: string): string` helper (`new URL(u).pathname`) and replaced `expect(after.exportUrl).toBe(body.exportUrl)` with two path-only comparisons: `urlPath(after.exportUrl) === urlPath(notApplied.previewUrl)` (proves the draft's live export is genuinely the rejected render's own object, which the old assertion never even checked) and `urlPath(after.exportUrl) === urlPath(body.exportUrl)` (self-consistency of the route's own response). Grepped the whole `tests/e2e/` tree for other same-object presigned-URL equality comparisons (`exportUrl).toBe(`, `previewUrl).toBe(`) — the only other hit (`regression.test.ts:206`) compares against a fixed literal legacy URL with no signature at all, not two independently-signed URLs, so it isn't flaky and was left untouched.

### Minor 1 — the guard now re-checks Draft.pendingAction (fixed)

`src/lib/drafts/revisions.ts:190-212`. Replaced the previous `tx.draft.findUnique` (read) + manual compare with a single guarded `tx.draft.updateMany({ where: { id: draftId, pendingAction: null, notAppliedRevisionId: adoptRejectedRevisionId }, data: { updatedAt: new Date() } })` — one atomic conditional UPDATE checking both facts at once, "touching" the row the same heartbeat-style way `touchDraftAction` does. `count !== 1` → `AdoptConflictError` → 409, exactly like the existing DraftRevision-level guard.

**Is the window fully closed, stated honestly:** yes, for the case Minor 1 named — "a refine or regenerate claimed after the route's pre-check". The route's `inlineEditBlockReason` check is a fast, non-transactional pre-check purely to fail fast without opening a transaction; the _authoritative_ decision is always this guarded UPDATE, evaluated fresh at transaction time. Reasoned through the Postgres mechanics: if a competing `claimDraftAction` (a separate UPDATE on the same Draft row) is racing this guard, one of two things happens — (a) it commits first, so our guard's `WHERE pendingAction: null` correctly fails to match and we 409; or (b) ours commits first (we never set `pendingAction` to anything non-null, only bump `updatedAt`), and the competing claim, which was blocked waiting on our row lock, proceeds to re-evaluate its own `WHERE pendingAction: null` against our committed state and succeeds — which is correct, since by then our adopt has already finished and there is nothing left for it to race against. There is no window where both an adopt and a genuinely different action can believe they exclusively hold the draft. New unit test: `a draft with a pendingAction already claimed (a refine/regenerate in flight) refuses the adopt, touching nothing` — sets the fake's `pendingAction` to `'REFINE'` before calling `commitDraftRevision`, asserts `AdoptConflictError` and that the rejected row's own guard never ran (untouched `adoptedAt`, no new chain row).

Test harness change: `tests/unit/draftRevisions.test.ts`'s fake `client.draft` gained `updateMany` (matching on `pendingAction`/`notAppliedRevisionId` against the fake's new `db.pendingAction` field, deliberately NOT recorded into `db.draftUpdates` since that array tracks the meaningful commit-shaped writes existing tests assert on by index) and lost the now-unused `findUnique` it had gained in the original submission (revisions.ts no longer calls it).

### Minor 2 — reuse `inlineEditBlockReason` (fixed)

`src/app/api/drafts/[id]/rejected/[revisionId]/adopt/route.ts:49-52`. Replaced the route's own `if (draft.pendingAction !== null) return ...409` with `const blocked = inlineEditBlockReason(draft.status, draft.pendingAction); if (blocked) return NextResponse.json({ error: blocked }, { status: 409 })`. This also now refuses adopting on a draft that isn't `EXPORTED`/`PUBLISHED` — harmless in practice, since a not-applied outcome can only exist after a refine, and refine itself is only reachable on a ready draft (`RefinementPanel` is gated on `ready` in the page), so no existing passing test exercises a not-ready draft with a live not-applied outcome.

### Minor 3 — `adopting` folded into `busy` (fixed)

`src/components/drafts/RefinementPanel.tsx`: `const busy = running || pendingAction !== null || awaitingResolution || adopting`. `NotAppliedCard` gained a `disabled?: boolean` prop (separate from `adopting`, which now drives only the spinner icon) and the panel passes `disabled={busy}` — the button disables whenever ANY action is in flight (including its own), not just its own `adopting` state.

### Minor 5 — concurrent double-adopt E2E (added)

`tests/e2e/refine-not-applied.test.ts`, new case `two concurrent adopts of the same render: exactly one 200, one 409, exactly one new revision` — fires `Promise.all([api.post(adoptUrl), api.post(adoptUrl)])` against the same rejected row, asserts `[a.status(), b.status()].sort()` is `[200, 409]`, and that exactly one new row exists in the revision list afterward.
