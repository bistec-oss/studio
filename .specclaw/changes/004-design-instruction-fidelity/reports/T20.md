### 2. `src/lib/testHooks.ts` — two new exports

**`mockVerifyOutcome(instruction: string, attempt: 1 | 2): VerifyResult | null`**

Sentinels in the instruction, checked in this fixed order (first match wins):

| Sentinel                 | Effect                                                                   |
| ------------------------ | ------------------------------------------------------------------------ |
| `__VERIFY_UNAVAILABLE__` | `{ kind: 'unavailable', reason: '…' }` on every attempt                  |
| `__VERIFY_FAIL_ALWAYS__` | `{ kind: 'miss', reasons: […] }` on every attempt (twice-failed path)    |
| `__VERIFY_FAIL_ONCE__`   | miss on attempt 1, `{ kind: 'pass' }` on attempt 2 (retry-succeeds path) |
| `__VERIFY_PASS__`        | `{ kind: 'pass' }` on every attempt                                      |
| (none)                   | `null` — real verification runs unchanged                                |

Pure, synchronous, no I/O. Imports `VerifyResult` from `refineVerify.ts` as a **type-only** import (`import type`), which is erased under `isolatedModules` — no runtime circular-import with `refineVerify.ts` (which imports this module for `MOCK_AI` + both seams).

**`buildMockRefineReply(args: { slimHtml, instruction, attempt, width, height, promptContext? }): string`**

Returns a raw reply string in the real refine envelope wire format (`refineEnvelope.ts`'s fenced-JSON-header-then-document shape), so `parseRefineEnvelope` + `effectiveClasses` run on it unchanged — never a parsed object.

- **Default (no sentinel):** byte-identical to `buildMockHtml(promptContext ?? '', width, height)` — no envelope header at all. Verified in tests to be `===` to a direct `buildMockHtml` call, and that it parses as `classificationDefaulted: true` → `add`.
- **Sentinels** (instruction substrings, checked in this order, first match wins):
  1. `__REFINE_TRUNCATED__` — reply has no closing `</html>`.
  2. `__REFINE_REDUCE_NOOP__` / `__REFINE_REDUCE_REAL__` — a `remove` whose reply either echoes the current document unchanged (structural miss — the reported "reduce the text" bug) or produces a much shorter document (pass). The named `supersedes` phrase is the first ≤6 words of `slimHtml`'s stripped visible text.
  3. `__REFINE_IMAGE_DUP__` / `__REFINE_IMAGE_REPLACE__` — a `replace` whose reply either keeps the superseded image AND adds a new one (miss — the reported duplicate-background bug) or drops the old one and adds a new one (pass). The superseded ref is the first `__INLINE_ASSET_n__` token or `src=`/`url()` reference found in `slimHtml`.
  4. `__REFINE_EMPTY_SUPERSEDES__` — a `replace` with `supersedes: []` (AC-10; verified to downgrade to `add` via the real `effectiveClasses`).
  5. `__REFINE_TOKEN_RENAME__` — renames an `__INLINE_ASSET_n__` token found in `slimHtml` to a still token-shaped but unrecognized string (verified via the real `reconcileInlineAssets` → `mismatch`).
  6. `__REFINE_MULTI_CLASS__` — returns `['replace', 'add']` (AC-11).
- **`__REFINE_FIX_ON_RETRY__`** — combinable modifier: when present and `attempt === 2`, flips cases 1–3 and 5 (truncated/reduce/image/token-rename) to their "fixed" variant. No effect alone or on multi-class.
- **Degrade behaviour:** when `slimHtml` carries no visible text (reduce cases) or no image/token (image/token-rename cases), the seam falls back to an empty `supersedes` or a synthetic non-resolving reference respectively — both are deterministic misses (a downgrade or "fragment not found"), never a crash or a silent pass. Token-rename with no token present falls back to the same byte-identical default reply. Covered by dedicated tests.

All string construction is pure and deterministic (no `Math.random`, no `Date.now()`), confirmed by an explicit "same args → same output" test.

## Concerns

1. **`findTextPhrase`/`findImageRef` are approximations, not the real extractor.** They mirror `domFacts.ts`'s `staticDomFacts` closely enough for the documented purpose (picking a fragment that will resolve against the real mock extractor), and this is proven indirectly by the envelope/effectiveClasses/reconcileInlineAssets round-trip tests, but I did not import `staticDomFacts` itself into the unit tests to double-check byte-for-byte agreement on `slimHtml`'s exact visible-text tokenization for arbitrary documents (e.g. entity decoding, `<br>` handling). This matters most for T21, which will construct real before-documents; if a future before-document's text extraction disagrees with my regex in some corner case, the `supersedes` phrase would still be _taken from_ `slimHtml` (so it will always be found in `slimHtml` itself, by construction) but might not match what `staticDomFacts` computes as the innermost element/passage in an unusual layout. I did not think this rises to a blocking concern since the mock's `staticDomFacts` reports the WHOLE document as one synthetic `body` element, so phrase-in-body-text is essentially guaranteed to line up.
2. **The image-ref regex (`IMAGE_ATTR_RE`) is single-match, first-occurrence.** For a `slimHtml` with multiple images, it always picks the very first one in document order. This is fine for the documented cases (T21 is expected to arrange a before-document with the relevant image), but worth flagging if a future test needs to target a _specific_ (not first) image.
3. I did not add a CHANGELOG-style entry to `docs/handoff.md` or `.specclaw` status files — those looked like the controller's own bookkeeping (already mid-edit when I started) rather than something this task's brief asked me to touch.
