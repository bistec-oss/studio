# Wave 5 dispatch P — T24 report (change 004 Phase 3): click-to-select element mode + E2E

**Status: DONE_WITH_CONCERNS.** The work is one commit on `v2`, `783c3d56` (not pushed). The concerns are listed below.

## What was built

### Pure client helpers: `src/components/drafts/inlineElementEdit.ts` (new; DOM-free, unit tested)

- `canEditElementText` (`:69`) / `canEditElementStyle` (`:81`) mirror the server's leaf rule and style rule.
  - Text is allowed only when all of these hold: the element has no content child elements (pure chrome is ignored, and an img-wrap counts as content); it is not void; it is not in `TEXT_FORBIDDEN`.
  - SVG elements additionally need a direct text node, because a self-closed `<rect/>` has no content range and the DOM can't tell it from `<rect></rect>`.
  - The server stays the authority. A contract test runs `applyElementEdit` on the equivalent stored HTML and asserts that the mirror agrees.
- `snapshotElementLocator(el, body, baseRevisionNumber)` (`:90`) builds `{path, tag, text, baseRevisionNumber}` with the shared `editorElementPath` / `editorFingerprintText`. It does not reimplement path or fingerprint logic, and it returns null for chrome.
- `resolveEditorPath` (`:118`) is the inverse of the path, using the same chrome-transparent child rule. It is used only to re-select the same element in the reloaded document after a save. The new locator is then snapshotted fresh from that document.
- `buildElementEditBody` (`:130`) builds exactly the Ruling W5-B body. It never sends a selector.
- `interpretElementEditResponse` (`:170`) maps every status/code to one UI outcome. `postElementEdit` (`:207`) sends the POST and never throws (a network failure becomes `{kind:'error'}`).
- `cssColorToHex` (`:228`) seeds the hex picker from the computed colour. It returns null when the colour is transparent or can't be shown.
- Colour and size are deliberately **not** pre-validated on the client. The server's 400 message is what the user sees, so there is one grammar, not two.

### The modal: `src/components/drafts/InlineEditModal.tsx`

- A `SegmentedToggle` switches between **Whole document** (the default) and **Single element**.
- **Whole-document mode is unchanged.** It keeps the same `wireEditor` chrome, the same `stripEditingChrome` save and the same `onSaved` + close flow. The only addition is an `input` listener, plus `setDirty` after a photo replace, so that a mode switch can warn with `useConfirm` before it discards unsaved typing.
- **One read.**
  - The document and its revision are held together as `LoadedDoc {html, revisionNumber, seq}`. It is seeded from the `html` + `baseRevisionNumber` props, which come from one `draft` object, i.e. one `GET /api/drafts/[id]`.
  - After that it is replaced only by `reloadFromServer()` (`:340`), which takes `htmlContent` and `currentRevisionNumber` from **one** response.
  - The iframe is keyed on `${mode}-${seq}`, so every load, and every mode switch, is a pristine parse.
- **No chrome in element mode.**
  - `wireSelector` (`:256`) injects nothing into `<body>`: no contenteditable, no img-wrap, no button. The only addition is a cursor rule in `<head>`, which is outside every path.
  - The selection and hover highlights are overlays drawn by the parent over the scaled iframe. They are not DOM mutations inside it.
  - Clicks are captured with `preventDefault`, so links and buttons in the design never activate.
- **Fingerprint timing.** `selectElement` (`:231`) snapshots the locator at click time, bound to the revision of the document it was wired with. The element-mode iframe is not editable, so nothing can change it between selection and apply.
- **One request in flight.** `applyElementEdit` (`:366`) is gated by `inFlightRef`, a ref rather than state, so a double click can't pass. Clicks in the iframe are ignored while a request is in flight, and every field and button is disabled while a request or reload is in progress or the draft is busy.
- **Chaining.** On a 200:
  - it shows the toast, calls `onSaved()` (the existing page refresh), sets a pending re-select `{path, tag, revisionNumber}` and re-GETs;
  - the next locator is snapshotted from the reloaded document and its pointer;
  - the re-select only fires if the reloaded document **is** the returned `revisionNumber`;
  - if the re-GET shows a newer pointer (another writer landed straight after), the re-select is dropped and a notice says so. The pair from the GET is still used, because it is self-consistent, and combining the returned number with newer HTML would be exactly the two-read bug.
- **The caller** (`src/app/(app)/drafts/[id]/page.tsx:536`) now mounts the modal per open and passes `baseRevisionNumber={draft.currentRevisionNumber}` from the same `draft` object as `html`.

### The side panel: `src/components/drafts/ElementEditPanel.tsx` (new)

- It shows the selected tag chip (mono), **Parent** (select the containing element) and clear.
- Fields: Text (a textarea, text leaves only; composites get an explanatory note instead), Text colour and Background (a hex swatch picker plus a text field that also takes `rgb()`/`rgba()`), and Font size. Each has its own Apply button, so one Apply is one request.
- The notice banner (`role="alert"`) carries the 409 states, and each field has its own inline error (`role="alert"`) for 400s.
- It uses the design-system tokens throughout (glass panel and inputs, `primary`/`primary-light`, and `light-`/`dark-` text tokens). Both themes were checked; see Screenshots.

## Verdict per item

**Residual Important: a failed re-read left the stale document writable. ADDRESSED.**

- Before the fix, `reloadFromServer` kept `loaded` unchanged on a failed read, `synced` stayed true, and `editorReady` came back true. Switching to Whole document (no re-read) and saving then serialized the pre-edit document, with no base revision, over the element edit.
- **Fail closed.** `reloadFromServer` now calls `failClosed()` on a failed read, or on a draft with no design (`InlineEditModal.tsx:386`, used at `:395` and `:410`). It clears `synced` and sets `syncFailed`.
  - The existing "Try again" overlay then blocks every write: Save, Apply, selection and navigation all gate on `editorReady`.
  - A successful read sets `synced` true and clears `syncFailed` (`:405`).
  - `syncWithServer` (`:420`) is now only the first read plus "Try again". Both go through the same fail-closed path.
- **Re-read on the mode switch.** `switchMode` into Whole document re-reads through the same gated path (`:528`), so document mode always starts from a fresh `{html, pointer}` pair.
  - `setMode` and the reload's `setReloading(true)` land in the same batched render, so there is never a render in which Save is enabled on the old document.
  - A failed switch read fails closed like any other read.
- **`selectBody`** now checks `synced` as well as `wiredKey` (`:502`).

## Test and TDD RED

- **TC-INLINE-18** (`draft-inline-edit.test.ts:716`) uses a Playwright `page.route` (`failDraftGet`, `:751`) that fails exactly one browser GET of `/api/drafts/<id>`.
- **Only the editor's GET may fail.** The draft page swaps to its error screen when its own `fetchDraft` fails, which would unmount the modal.
  - After an Apply, `onSaved` issues the page refetch first and the editor's re-read second, so phase 1 fails the 2nd GET.
  - If that order ever changes, the page errors and the test fails loudly; it cannot pass by accident.
- **Phase 1.** An element Apply succeeds, the editor's re-read fails, then the user switches to Whole document and saves. The element edit must survive.
