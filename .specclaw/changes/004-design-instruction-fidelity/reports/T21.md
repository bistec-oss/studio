### What changed

- **`src/lib/testHooks.ts`: `buildMockVerifierReply`** has three new sentinels, documented in its JSDoc:
  - `__VERIFIER_SAYS_NO__` returns a well-formed `{"applied": false, "reason": …}`, which is a miss;
  - `__VERIFIER_GARBAGE__` returns prose with no JSON, which the parser can't read, so it is unavailable;
  - `__VERIFIER_EMPTY__` returns `''`, which is unavailable.
- **They are not forced outcomes.** They are named `__VERIFIER_…__` and never `__VERIFY_…__`, so `mockVerifyOutcome` returns null for them.
  - `verifyRefine` therefore runs the real path: fact extraction, then `onVerifierCall`, then this canned reply, then `parseVerifierVerdict`.
  - As a result, `rejection.verifierCalls` counts the calls truthfully.
  - These sentinels are only reached for an `add` whose structural checks passed.
  - With no sentinel, the reply is unchanged ("applied").
- **Unit tests.**
  - `tests/unit/refineVerify.test.ts` ("MOCK_AI seam" describe) has 4 new cases. Each sentinel goes through the real parser with MOCK_AI on. The cases assert: extraction ran; `onVerifierCall` fired exactly once; no real SDK/CLI call; the results are a miss with the `add: Mock verifier…` reason, unavailable `verifier response was not a valid verdict`, and unavailable `verifier returned an empty response`. A fourth case shows the sentinels cost no call on a structural class.
