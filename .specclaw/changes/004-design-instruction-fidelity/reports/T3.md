## T2 — Self-explaining, always-both redeploy step

File: `.github/workflows/docker-publish.yml`.

Replaced the two independent `curl -fsS` steps with one script step (`id: redeploy`) that loops over both resource UUIDs via a `redeploy_one <name> <uuid>` function:

- `curl -sS -o <tmp file> -w '%{http_code}'` (not `-f`) so the body survives a non-2xx status.
- `status_to_reason()` maps 401/403 → "token rejected — rotate COOLIFY_API_TOKEN (docs/coolify-token-rotation.md)", 404 → "resource UUID not found", 2xx → "ok", else → "unexpected response" (with the body printed for that last case only, via `::error::`).
- `set -uo pipefail` (no `-e`) so a failed `redeploy_one` for one resource never aborts the other — both are always invoked.
- On success for `scheduler`, `deployment_uuid` is pulled out of the response (`jq -r '.deployments[0].deployment_uuid // empty'`) and written to `$GITHUB_OUTPUT` as `scheduler_deployment_uuid`, per ruling 2, for T4's verify step to consume.
- Final summary line + `exit 1` if either `app_result` or `scheduler_result` is non-zero.

Token handling: `COOLIFY_API_TOKEN: ${{ secrets.COOLIFY_API_TOKEN }}` is set at the step's `env:` and referenced only as `$COOLIFY_API_TOKEN` inside `run:` — never interpolated into the script text, never echoed, no `set -x`.

Also added: `workflow_dispatch:` trigger (kept `push: branches: [main]`), and workflow-level `env.COOLIFY_URL` / `env.PROD_URL` (ruling 4).

## T4 — Post-deploy verification + current action majors

### Verify step

New step, `Verify deploy (prod /api/health + scheduler deployment status)`, appended after the redeploy step (no `if:` condition — it only runs if the redeploy step succeeded, which is correct: a failed redeploy already reds the job and there's nothing new to poll for; this was a deliberate simplification over adding `if: always()`, since the always-both requirement is about the app-check vs scheduler-check _within_ this step, not about running after a failed redeploy).

- **App check:** loop `seq 1 40` (× `sleep 15` = ~10 min), `curl --max-time 10 "$PROD_URL/api/health"`, `jq -r '.commit // empty'`, compares against `${{ github.sha }}`; tracks `last_commit` for the failure message; network errors / non-200 fall through to "not yet" via `|| true`.
- **Scheduler check:** reads `${{ steps.redeploy.outputs.scheduler_deployment_uuid }}`; if empty, `::error::scheduler status unknown — the redeploy response had no deployment_uuid` and fails (ruling 2's exact contract) without ever calling Coolify. Otherwise polls `GET $COOLIFY_URL/api/v1/deployments/<uuid>` (Bearer auth) with the same 40×15s budget; `finished` → success, `failed`/`cancelled` → breaks immediately with an error (does not burn the rest of the budget), anything else → keeps polling.
- Both checks run unconditionally in sequence (no early return between them); final `if` fails the step if either is unverified.

### Local proof of the verify logic

Since `${{ github.sha }}` and `${{ steps.redeploy.outputs.scheduler_deployment_uuid }}` are resolved by the GitHub Actions runner _before_ bash ever sees the script (not at bash-evaluation time), I extracted the step's `run:` text and substituted those two expressions with a literal test SHA / a `$FAKE_DEPLOYMENT_UUID` env var respectively (this mirrors what the runner does — no logic change, just where the substitution happens) and shortened `sleep 15` → `sleep 0.2` to keep the timeout case fast. Ran it against two Node stubs (fake `/api/health` and fake `/api/v1/deployments/<uuid>`):

- **Both match / finished:** `prod /api/health reports deadbeef00 after 15s` (i.e. after 1 fast-sleep iteration) / `scheduler deployment finished after 15s` → `exit=0`.

## Fix round 1 (review findings)

Same worktree/branch. One commit: `4c919162` — ci: fix scheduler status poll auth handling; guard manual dispatch to main.

### Finding 1 (Important) — scheduler status poll vs token scope

Confirmed the bug as described: the old scheduler-status loop piped `curl` straight into `jq -r '.status // empty'` with no status-code check, so a 401/403 response (deploy-only token hitting a read-gated endpoint) would just produce an empty `.status`, fall into the `*) sleep 15 ;;` branch, and silently retry for the full 40 attempts before failing with an unexplained "last status: unknown".

Fix, in the scheduler branch of the verify step (`.github/workflows/docker-publish.yml`):

- Switched the poll to the same `-o <tmp file> -w '%{http_code}'` pattern the redeploy step already uses (not `-f`), so the HTTP status is captured on every attempt instead of being invisible to the pipe.
- On `401`/`403`: prints `::error::token rejected by /api/v1/deployments — COOLIFY_API_TOKEN needs the read ability as well as deploy (docs/coolify-token-rotation.md)` and breaks immediately — no more looping 40 times against a token that will never work. Guarded the final generic timeout message with `&& [ "$auth_failed" != 1 ]` so the two errors don't both print for the same failure.
- On any other non-200: `last_status` resets to `"(none)"` for that attempt (falls through to the default `sleep 15` case) and `last_http` is updated, so a run that times out for a different reason now reports `... last status: unknown (last HTTP: <code>)` instead of just "unknown".
- Updated the token-scope comment above the redeploy step (was: "create an API token with deploy scope") to say the token needs **both** `deploy` (for `/deploy`) and `read` (for `/deployments/<uuid>`, which is read-gated not deploy-gated).
- Left `docs/coolify-token-rotation.md` untouched — per the coordinator's instruction, that doc lives only on `v2` and is the controller's to update there.

### Finding 2 (Important) — workflow_dispatch could deploy any ref

Confirmed: `workflow_dispatch:` had no ref restriction, so a manual run from a feature branch would build and redeploy prod with that branch's code — `push` was already `branches: [main]`, but dispatch bypassed that entirely.

Fix: added `if: github.ref == 'refs/heads/main'` at the `build-and-push` job level (simplest form per the coordinator's suggestion). A dispatch on any other ref now shows as a skipped job in the Actions UI rather than silently deploying; `push` behavior is unchanged (it was already branch-filtered, and `refs/heads/main` is what `push: branches: [main]` resolves to, so both triggers now agree explicitly). Updated the `workflow_dispatch:` trigger comment and added a comment on the `if:` line explaining why.
