# Wave 2 dispatch F — T8 report

## What I implemented

`FR-22`: a `Draft` now carries `fontSet`, a digest of the Alpine `font-*` apk
packages installed at render time, stamped next to the existing
`promptVersion` on every write that already stamps `promptVersion` for a
render. Absent (`null`) is valid and expected everywhere off the built Alpine
image (Windows dev, Ubuntu CI) and for drafts rendered before this column
existed.

- **New `src/lib/renderer/fontSet.ts`:**
  - `fontSetIdFromApkDb(text: string): string | null` — pure parser, no I/O.
    Splits Alpine's `/lib/apk/db/installed` format (blank-line-separated
    package records, `P:`/`V:` fields among others) into records, keeps only
    packages whose name starts with `font-`, pairs each with its version,
    **sorts** (order-independence) and joins as `name@version`, then
    `sha256`s the joined list and returns `` `apk:${first 12 hex chars}` ``.
    - No package records parsed at all (empty string, or garbage with no
      `P:` lines) → `null` — nothing meaningful to digest, same "absent" as
      a missing file.
    - Package records exist but none are `font-*` → a **stable non-null
      id** (hash of the empty font list). Chose this over `null` (brief
      said either is fine, document the choice) because it's a real,
      deterministic parse result distinct from "couldn't parse anything" —
      collapsing both into `null` would make "no fonts installed" and
      "unparseable input" indistinguishable to a reader.
  - `getFontSetId(): string | null` — memoized at module scope (computed
    once per process; the installed font set can't change without a
    redeploy/new container, so there's nothing to gain by re-reading on
    every render). Reads `/lib/apk/db/installed`, delegates to the pure
    parser. **Never throws:** `ENOENT` (the expected case everywhere except
    the built Alpine runner image) returns `null` silently; any other
    read error is logged once via `console.warn` and also returns `null`
    (cached, so it can only log once regardless).

- **Schema + migration:** `Draft.fontSet String?` added next to
  `promptVersion` in `prisma/schema.prisma`. New migration
  `prisma/migrations/20260927120000_draft_font_set/migration.sql`:
  ```sql
  ALTER TABLE "Draft" ADD COLUMN "fontSet" TEXT;
  ```
  Nullable, no backfill, matching the existing `promptVersion` migration's
  style (`20260702113000_draft_prompt_version`). Ran `npx prisma generate`
  afterward (did not touch any running Postgres container — this only
  updates the local `@prisma/client` typings/engine, no DB connection).

## Render/export sites deliberately left unstamped, and why

Per the brief's Fact #24, I checked `/api/generate/export`, revision
restore, and refine specifically:

- **`refine`** — routes through `commitDraftRevision` (site 3 above), so
  it's covered without a direct edit to `refine/route.ts`.
- **`/api/generate/export/route.ts`** — renders `htmlContent` → PNG via
  Puppeteer and writes `{ exportUrl: key, status: 'EXPORTED' }`, but has
  **never** written `promptVersion` (confirmed by reading the file in
  full). Controller ruling 3 scopes this task to "every site that stamps
  `promptVersion` for a render" — this site doesn't, so adding `fontSet`
  here alone (with no `promptVersion` alongside it) would be new,
  unrequested behavior outside the brief's stated boundary, not a parallel
  fix. Left untouched.
- **`revisions/[rev]/restore/route.ts`** — same situation: it re-renders a
  revision's stored `htmlSnapshot` only when that legacy revision has no
  stored `exportUrl`, and its `prisma.draft.update` has never included
  `promptVersion` either. Left untouched for the same reason.
- **`regenerate-design/route.ts`'s "legacy guard" branch** (lines ~73–88,
  pre-edit numbering) — this branch only `tx.draftRevision.create`s a
  snapshot of the **already-live** design (so Undo has a target on old
  drafts predating `currentRevisionNumber`); it does **not** touch the
  draft's live fields, so it isn't a render write in the sense this task
  cares about. Left untouched. (Note: `DraftRevision` itself has no
  `promptVersion` column either — confirmed in `schema.prisma` — so
  per-revision provenance is a pre-existing limitation, not something T8
  introduces or was asked to fix.)
- **`regenerate-copy`** — doesn't render at all (copy-only); not touched,
  per ruling 3's second sentence.

## Concerns

- `getFontSetId`'s process-lifetime memoization means if the apk database
  were somehow altered mid-process (never happens in the real deployment —
  the image is immutable per container lifetime; a font change always
  means a new image/container), the cached value wouldn't update. This
  matches the brief's explicit instruction ("computed once and cached
  (module-level memo)") — flagging only so it's a known, intentional
  tradeoff rather than an oversight.
- `/api/generate/export` and revision-restore are real render sites that
  still don't carry any glyph-environment provenance (`promptVersion` or
  now `fontSet`). This is a pre-existing gap I did not introduce and the
  brief's scoping rule (ruling 3) explicitly excludes them from this task
  — noting it here in case a future task wants to close it.
- Optional Docker in-image proof: done. Built `bistec-studio:fontset` from
  the real `Dockerfile` (`docker build -t bistec-studio:fontset .`), then
  ran a plain `node -e` script inside the built runner image (no TS
  available there) that reads `/lib/apk/db/installed` and reproduces
  `fontSetIdFromApkDb`'s exact algorithm (same split/commit/sort/sha256
  logic, copy-pasted into the inline script rather than re-derived, so it's
  provably the same digest the TS module would compute). Output:
