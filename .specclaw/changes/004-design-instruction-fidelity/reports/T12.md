## The contract

### DomFacts (in `src/lib/agent/instructionClasses.ts`; T14 implements the extractor)

```ts
interface DomElementFact {
  tag: string // lowercase
  id: string | null
  classes: string[]
  text: string // subtree innerText, whitespace collapsed (ancestors contain descendants' text)
  imageSources: string[] // this element's <img> src + every url() in its computed background-image
  fontSizePx: number | null // computed, rounded to an integer
  box: { width: number; height: number } | null // rendered size, rounded to integers
}
interface DomFacts {
  text: string // body innerText, whitespace collapsed
  imageSources: string[] // all sources, document order, duplicates kept
  elementCount: number // rendered (display != none) elements under <body>
  elements: DomElementFact[] // every rendered element carrying text or an image source, in document order
}
```

Contract notes for T14:

- A data URI that the model saw as `__INLINE_ASSET_n__` must appear in `imageSources` as that token. Otherwise the model's `supersedes` and the facts use different names for the same image.
- `elements` must be in document order, because the constrain no-op check compares facts directly.

### Post-conditions

The signature is `(input: { before, after, supersedes, classes }) => { ok: true } | { ok: false, reason }`. Reasons are written to be read by the model, so the FR-11 retry can show it the miss.

**Deviation from ruling 1 (an addition): the input also carries `classes`**, meaning every class the instruction had. Without it, multi-clause instructions (AC-11) contradict themselves. For "make the headline smaller and add a logo" (constrain + add), constrain's "nothing added" check would reject the logo that the add clause asked for. The same goes for "use the upload as the background and make the text smaller" (replace + constrain): the upload is a new image source. So when an additive class (`add` or `replace`) is also present, the whole-document growth checks stand down. The per-fragment checks never do.

**How a fragment is matched.** A fragment is a verbatim piece of the original document. There are three kinds:

- **Image URL.** Any `url('…')` wrapper and quotes are removed first. It matches if it is a substring of an extracted source, so a filename or relative path also matches.
- **`#id` or `.class`.** Matched against element ids and class tokens, or as visible text, so a hashtag such as `#IRP` works. It is never matched as a substring of an image URL, where `.logo` would hit an unrelated `brand.logo.svg`.
- **Text phrase.** Matched against visible text, ignoring case and whitespace, because `text-transform: uppercase` renders differently from the source.

**Per class:**

- **replace:** `supersedes` must be non-empty after trimming, or it fails closed. Every fragment must be present in `before`; a fragment that was never there is a miss. Every fragment must be absent from `after`.
  - If `remove` is also present, the two classes share one flat `supersedes` list. In that case a text phrase that was shortened rather than deleted also satisfies replace. Image and `#id`/`.class` fragments still have to be gone.
  - The duplicate-image regression (AC-09) fails this check. It has its own test.
- **remove:** the same non-empty and present-in-`before` rules apply. Then:
  - Each fragment must be **reduced**: absent from `after`, or a text phrase whose innermost container (the element with the shortest text that contains the phrase) got strictly shorter.
  - The document must also have **shrunk**: shorter visible text, fewer image sources, or fewer elements. This stands down when `add` or `replace` is also present.
  - **Deviation from ruling 3:** the ruling says "visible text strictly shorter". I widened it to "any of text, images or elements shrank", because "remove the logo" is a valid remove that does not change text length. The per-fragment check still makes "reduce the text" shorten the text it names (AC-08).
- **constrain:** nothing may be added and something must change.
  - Nothing added means: no new image source, element count not increased, visible text not longer. These checks stand down when `add` or `replace` is also present.
  - Something changed means the before and after facts differ (text, sources, count, or any element's tag, id, classes, text, sources, fontSizePx or box). This check always applies.
- **add:** `postCondition: null`. T14's Haiku verifier handles it.

**Worked constrain example (in the module header and in the semantics text).** The instruction is "make the headline smaller", classified as `["constrain"]` with `supersedes: []`.

- ✓ The headline goes from 96px to 72px and nothing else changes.
- ✗ The headline shrinks but a "NEW" badge is added: the element count and the text grew.
- ✗ The facts are identical: nothing changed.

The semantics text also carries a second example, "keep the body text under 12 words".

**What is not measured: the bound itself.** Whether the headline is actually _smaller_, or the body actually under N words, is not checked. The target and the value of the bound are written in the instruction's prose. Checking them needs either a model or a structured `bound` field in the envelope. The facts can prove "nothing added" and "something changed", and those are what is checked.

### The table

`INSTRUCTION_CLASSES: Record<'add'|'replace'|'remove'|'constrain', { semantics, postCondition, destructive }>`. Other exports:

- `INSTRUCTION_CLASS_KEYS`
- `PRESERVING_CLASS = 'add'`
- `renderClassSemantics(table = INSTRUCTION_CLASSES)`, which renders the block for the refine prompt: each class's semantics word for word, the FR-05 rule ("cannot cleanly classify → add (or constrain)"), and the `supersedes` rule with an example.

The table is a parameter so that AC-19 can be tested: editing the table changes the rendered block. `destructive` lives in the table, so `effectiveClasses` reads it from there instead of keeping its own list.

### Envelope wire format (`src/lib/agent/refineEnvelope.ts`)

A JSON header comes **before** the document. The code fence around it is optional:

````
```json
{"classes": ["replace"], "supersedes": ["https://example.com/images/old-background.png"]}
```
<!DOCTYPE html>
<html>…</html>
````

How `parseRefineEnvelope(raw)` works:

- It returns `RefineEnvelope | null`, with the fields `classes`, `supersedes`, `html`, `discarded` and `classificationDefaulted`.
- The document is cut with `extractHtmlDocument`, not a second boundary.
- It looks for the header only outside the cut document:
  - first in the text before the document, taking the **last** JSON object that has `classes` or `supersedes`;
  - failing that, in the text after the document, taking the first such object.
- Braces inside the document (CSS, JSON script tags) are never read as the header.
- Every `{` is tried as a starting point on its own, and braces inside strings are handled, so an unbalanced brace in the narration cannot swallow the header.
- Class values are matched ignoring case and surrounding whitespace, unknown values are dropped, and duplicates collapse. A single string is accepted in place of an array.
- `supersedes` entries are trimmed. Empty entries, non-strings and duplicates are dropped.
- **Defaults:** no header, unparseable JSON, no `classes`, or no known class left gives `['add']` with `classificationDefaulted: true`. A missing `supersedes` gives `[]`. No document at all gives `null`.
- `discarded` is the narration with the header and fence lines removed, for logging.
- `REFINE_ENVELOPE_EXAMPLE` and `renderEnvelopeProtocol()` hold the output protocol for T17. The tests parse that example, so the prompt and the parser cannot disagree.

### effectiveClasses (FR-04, for the route)

`effectiveClasses({ classes, supersedes })` returns `{ classes, downgraded }`. When `supersedes` names nothing (empty after trimming), `replace` and `remove` become `add`. Order is kept and duplicates collapse. `downgraded` lists what was downgraded; if it is non-empty, the route should treat the classification as ambiguous (FR-05).

The downgrade target is `add`, not `constrain`. `add`'s semantics are "preserve all existing content", which is exactly what "preserving behaviour" means. `constrain`'s no-op check would also reject an honest preserving output.

Examples:

- `['replace']` with `[]` gives `['add']`, downgraded `['replace']`.
- `['remove','constrain']` with `[]` gives `['add','constrain']`.

## Contract after this round

**Fragments** are used by `supersedes` and `constrains[].fragment`. HTML entities (`&amp;`, `&nbsp;`, `&quot;`, and decimal and hex numeric forms) are decoded before matching. Each fragment is resolved in `before` to the content it identifies:

- **`#id` / `.class` that matches an element.** It identifies that element's image sources. If the element carries no image, it identifies the element's visible text instead. The element itself may survive the edit. If the token matches no element, it falls through to the text rule, so a hashtag like "#IRP" still works.
- **A substring of an image source.** This covers a URL, a filename, `url('…')`, or an `__INLINE_ASSET_n__` token. It identifies that image.
- **A text phrase.** It identifies the phrase plus the "passage": the full text of the phrase's innermost containing element.

**Reduced text (item 1).** A text passage counts as reduced only when it no longer appears intact in `after.text`, and either the phrase is gone or its innermost container got shorter. A token that identified text is reduced when the passage is no longer intact and the element is gone or its text is shorter.

**replace (item 3):** every fragment's content is absent from `after`. With `remove` also present, a fragment only has to be reduced.

**remove (item 2):**

- Every fragment's content must be reduced.
- If any fragment carries text, the visible **word count** must be strictly lower.
- If every fragment is image-only, the design must have fewer image sources or fewer elements.
- The whole-document check stands down while an `additive` class is also present. The per-fragment check always applies, and it is the check item 1 hardened.

**constrain (item 4):**

- Each `constrains` target must resolve to at least one element in `before`.
- Each such element's counterpart in `after` is found by, in order: the same id; else the same tag and classes at the same position; else the fragment resolved again in `after`. If no counterpart exists, it is a miss, because a constrain must not delete.
- The counterpart must change measurably. The measured attributes are font-size, box area, text length and word count.
- With a direction, at least one attribute must move that way and none may move the other way.
- The "nothing added" checks apply only when constrain is the only class.
- A constrain with no target fails closed.

**Envelope.** The header gains an optional `constrains: [{fragment, direction?: "decrease"|"increase"}]`. A bare string entry becomes `{fragment}`, an unknown direction is dropped, and entries de-duplicate by fragment. A JSON object carrying any of the three keys counts as a header. `REFINE_ENVELOPE_EXAMPLE` now shows `replace` + `constrain` with both lists:

````
```json
{"classes": ["replace", "constrain"], "supersedes": ["https://example.com/images/old-background.png"], "constrains": [{"fragment": "#headline", "direction": "decrease"}]}
```
<!DOCTYPE html>
<html>…</html>
````

**effectiveClasses** now takes `{classes, supersedes, constrains?}`. A destructive class with an empty `supersedes`, or a `constrain` with no usable target, becomes `add`, and the downgrade is reported.

**Item 5.** If narration mentions `<!DOCTYPE html>` or `<html>` before the header, the parser re-cuts. The condition is that the cut document contains a header before its first `<head>`/`<body>`/`<style>` and another document start follows that header. The document is then cut again with `extractHtmlDocument` from the text after the header.

**Items 7 and 8:**

- The semantics ask for a phrase unique to the passage.
- `additive` is now a per-class flag in the table. Post-conditions receive the table as a second argument.
- New `checkPostConditions(input, table = INSTRUCTION_CLASSES)`, which is the verifier consumer for T14.

## Interpretations worth a second look

1. **Remove's word-count check stands down while `add` or `replace` is present.** Ruling 2 says "whenever ANY fragment is text". Applied literally, "shorten the paragraph and add a caption" would always fail. Ruling 1 describes the stand-down as existing behaviour and hardens the per-fragment check to cover it. I kept the stand-down, and the per-fragment passage-intact rule still applies.
2. **A token's content: an element with an image is identified by its images; one without is identified by its text.** DomFacts has no parent links, so "the element's own text" cannot be separated from its children's text. 3. **Constrain direction** uses "some attribute moved that way and none moved the other way", across font-size, box area, text length and word count. Box _area_ rather than width lets a smaller font that reflows onto fewer, wider lines still read as "decrease".
4. **Colour, weight and spacing changes are not measurable from facts.** The semantics now route them to `add`, which the model verifier checks.

4. **Finding 4: the doctype survives the header rescue.**
   - When the item-5 re-cut happens, a doctype that appeared before the header in the first cut is prepended to the re-cut document, if the re-cut document has none of its own.

   - `locateDocument` now returns `{ at, length, html }`, so `html` is no longer necessarily a raw slice. `before`/`after` are computed from `at` and `length`.

## Consequence of the ≥50% rule (flag for the controller)

**Heavy cuts now read as gone.** Suppose a constrain's target phrase vanishes and its passage keeps fewer than half its words, e.g. "keep the body under 5 words". The passage then has no counterpart and reads as **gone**, so the constrain misses because it treats the edit as a deletion.

- Under round 2 the position fallback found that passage. My round-2 test "falls back to position when the targeted phrase is gone" now asserts the miss instead, renamed to "phrase gone: a passage that kept under half its words reads as gone (fail closed)".
- A new test covers a moderate cut that loses the phrase but keeps most of the words; it still passes.
- Mitigation: the constrain semantics now say a text phrase used as the target "must still be present after your edit". When it is, the passage is found by the phrase-survives path, whatever the cut.
- For `remove`, "gone" counts as reduced, so remove is unaffected.
