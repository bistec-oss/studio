## What was implemented

### The attempt loop: new `src/lib/drafts/refineAttempt.ts` (Ruling F)

`runRefineAttempts(input, deps)` (`:268`) takes two injected dependencies: `runRefine({attempt, model, retryReasons?})` returns the raw reply, and `verify(req)` returns `{result: VerifyResult, modelCalls}`. It also takes an optional `parseConflict`.

Each attempt runs these steps:

1. **Conflict check (API mode) before the envelope is parsed** (`:283`). CLI mode passes no `parseConflict`.
2. **`parseRefineEnvelope`.** If there is no document, the attempt is a miss.
3. **Truncation rule** (`:220`). A document with no closing `</html>` is a miss. It is never rendered or verified.
4. **FR-04/AC-10, enforced by the route** (`:237`). `effectiveClasses()` checks each downgraded class against `INSTRUCTION_CLASSES[c].destructive`. A downgraded replace/remove is a miss, and the retry is told `replace: supersedes was empty, so nothing may be replaced — …`. A downgraded constrain simply stays `add` and goes to the Haiku verifier.
5. **Ruling C reconcile, run on `env.html` only** (`reconcileTokens`, `:129`):
   - renamed, duplicated or unknown tokens → mismatch;
   - a `__INLINE_ASSET_` prefix count higher than the number of well-formed sent tokens → mismatch (the truncated-prefix case);
   - an absent token that a supersedes fragment names, with a non-downgraded destructive class present → `intended-removal` (committed with the asset gone);
   - any other absent token → `preservation-miss` (retry path).
   - Reasons are capped at 300 characters.
6. **Verification runs only if steps 2–5 found nothing.** So an attempt that has already missed never spends a verifier call. A `verify` that throws fails closed as `unavailable` (`:299`). Acceptance goes only through `isAccepted()`, which accepts `pass` alone (FR-10).
7. **Retry.** A miss on attempt 1 re-runs the refine once, on the same `input.model` (AC-20b), with `retryReasons` set. A miss on attempt 2 returns `not-applied`. `MAX_REFINE_ATTEMPTS = 2` (`:62`), and there is at most one verify per attempt. That structurally caps a refine at 2 refine calls and 2 verifier calls (AC-15).

What the loop returns:

- **`accepted`:** `html` is `restoreInlineAssets(env.html)`, exactly the document that was verified ("verify and commit the same document").
- **`not-applied`:**
  - `reason` (human-readable);
  - `html`: the last attempt's restored document if it is usable, otherwise `null`;
  - `unusableHtml`: the model-facing document, kept for diagnosis;
  - `diagnostics`.
- **`conflict`.**

`settleRefine(result, sinks)` (`:336`) is the only place an outcome becomes a write:

- `commit` is called for accepted, and nothing else commits (AC-16 is a property of this switch);
- `reject` is called for not-applied, and it returns `'not-applied'`;
- `conflict` is called for a conflict.

### Rejected-render record in `revisions.ts` (Rulings D and E)

- **`refineAttemptDiagnosticsSchema` / `rejectionDiagnosticsSchema`** (zod, `:200` / `:233`). The exact shape is below.
- **`recordRejectedRender(args)`** (`:296`):
  - renders and uploads the last usable document once;
  - writes one rejected row in a transaction: `revisionNumber: null`, `rejectedAt`, `instruction`, `htmlSnapshot` (restored html, or `unusableHtml`, or `''`), `exportUrl` (key or null) and `rejection` (zod-parsed);
  - sets `Draft.notAppliedReason` (capped at `MAX_NOT_APPLIED_REASON = 500`) and `Draft.notAppliedRevisionId`.
  - A render/upload failure is logged. The row is still recorded, with `export: 'render-failed'` and no export, so the not-applied outcome is never masked.
- **`discardNotAppliedRender(client, draftId)`** (`:262`). A single `updateMany` with no read. It stamps `discardedAt` on the rejected row the draft references, filtered on `notAppliedOn: { some: { id } }`, `rejectedAt` not null, `adoptedAt` null and `discardedAt` null. It runs whenever the outcome is cleared (commit, successful action) or replaced (a newer rejected render).
- **`commitDraftRevision`** now discards and applies `NOT_APPLIED_CLEARED` inside its existing transaction (`:159–163`). This covers refine success and inline-edit. T19's adopt will go through it too.
- **Classes are never on committed rows** (FR-02). They exist only in `rejection` JSON, which a CHECK constraint allows only on rejected rows.

### Not-applied lifecycle in `draftActions.ts`

- `completeDraftAction` (`:41`) is the success release. It is a **batch** transaction: discard first, then clear `pendingAction`, `pendingActionError` and `notApplied*`.
- `startDraftAction` accepts `work: () => Promise<void | DraftActionCompletion>`, where `DraftActionCompletion = 'not-applied'`.
  - On `'not-applied'` it uses the plain `releaseDraftAction(draftId)`, which releases with no error and keeps the outcome just recorded.
  - Every other success clears the outcome. That includes regenerate-design/copy, as a DB side effect only.
- A crashed run is now also logged with `console.error`. The next claim clears `pendingActionError`, so without the log a crash could vanish.

### Route (`src/app/api/drafts/[id]/refine/route.ts`)

The route is kept thin:

### Flat supersedes: I chose the replace-only exemption, not per-clause (`instructionClasses.ts:375`, header `:80`)

`replacedWholesale(after, r)` counts a text or token fragment as "replaced wholesale" when all of these hold:

- its images are gone;
- the passage is not intact;
- for a text fragment, the named phrase is gone;
- no same-shape element (for a token, no element still carrying it) keeps half or more of the passage's distinct words.

The id is deliberately not followed. Replace may reuse the same element, and following the id was the second way "change the headline to X and remove the logo" failed (a headline with `id="headline"`).

Such a fragment:

- satisfies replace when remove is co-present;
- is exempt from remove's per-fragment and shape checks, but only when replace is present. remove+add still requires the reduction.

**Why this over per-clause:**

- It needs no change to the envelope protocol, parser or prompt, and no change to T12/T13/T14 types.
- It passes the target case whether or not the model labels its fragments.
- A rewording that keeps half the words still has to shrink, so all the existing I1/N4b/R1 guards still hold.

**Accepted consequence** (documented in the header): in a replace+remove, a passage that the remove clause should have shortened, but that was instead rewritten wholesale and made longer, passes. Per-clause supersedes is the stated upgrade path.

A `helpers distinctWords`/`sharedWords`/`keepsMostOf` refactor makes counterpart's overlap and the new check share one definition. Counterpart's behaviour is unchanged (98/98 in `instructionClasses`).

## For T18, T19 and T21

- **Draft fields:**

  - `notAppliedRevisionId`: the rejected `DraftRevision.id`.

  ```
  { version: 1, refineCalls: 1..2, verifierCalls: 0..2, reasons: string[],   // final attempt's

  ```

  - `commitDraftRevision` runs `discardNotAppliedRender` inside its transaction, and that call skips rows with `adoptedAt` set.

### I1 — mechanism

- Prisma interactive transactions default to `maxWait` 2000 ms to acquire a pool connection. On this Windows host a new pool connection to `localhost` takes ~2.1 s (the engine tries `::1` first and is refused; Postgres listens on 127.0.0.1 only). A parallel refine burst grows the pool, so a winner's `commitDraftRevision` transaction waited >2000 ms and failed P2028 ("Unable to start a transaction in the given time") after its 202. The next winner's claim then cleared `pendingActionError`, so the final poll saw no revision, no rejected row and no error — exactly run 1.
- Evidence (temporary instrumentation removed): cold-pool bursts log `refine 202/409 in 2.2s` with ~2.1 s of application time. The failing draft `cmukku41p…` has two requests at 2.3 s. 6 fresh-server cycles showed 8 stalls each, and the unmodified pre-T17 code at c53cacee showed the same 8 stalls, so this is the environment and not T17. Per-step timing: the claim returned after 2069 ms and the brand-kit lookup after 2076 ms, against ~20 ms normally. `::1:5432` is refused, and `dns.lookup('localhost')` returns `::1` first. A standalone Prisma 5.22 repro against the `.env.test` URL: `localhost` with the 2 s default → P2028 after ~2.0 s (2/2); `localhost` with maxWait 10 s → OK after ~2.05 s; `127.0.0.1` with 2 s → OK after ~10 ms. A batch transaction has no maxWait, so the same wait just took ~2.05 s and succeeded.
- Test contract: H7a's "one revision per 202 winner" is supposed to fail when a winner's run crashes. The test was right, so it is unchanged.
- Fix:
  - `withNextRevisionNumber` (refine, inline-edit, regenerate-design) and `recordRejectedRender` pass `{ maxWait: TX_MAX_WAIT_MS = 10_000 }` via `TX_OPTIONS` in revisions.ts.
  - `claimDraftAction` no longer clears `pendingActionError`. A crash's error survives until the next run settles: a success clears it, a not-applied refine clears it, a new crash replaces it.
  - `[draft-action] draft … failed:` logs every crash.
  - UI unaffected: RefinementPanel and CopyEditor read the error only when `pendingAction` returns to null.
  - Rejected: pointing `.env.test` at 127.0.0.1. That hides this host's trigger, and any slow connect would still hit a 2 s limit shorter than the engine's own.

### Minor 1

`refineAttempt.ts` records `outcome.modelCalls` exactly as spent (no `Math.min`). An over-spend produces diagnostics the schema rejects: at most 1 per attempt and 2 in total.

### Minor 2

`recordRejectedRender` validates `rejectionDiagnosticsSchema.omit({ export: true })` before any render or upload.

### Minor 4

`touchDraftAction(draftId, action)` bumps `updatedAt` only `WHERE pendingAction = action`, so it cannot revive a swept action. The refine route calls it at the start of each attempt. Worst case between heartbeats in CLI mode:

- attempt 1 → attempt 2: 300 s refine + 60 s after-facts render + 60 s verifier ≈ 420 s;
- attempt 2 → settled: 420 s + 60 s final render + upload + ≤10 s transaction wait ≈ 490 s.

Both are under the 900 s sweep, with ~410 s of margin. The claim → attempt 1 stretch (background step) is unchanged and shared with regenerate-design.
