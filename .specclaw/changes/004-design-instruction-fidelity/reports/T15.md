## Representation chosen and why

**A rejected row has a NULL `revisionNumber` plus a non-null `rejectedAt`. A DB CHECK constraint makes those two facts the same statement.**

`DraftRevision.revisionNumber` becomes `Int?`. A committed row keeps its number (1..N, contiguous per draft). A rejected row has **no chain position at all**.

Why this beats negative numbers:

1. **The pointer structurally cannot reference a rejected row.** `Draft.currentRevisionNumber` is an Int that is compared to `revisionNumber`, and `= N` never matches NULL in SQL. The same goes for restore's `[rev]`: it is parsed as an integer, so it cannot express "the rejected row". A row id gives 400 and any number gives 404. With negative numbers, a pointer or `[rev]` of `-1` would address a rejected row.
2. **Contiguity is free.** Rejected rows consume no number, so committed numbers stay 1..N (TC-REG-H7a). With negative numbers, `max+1` over only-rejected rows gives 0, and a filter is still needed.
3. **The unique constraint holds unchanged.** Postgres UNIQUE treats NULLs as distinct, so `@@unique([draftId, revisionNumber])` accepts any number of rejected rows.
4. **The type system helps.** Prisma now types `revisionNumber` as `number | null`. Any new raw read of the table therefore gets a nullable number and has to confront it.
5. **The database enforces it.** `CHECK (("revisionNumber" IS NULL) = ("rejectedAt" IS NOT NULL))` means "numbered but rejected" and "unnumbered but committed" cannot exist.

**The one leak the representation does NOT close structurally is ordering.** Postgres sorts NULLs **first** under `ORDER BY … DESC`. The old `withNextRevisionNumber` query (`findFirst where {draftId} orderBy desc`) would therefore return the rejected row as "latest" and compute `null ?? 0 + 1 = 1`. The result would be a P2002 loop ending in a 500 on every refine, inline edit and regenerate.

I confirmed this empirically with a negative control. I blanked the filter and re-ran §U: TC-REJ-02 failed with `Unique constraint failed on (draftId, revisionNumber)`, and TC-REJ-01 failed on the count.

Hence **filter at the query helper**. `COMMITTED_REVISION = { rejectedAt: null, revisionNumber: { not: null } }` is the single definition, exported from `src/lib/drafts/revisions.ts`, together with:

- `committedRevisionWhere(draftId)`
- `listCommittedRevisions(draftId)`: the version-switch list, newest first. It also re-filters nulls after the query, so its return type is `revisionNumber: number`.
- `findCommittedRevision(draftId, n)`: the restore/Undo target.
- `nextRevisionNumber(tx, draftId)`: used inside `withNextRevisionNumber`.

The filter states both conditions even though the CHECK makes them equivalent, so it holds on its own terms. The unit tests cover a CHECK-violating corrupt row.

## Migration SQL (`prisma/migrations/20260927130000_refine_not_applied/migration.sql`)

This is separate from Phase 1's `20260927120000_draft_font_set` (NFR-06). All columns are nullable and there is no backfill. `prisma migrate diff` from a freshly migrated DB against the schema is empty, so there is no drift. Prisma does not model CHECK constraints and ignores them in its diff.

```sql
ALTER TABLE "Draft" ADD COLUMN     "notAppliedReason" TEXT,
ADD COLUMN     "notAppliedRevisionId" TEXT;

ALTER TABLE "DraftRevision" ADD COLUMN     "adoptedAt" TIMESTAMP(3),
ADD COLUMN     "adoptedRevisionNumber" INTEGER,
ADD COLUMN     "discardedAt" TIMESTAMP(3),
ADD COLUMN     "rejectedAt" TIMESTAMP(3),
ADD COLUMN     "rejection" JSONB,
ALTER COLUMN "revisionNumber" DROP NOT NULL;

ALTER TABLE "DraftRevision" ADD CONSTRAINT "DraftRevision_rejected_iff_unnumbered"
  CHECK (("revisionNumber" IS NULL) = ("rejectedAt" IS NOT NULL));

ALTER TABLE "DraftRevision" ADD CONSTRAINT "DraftRevision_rejection_fields_only_when_rejected"
  CHECK (
    "rejectedAt" IS NOT NULL
    OR ("rejection" IS NULL AND "adoptedAt" IS NULL AND "adoptedRevisionNumber" IS NULL AND "discardedAt" IS NULL)
  );

ALTER TABLE "DraftRevision" ADD CONSTRAINT "DraftRevision_adoption_complete"
  CHECK (("adoptedAt" IS NULL) = ("adoptedRevisionNumber" IS NULL));

ALTER TABLE "Draft" ADD CONSTRAINT "Draft_notAppliedRevisionId_fkey" FOREIGN KEY ("notAppliedRevisionId") REFERENCES "DraftRevision"("id") ON DELETE SET NULL ON UPDATE CASCADE;
```

(The file itself also carries explanatory comments.)

**Columns:**

- `DraftRevision.rejectedAt`: the rejected marker.
- `DraftRevision.rejection Json?`: free-form diagnostics holding the classes and the verifier's miss. The instruction is already a column.
  - **FR-02 vs FR-13 ruling:** this is recorded in a schema comment at the column. Classes are stored here only, never as a typed column. The second CHECK makes them impossible on a committed row, so FR-02 is enforced by the DB for committed rows.
- T19 adoption bookkeeping:
  - `adoptedAt` + `adoptedRevisionNumber`, all-or-nothing by CHECK.
  - `discardedAt`. I added it because FR-14a says "already-adopted **or discarded** → 409", and T19 must not need its own migration.
- `Draft.notAppliedReason` + `Draft.notAppliedRevisionId`:
  - The reference is a real FK with `ON DELETE SET NULL`, so the draft hard delete (revisions first, then draft) keeps working.
  - These are separate from `pendingActionError`.
- Relation names were added (`"DraftRevisions"`, `"DraftNotAppliedRevision"`) because there are now two Draft↔DraftRevision relations. This is a schema-only change with no DB effect.

## How T19 will address a rejected row

**By row id, not by `[rev]`.** A rejected row has no number, and `[rev]` under `/revisions/[rev]/` is an integer for `restore`. Reusing that segment for an id would give one dynamic segment two meanings.

Recommended route: **`POST /api/drafts/[id]/rejected/[revisionId]/adopt`**. This deviates from the tasks.md sketch `/revisions/[rev]/adopt`, and the path in tasks.md should be updated.

T19 should look the row up with `{ id: revisionId, draftId: params.id, rejectedAt: { not: null }, adoptedAt: null, discardedAt: null }`: a miss on id/draft gives 404, an adopted or discarded row gives 409. It then commits a fresh row via `commitDraftRevision`, which gets the next committed number and moves the pointer. It records `adoptedAt` + `adoptedRevisionNumber` on the rejected row and clears `Draft.notApplied*`.

**Hand-off notes for T19:**

- **Atomicity.** `commitDraftRevision` offers no hook into its transaction. For the commit and the adoption stamp to be atomic, T19 should either add an optional `onCommitted(tx, revisionNumber)` argument or do a guarded `updateMany where adoptedAt IS NULL` claim before committing. The `pendingAction` claim already serializes it.
- **"Marked user-accepted" on the committed row.** This is derivable from the reverse link (`rejected.adoptedRevisionNumber = committed.revisionNumber`). I added no column for it on committed rows, to keep FR-02 clean. If T19 wants it visible in the list, prefixing the instruction (e.g. "Used anyway: …") needs no schema change.

## 1. (Important) Down path documented in the migration header, in order

This is a manual down path: Prisma has no down migrations. The header explains why the order matters.

Code from before Phase 2 uses an unfiltered newest-first `withNextRevisionNumber`. Postgres sorts NULLs first under DESC, so a single rejected row makes that query compute 1. Every retry then fails on the unique constraint (P2002). The result: every refine, inline edit and regenerate-design fails for that draft.

Step 2 therefore **must run before, or together with, any revert of Phase 2 code**, including a Coolify rollback to a pre-Phase-2 image. Steps 1 and 2 on their own make pre-Phase-2 code safe again. Steps 3 and 4 restore the schema.

```sql
-- 1. detach drafts from the rejected rows about to be deleted
UPDATE "Draft" SET "notAppliedReason" = NULL, "notAppliedRevisionId" = NULL;
-- 2. delete every rejected (out-of-chain) render (an adopted render's committed copy is a numbered row and is kept)
DELETE FROM "DraftRevision" WHERE "revisionNumber" IS NULL;
-- 3. drop the FK, its index and the three CHECK constraints
ALTER TABLE "Draft" DROP CONSTRAINT "Draft_notAppliedRevisionId_fkey";
DROP INDEX "Draft_notAppliedRevisionId_idx";
ALTER TABLE "DraftRevision" DROP CONSTRAINT "DraftRevision_rejected_iff_unnumbered";
ALTER TABLE "DraftRevision" DROP CONSTRAINT "DraftRevision_rejection_fields_only_when_rejected";
ALTER TABLE "DraftRevision" DROP CONSTRAINT "DraftRevision_adoption_complete";
-- 4. restore NOT NULL, then drop the added columns
ALTER TABLE "DraftRevision" ALTER COLUMN "revisionNumber" SET NOT NULL;
ALTER TABLE "DraftRevision" DROP COLUMN "rejectedAt", DROP COLUMN "rejection",
  DROP COLUMN "adoptedAt", DROP COLUMN "adoptedRevisionNumber", DROP COLUMN "discardedAt";
ALTER TABLE "Draft" DROP COLUMN "notAppliedReason", DROP COLUMN "notAppliedRevisionId";
-- then: DELETE FROM "_prisma_migrations" WHERE "migration_name" = '20260927130000_refine_not_applied';
```
