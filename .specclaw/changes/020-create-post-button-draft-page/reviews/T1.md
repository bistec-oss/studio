## Findings

### [WARN] tests/e2e/create-post-button.test.ts:AC-02b — Send-not-covered check is likely vacuous at 1440×900 — Quality (test quality)

**Problem:** `send.scrollIntoViewIfNeeded()` centres the target when it is outside the viewport. Send is in the right column of the `xl:grid-cols-[0.92fr_1.08fr]` grid (`src/app/(app)/drafts/[id]/page.tsx:412`, `:627`), and it is the trailing 34 px submit inside the refine pill (`src/components/drafts/RefinementPanel.tsx:364-376`). If it starts below the fold, it is moved to about y≈450 in a 900 px viewport. The floating button is `fixed bottom-6 right-6` (`CreatePostButton.tsx:29`), so it occupies roughly y 824–876 and x ≈1250–1416. Its centre is not in that band, so `elementFromPoint` returns Send and the test passes with the button restored. The check only bites when Send is already in the bottom-right band at load, which I could not confirm without running the page. The spec's claim that the test "would fail if the button came back" (`spec.md`, AC-02 "What it guards") is therefore not established. The implementer's report says no mutation check was run.

Quoted:

```
await send.scrollIntoViewIfNeeded()
const result = await send.evaluate((el) => {
```

**Fix:** Put Send inside the button's footprint before the hit test, then run a mutation check. For example, after the scroll, `window.scrollBy(0, r.bottom - (window.innerHeight - 24))` moves Send's bottom edge onto the button's bottom edge, so its centre lands in y 824–876. Then confirm `elementFromPoint` returns the button when the button is restored on this page (temporarily, in the working tree), and that the test fails. If the x ranges do not overlap at 1440, scroll horizontally too, or assert on a probe point inside the button's corner. Record the mutation result in `reports/T1.md`. Until then, the spec's "it would fail if the button came back" claim should be softened.
